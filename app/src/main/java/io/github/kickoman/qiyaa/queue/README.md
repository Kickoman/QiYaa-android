# `queue/` — очередь

Что играть: источники (лайки, плейлист, альбом, артист, станция, волна, поиск), режим джема, тикеты «побеждает последний запрос», поколения очереди, догрузка волны, продолжение очереди волной по истории, выделение и правка очереди, лайки и дизлайк, отметка `/play-audio`, политика ошибок воспроизведения и правило shuffle. Порт очереди из `src/core/player.cpp` десктопной версии; поведение описано сценариями `spec/player/` (ID вида `SRC-06`, `WAVE-05`, `ERR-04`), режим джема — `spec/jam/host.md` (`HOST-01`…).

Пакет **не** знает про ExoPlayer: плеер виден ему как интерфейс `PlayerEngine`, а адаптер к Media3 — `playback/Media3Engine`. Он **не** ходит в сеть сам: запросы идут через `MusicSource` (в приложении — `LibraryMusicSource` над `yandex/Library`). Он **не** показывает текст: всё для пользователя уходит `QueueEvent`, а строку собирает `ui/QueueEventText.kt`.

Чистая JVM, импортирует только `yandex`:

```bash
grep -rlnE '^import (android|androidx)' app/src/main/java/io/github/kickoman/qiyaa/queue/   # ничего не печатает
grep -rln 'qiyaa\.\(playback\|ui\|data\)\.' app/src/main/java/io/github/kickoman/qiyaa/queue/   # ничего не печатает
```

## `QueueController`

```kotlin
data class QueueState(entries: List<QueueEntry>, title: String, isWave: Boolean, loadingMore: Boolean, selected: Set<Int>, activeSourceId: String?, continueWithVibe: Boolean = false) {
    val tracks: List<Track>   // entries.map { it.track }; в equals не входит
}
data class QueueEntry(track: Track, part: EntryPart = HEAD, wave: WaveContext? = null, item: ItemMark? = null, seedsVersion: Int? = null) {   // wave: сессия, станция и порция; null — без фидбека
    val isWaiting: Boolean   // ITEM, который ждёт
    val isJamItem: Boolean   // ждёт и с itemId: часть джема
    val isSpent: Boolean     // OTHER или ITEM, который уже не ждёт: играет снова, только если его выбрали
}
enum class EntryPart(key: String) { HEAD("head"), CONTINUATION("continuation"), ITEM("item"), OTHER("other"); companion object { fun fromKey(key: String?): EntryPart?; fun defaultFor(isWave: Boolean): EntryPart } }
data class ItemMark(itemId: String?, addedBy: String, waiting: Boolean)   // itemId null — элемент прошлого джема
data class PlayModes(shuffle: Boolean = false, repeat: Boolean = false, locked: Boolean = false)   // выбор пользователя; locked — «Моя волна» или станция

class QueueController(source: MusicSource, connectivity: Flow<Boolean>, scope: CoroutineScope, io: CoroutineContext, newPlayId: () -> String = UUID, clock: () -> Long = монотонные мс, store: QueueStore? = null, logFailure: (Stage, Throwable) -> Unit = {}, continueWithVibeByDefault: () -> Boolean = { true }) {
    val state: StateFlow<QueueState>;  val events: SharedFlow<QueueEvent>;  val engine: PlayerEngine?
    val modes: StateFlow<PlayModes>
    fun attach(engine: PlayerEngine);  fun detach(engine: PlayerEngine)
    fun resumePoint(): ResumePoint?   // треки, индекс и позиция для «играть» после выгрузки процесса; null — очередь пуста
    // команды из UI
    fun loadSource(title: String, sourceId: String? = null, autoplay: Boolean = true, loader: suspend () -> List<Track>)
    fun playWave(seeds: List<String>, title: String, sourceId: String = seeds.first())
    fun search(text: String, title: String)
    fun setQueue(tracks, title, isWave, autoplay, sourceId);  fun clear()   // setQueue: записи части defaultFor(isWave), без контекстов; в джеме оба — новая база (HOST-21, HOST-36)
    fun removeIndices(indices: Set<Int>);  fun toggleSelected(index: Int);  fun selectAllOrNone()   // в джеме ждущие элементы джема уходят через сервер (HOST-36)
    fun next();  fun previous();  fun stop()   // транспорт: сюда приходят кнопки приложения, уведомление и гарнитура
    fun setShuffle(on: Boolean);  fun setRepeat(on: Boolean)   // выбор пользователя: экран плеера и команды сессии
    fun toggleLike(track: Track);  fun setLiked(track: Track, liked: Boolean);  fun dislike(track: Track)
    fun currentWaveSeed(): String?   // станция (первый сид) играющей волны; null для обычной очереди
    fun likeCurrent();  fun dislikeCurrent()   // то же для текущего трека плеера (кнопки уведомления); без движка или трека — ничего
    fun requestMore()   // «вперёд» в конце волны: снова запросить догрузку и продолжить с первого нового трека
    fun setContinueWithVibe(on: Boolean)   // флаг «продолжать волной» этой очереди; в волне и станции и при том же значении — ничего
    // события движка
    fun onItemChanged(track: Track?, transition: Transition, isPlaying: Boolean);  fun onEnded()
    fun onPlayingChanged(isPlaying: Boolean);  fun onFailure(kind: FailureKind, error: ErrorKind)
    fun onSeeked()   // перемотка внутри текущего трека: конец ожидания продолжения, отчёт джема (HOST-06), сохранение позиции
    fun onPausedAtEnd()   // движок встал на паузу в конце трека по pauseAtEndOfCurrent: переход к цели обхода (заворот головы, CONT-10), конец очереди или просто play()

    val isJamActive: Boolean
    fun startJam(listener: JamPlaybackListener, waveFeedback: Boolean)   // очередь не меняется: она — база
    fun onJamQueue(entries: List<JamEntry>, seeds: List<String>, seedsVersion: Int)   // из каждого state сервера
    fun jamSkip(itemId: String)   // command{skip}
    fun reportJamPlayback()   // onPlayback того, что играет сейчас (HOST-26)
    fun endJam()   // и без джема: восстановленная очередь
    companion object { MY_WAVE_SEED = "user:onyourwave"; LOAD_MORE_WHEN_LEFT = 2; WAVE_HISTORY = 5; RESTART_AFTER_MS = 3_000; PLAYING_REPORT_MS = 10_000 }
}
```

В приложении `AppGraph` создаёт контроллер со `scope` на `Dispatchers.Main.immediate` и `io = Dispatchers.IO`; все методы вызываются с главного потока, запросы `MusicSource` и загрузчики — на `io`. В тестах оба — диспетчер `runTest`, время виртуальное. `continueWithVibeByDefault` — значение настройки «продолжать волной» для новых очередей (CONT-01), в том числе для начальной пустой очереди нового контроллера (её флаг решает в джеме, HOST-14); пакет не может импортировать `data/`, поэтому это лямбда. `AppGraph` передаёт `{ settings.continueWithVibe.value }` (ключ `playback/continueWithVibe`, `data/README.md`); переключатели на экранах — `ui/README.md`, «Продолжать волной».

Гарантии (сценарии `spec/player/`):
- **Побеждает последний источник** (SRC-01…03). Каждый `loadSource`/`playWave`/`search` берёт билет; ответ или ошибка устаревшего билета отбрасываются молча. Поиск с лучшим артистом или альбомом — один источник, как бы много запросов он ни делал. `SourceLoaded` несёт число доступных треков источника, а не всей очереди: в джеме очередь держит ещё текущий трек и элементы.
- **Недоступные треки** (`available == false`) не попадают в очередь (SRC-05). Источник, в котором нет ни одного доступного трека, оставляет очередь и воспроизведение как есть и сообщает `SourceEmpty` (SRC-07, SRC-08); поиск — `NothingFound` (SRC-12); первая порция волны — `SourceEmpty` без сессии и догрузки (WAVE-03). Проверка на пустоту идёт после фильтра доступности.
- **Волна** стартует с `SourceLoading` сразу и `WaveStarted` после ответа (WAVE-01). Догружается, когда текущий трек — один из двух последних в порядке воспроизведения (`LOAD_MORE_WHEN_LEFT = 2` считает текущий вместе с оставшимися), с последними 5 id очереди, не больше одного запроса за раз (WAVE-05, WAVE-06). Поколение очереди не даёт дописать ответ к уже заменённой очереди, а её ошибку показать (WAVE-07). Если плеер дошёл до конца во время догрузки, продолжает с первого нового трека (WAVE-08); его индекс берётся прямо перед дописыванием, так что строки, удалённые во время запроса, его не сдвигают. Неудачная догрузка в конце волны сама не повторяется; `requestMore()` («вперёд») отправляет запрос снова, и после ответа воспроизведение продолжается с первого нового трека (WAVE-09). Ответ, где нет ни одного доступного трека, ничего не меняет. Тот же механизм догружает и волну по истории (ниже).
- **«Ждёт продолжения»** (`continueAtEnd`). Ответ догрузки сам включает воспроизведение, только если очередь его ждёт: трек кончился (`onEnded`), когда продолжение следует, «вперёд» в конце (`next()`, `requestMore()`) или сломанный последний трек (ERR-07). Если после этого запроса в пути нет, ожидание снимается. Без ожидания ответ просто дописывается: так включение флага в остановленной в конце очереди спрашивает волну, но играет её только «вперёд» (CONT-03), как на десктопе. Ожидание кончается и тогда, когда пользователь сам решил, что играть, как в `Player::stop()` и `playIndex()` десктопа: «стоп» (`stop()`), новый текущий трек (`onItemChanged` с треком: выбор строки, «плей» в конце, который перематывает к первому треку) и перемотка внутри текущего (`onSeeked`: «плей» в конце из уведомления, выбор текущей строки, ползунок, «назад» после 3 с). Ответ, пришедший после этого, только дописывается и не уводит с выбранного трека, а строка «загружаю ещё» волны по истории гаснет сразу. Своя волна живёт по тем же правилам (WAVE-08): ждать заставляет только сам конец. Запрос в пути отмечает приватный флаг `asking` (не больше одного запроса, WAVE-06); `QueueState.loadingMore` — то, что показывает строка «загружаю ещё» в плейлисте: для своей волны — пока идёт любой запрос, для волны по истории — только пока очередь ждёт, тихий запрос CONT-04 строки не показывает.
- **Продолжение волной по истории** (CONT-01…08, `spec/player/continuation.md`). У очереди, чей источник своего продолжения не имеет (лайки, плейлист, альбом, артист, поиск), за головой может идти волна ротора по сидам из её истории.
  - **Флаг** `QueueState.continueWithVibe`. Каждая новая очередь (`loadSource`, `search`, `setQueue`, `playWave`) и `clear()` берут его из `continueWithVibeByDefault()` (CONT-01); в «Моей волне» и станции он ничего не меняет, и `setContinueWithVibe` там ничего не делает. `setContinueWithVibe(on)` меняет только эту очередь, не настройку (CONT-02), и сохраняет её. Включение снимает остановку (см. ниже) и сразу проверяет догрузку, так что при «осталось ≤ 2» волна стартует сразу; выключение запрещает новые запросы, а ответ, который уже в пути, дописывается (он отвечает на запрос, сделанный при включённом флаге, как на десктопе), и её треки доигрывают, после чего очередь останавливается, как TR-04. То же значение ещё раз ничего не делает: нажатие на уже горящее «вкл» не снимает остановку и не спрашивает снова.
  - **Сиды** (CONT-05) — `StartHistory`: трек записывается, когда **начался** (тот же момент, что `/play-audio`), и только если начавшаяся запись — не `CONTINUATION`: голова, элементы джема (`ITEM`) и `OTHER` (CONT-05: треки этой очереди, которые начинались, как `noteStarted` десктопа). Треки продолжения (волны по истории и волны джема) сидами не бывают, даже если тот же id есть в голове: часть берётся у записи, а не у id. Все `Track` Android приходят из каталога Яндекс Музыки, поэтому исключение «не из Яндекс Музыки» здесь отбрасывать нечего. История очищается новой очередью и `clear()`.
  - **Когда проверяется** (CONT-04): трек стал текущим (`onItemChanged`), трек начался (конец `onStarted`, вне своей волны — сид появляется только после старта, CONT-06), включение флага, конец очереди (`onEnded`), «вперёд» в конце, ERR-07, `state` джема, пока трек играет или на паузе. Условия: флаг включён, нет остановки, повтор не держит голову (тогда `remaining` = `Int.MAX_VALUE`, см. «Повтор действует только в голове»), осталось ≤ 2 в порядке воспроизведения, и есть хотя бы один сид. Без сида запроса нет, и голова останавливается в конце, как TR-04 (CONT-06).
  - **Первый запрос** — `startWave(history.seeds())` (`track:<id>`, без альбома: альбом заставил бы ротор начать «Мою волну», `spec/jam/seeds.md`). Без `SourceLoading`, `WaveStarted` и тостов: доступные треки ответа дописываются после головы как `CONTINUATION` с `WaveContext(сессия, первый сид, batchId)`. Сессия и станция (первый сид — запасной путь TRK-10) запоминаются, `radioStarted` уходит до первого `trackStarted` (канал фидбека упорядочен). Дальше — догрузка как у волны (WAVE-05…09): `moreWave` с последними 5 id очереди, какой бы части они ни были.
  - **Остановка** (`stalled`, CONT-07). Первый запрос упал (`Failed(Stage.WAVE)` — та же строка «ошибка волны», что у WAVE-04) или не принёс ни одного доступного трека (без статуса): ничего не дописывается, и больше никаких запросов — голова доигрывает и останавливается, как TR-04. Снимают остановку «вперёд» в конце (с сидами, какие есть тогда), включение флага, новая очередь, `clear()` и `state` джема с новой версией сидов (HOST-11). Ошибка более поздней догрузки — `Failed(Stage.WAVE_MORE)` и правила WAVE-09, без остановки.
  - **«Вперёд» в конце** с включённым флагом: снимает остановку, ждёт продолжения и проверяет догрузку; запрос в пути — `LoadingMore`, запроса нет (нет сидов) — остановка, как TR-04.
  - **Фидбек** (CONT-08). `/play-audio` — для каждого трека вне джема. Фидбек ротора — по `entry.wave`: только треки волны и только в их сессию; треки головы его не шлют, даже если тот же id есть в волне.
  - **ERR-07.** `ErrorPolicy` получает `endless = continuationFollows()`: в своей волне — да; в очереди с головой — флаг включён, нет остановки и есть чем спросить (запрос в пути, сессия, сид истории или сиды джема). Остановленная волна по истории или волна без сидов на сломанном последнем треке останавливается. Если сломанный трек всё-таки заиграл (`onPlayingChanged(true)`, пока счётчик неудач не ноль: «плей» повторил его), ожидание продолжения снимается до сброса счётчика, и поздний ответ только дописывается, не уводя с трека.
  - **Восстановление.** Флаг берётся из файла, у файла без флага — из настройки; история — из файла; сессия волны по истории сохраняется так же, как у волны, и после восстановления устаревшая: первый запрос — `startWave` по сидам истории (без них — по сохранённой станции), затем `radioStarted` новой сессии, её первый сид становится станцией, треки дописываются в конец. Треки, пришедшие до выгрузки, шлют фидбек в свою старую сессию и порцию. `stalled` не сохраняется.
- **Shuffle и повтор принадлежат контроллеру; в волне они не действуют** (WAVE-10…12). Выбор пользователя приходит командой `setShuffle`/`setRepeat`: с экрана плеера (`ui/PlayerViewModel`) напрямую, из уведомления, Bluetooth и других контроллеров сессии — через `playback/QueueForwardingPlayer`. Эхо плеера (`onShuffleModeEnabledChanged`/`onRepeatModeChanged`) контроллер не слушает, режимы ExoPlayer пишет только он. Два экземпляра `WaveModeRule`: пока очередь заперта (`locked` = `isWave`: «Моя волна» и станция; джем режимы не запирает, они — режимы базы), выбор отклоняется и не запоминается; `applyModes()` ставит движку shuffle `playerModeFor(locked)`, а повтор — по курсору (ниже), то есть в запертой очереди оба выключены. `applyModes()` идёт при `attach`, `setQueue`, каждой смене трека (`onItemChanged`, после сбора ждущих элементов и до остальной работы), дописывании продолжения, `removeIndices`, `setShuffle`/`setRepeat`, `startJam`, каждом `state` джема (вставки, удаления, устаревший хвост) и `endJam`. Выбор и запертость публикуются в `modes`: экран плеера подсвечивает SHF/RPT по выбору и приглушает при `locked`. Выбор запоминается только вне волны и возвращается для обычных очередей. Так последний трек волны не переходит к первому, а ждёт догрузку (WAVE-08).
- **Ошибки воспроизведения** (ERR-01…07) — по `ErrorPolicy`, см. ниже.
- **Повтор действует только в голове** (CONT-10, CONT-11). «Повтор держит голову» = выбор повтора, очередь не заперта, курсор в голове (`inHead`) и в очереди есть хоть одна запись `HEAD`; пустая очередь тоже голова, так что повтор, выбранный на пустой очереди, сразу доходит до движка. `inHead` — как `Queue::inHead` десктопа: запись `HEAD` стала текущей — да, `CONTINUATION` — нет, `ITEM` и `OTHER` его не меняют; новая очередь ставит «есть ли записи `HEAD`», `clear()` — нет, восстановление — по ближайшей записи базы (`HEAD` или `CONTINUATION`) на сохранённом текущем или перед ним, а без такой записи — «есть ли `HEAD`». Пустая база с одними элементами и `OTHER` головы не держит: повтор не делает `remaining` бесконечным, и волна джема спрашивается (как навигатор десктопа с пустой головой). Пока держит, `remaining` = `Int.MAX_VALUE`, и волна по истории не стартует. Если продолжения в очереди нет, движку ставится повтор всей очереди (`repeatEnabled`), то есть головы, как раньше (TR-05). Если треки продолжения уже есть (пришли до включения повтора или ответ пришёл после), повтор очереди дошёл бы до них, поэтому `repeatEnabled = false`, а голову заворачивает сам контроллер: на последнем треке головы в порядке воспроизведения цель обхода — первый трек головы, а не продолжение, поэтому `pauseAtEndOfCurrent = true`, движок встаёт на паузу в конце трека и зовёт `onPausedAtEnd()` (раздел «Что играет следующим»). Курсор в продолжении — повтор выключен и порядок продолжения по индексу: «вперёд» и конец трека ведут к следующему треку продолжения, последний ждёт догрузку (WAVE-08, WAVE-09), а не заворачивает очередь. После выключения повтора треки продолжения идут за головой.
- **Заворот головы** — тот случай, где цель обхода расходится с порядком движка (раздел «Что играет следующим»): пауза в конце, «вперёд» на последнем треке головы и пропуск сломанного последнего трека головы по `ErrorPolicy` (`SkipToNext`, после заворота по-прежнему `prepare()` + `play()`: после ошибки плеер в `STATE_IDLE`) переходят к первому треку головы в порядке воспроизведения, то есть с shuffle — в проходе головы, через `wrapTo(target)`. Четвёртый путь — «назад» в пределах 3 с на первом треке головы (после ветвей перемотки #86): `wrapTo` к последнему треку головы. Если цель — сам текущий трек (голова из одного трека), это `restart()`: `seekTo` на тот же индекс в ExoPlayer смены трека не даёт, а TRK-02 считает повтор новым стартом. Стык на завороте не бесшовный.
- **«Вперёд»** (`next()`): цель обхода — сначала ждущие элементы, затем следующий трек в порядке воспроизведения (TR-03), с повтором — первый после последнего (TR-05, с продолжением в очереди — заворот головы выше); в конце конечной очереди — пауза и начало текущего трека, курсор остаётся (TR-04); в конце волны — `LoadingMore` и `requestMore()` (WAVE-09); в конце очереди с включённым флагом — волна по истории (выше). То же в джеме: своего «вперёд» у джема нет; удержанный элемент «вперёд» отпускает без перемотки («Режим джема»). Очередь помнит, что остановилась в конце (`stoppedAtEnd`): «вперёд» в конце без продолжения (TR-04), естественный конец без продолжения, остановка ERR-07 на последнем треке и ответ, который пришёл пустым или устаревшим, пока очередь ждала. Снимают его смена трека, начало игры, новая очередь и `clear()`. «Вперёд» из этого состояния, когда следующий трек уже есть (например, ответ волны пришёл до «вперёд»), переходит на него и делает `prepare()` + `play()`: после `stop()` плеер на паузе, после ошибки — в `STATE_IDLE` (CONT-03). `stop()` сам флаг не ставит: это и кнопка «стоп» посреди очереди.
- **«Назад»** (`previous()`): после 3 с (`RESTART_AFTER_MS`) — перемотка текущего трека в 0 (`seekToPosition(0)`), та же игра: ни `skip`, ни нового `trackStarted` и `/play-audio`, секунды прослушивания считаются дальше (TR-02). Иначе предыдущий трек, на первом с повтором — последний (с продолжением в очереди — последний трек головы, заворот выше), без повтора — рестарт первого трека (TR-01): `restart()`, как у «стоп», то есть `skip` и новая игра. В конце конечной очереди (`STATE_ENDED`, TR-04) позиция равна длине трека, поэтому «назад» перематывает последний трек в 0; его игра закрылась в конце (`onEnded`), так что, когда трек снова заиграет (ExoPlayer оставляет `playWhenReady`), это новый старт. Десктоп здесь идёт к предыдущему треку; спека этот случай не описывает.
- **Shuffle — проход головы** (TR-03). С shuffle порядок воспроизведения — проход головы (каждый её трек один раз, в случайном порядке), затем все остальные записи по индексу; записи, добавленные позже, в голову не попадают (см. «`PlayerEngine`» ниже). Проход начинается заново: `setTracks` (новая очередь, восстановление, `attach`) — с трека, с которого очередь играет; включение shuffle пользователем (`setShuffle(true)`, когда до этого он не действовал) — с текущего трека, если курсор в голове, как на десктопе. Ждущие элементы идут в проходе сразу за ним (`lead`, «`PlayerEngine`» ниже). Новая база в джеме (выбор источника, «очистить») начинает новый проход с текущего трека и ждущих элементов, если shuffle действует. `endJam` проход не трогает. Удаление строк проход сохраняет. Проход в файл не пишется: после выгрузки процесса новый проход начинается с восстановленного трека, так что уже сыгранные треки головы могут прозвучать снова. Голова кончается, когда проход сыграл каждый её трек по разу; затем идут треки продолжения в своём порядке (CONT-09). Ответ волны, пришедший посреди прохода, встаёт после головы, и проход не перемешивается. Shuffle в очереди с головой остаётся включённым и тогда, когда играет продолжение: порядок держит продолжение на месте; выключен он только в «Моей волне» и станции (WAVE-10).
- **Голова и продолжение.** Каждая запись очереди (`QueueEntry`) знает свою часть. «Моя волна» и станция (`playWave`) — все записи `CONTINUATION`, у каждой `WaveContext` своей порции, включая догруженные. `loadSource`, `search` и `setQueue(isWave = false)` — все `HEAD` без контекстов; волна по истории дописывается за ними записями `CONTINUATION` с контекстом своей порции. Элементы джема — `ITEM` с меткой `ItemMark` (кто добавил и ждёт ли), треки волны джема — `CONTINUATION` с контекстом и `seedsVersion` (таблица в «Режим джема»). Голова — не обязательно префикс: элементы встают за текущей строкой, в том числе посреди головы, поэтому движок получает индексы записей `HEAD`.
- **Сначала `state`, потом движок.** Каждая правка плейлиста движка идёт после такой же правки `state`, поэтому `entries[engine.currentIndex]` — та запись, о которой сообщает движок, в том числе в колбэке, который движок зовёт синхронно из самой правки (удаление текущего трека в ExoPlayer и `support/FakeEngine`). `onStarted` берёт часть и контекст из этой записи, сверив id трека. `removeIndices` удаляет по одному индексу по убыванию, а текущую строку — последней (ниже, «Удаление текущего трека»): сначала из `state`, потом из движка. Проверка: `./gradlew testDebugUnitTest --tests '*QueueEditingTest*entry the engine reports*'`.
- **Один хозяин плеера.** Движок может смениться (сервис пересоздан при живом процессе): `detach` запоминает трек и позицию, `attach` нового движка кладёт ту же очередь на паузе туда же, вместе с режимами shuffle и повтора. Очередь, выбранная без движка, применяется при `attach`; правка очереди без движка меняет только `state`. Подробнее — `playback/README.md`.
- **Очередь переживает выгрузку процесса** (Kickoman/QiYaa-android#8). Контроллер пишет `QueueSnapshot` в `store` при каждой правке очереди, смене трека, паузе, перемотке (`onSeeked`), смене shuffle или повтора и `detach`; запись идёт на `io` через `Channel.CONFLATED`, так что частые изменения дают одну запись. Конструктор читает `store` и восстанавливает `state` (с флагом «продолжать волной»), выбор shuffle и повтора, историю стартов, `inHead` (выше) и точку возврата: первый `attach` кладёт очередь на паузе на тот же трек и позицию. Записи восстановленной волны сохраняют свою часть и свой `WaveContext`, поэтому фидбек уходит в старую сессию и порцию. Для догрузки старая сессия не используется: первая догрузка после восстановления делает `startWave` по сохранённой станции, отправляет `radioStarted` новой сессии и дописывает её треки в конец.
- **Дизлайк** (TR-07, TR-10, TRK-07). `dislike(track)` всегда шлёт запрос `dislike`, а остальное решает в момент вызова, по id: если `track.id` — id текущей записи движка (трек под курсором: играет, на паузе или остановлен), дальше то же, что «вперёд»: следующий трек, в конце конечной очереди — пауза и начало трека, в конце волны — догрузка, у трека волны — `skip` в фидбек; событие `DislikedAndSkipped`. Иначе ничего из того, что играет, не меняется: ни «вперёд», ни фидбека волны, ни правки очереди; событие `Disliked`. Сравнивается id трека, а не строка: дизлайк другой строки с тем же треком тоже пропускает текущий (дизлайк — на трек, а не на строку; так же `Catalog::isCurrent` на десктопе), а трек, который перестал быть текущим, пока пользователь выбирал действие, получает только дизлайк. Кто зовёт: меню строки плейлиста — с треком строки, кнопки экрана плеера и библиотеки — с показанным треком (`ui/PlayerViewModel.dislikeCurrent`), уведомление — `dislikeCurrent()` с текущим.
- **Лайк.** `toggleLike(track)` читает `isLiked` в момент нажатия и шлёт обратное — так работают ♥ экрана плеера и уведомления (`likeCurrent()`). `setLiked(track, liked)` шлёт ровно `liked`: меню строки плейлиста передаёт `!liked` того состояния, которое показало, поэтому действие совпадает с подписью, даже если ответ на прошлый лайк ещё в пути. Оба отдают `LikeChanged(liked)`.
- **Обратная связь волны** (TRK-03…08). Каждая запись волны помнит `WaveContext` — сессию, станцию (первый сид) и `batchId` порции, из которой пришла, включая догруженные. Контекст хранится в записи, а не по id трека: один и тот же трек в двух местах очереди шлёт фидбек каждой своей записи. `radioStarted` уходит при старте волны до её первого `trackStarted`. `trackStarted` — когда трек начался; при закрытии — `trackFinished` (автопереход, повтор, конец очереди) или `skip` (всё остальное: «вперёд», «назад» на другой трек, выбор трека, рестарт первого трека «назад» без повтора (TR-01), «стоп», новая очередь, удаление текущего трека, ошибка трека, дизлайк, отключение движка) с секундами, которые звук реально играл. «Назад» после 3 с трек не закрывает: это перемотка (TR-02). События трека уходят в его сессию, даже если очередь уже сменилась на другую волну. Обычные очереди фидбек не шлют. Все события отправляются по одному через `Channel`, поэтому `skip` уходит раньше следующего `trackStarted`.
- **Отметка `/play-audio`** (TRK-01, TRK-02) уходит, когда трек **начался**: стал текущим и после этого заиграл — сразу, если при смене трека звук уже шёл (`isPlaying` в `onItemChanged`, как при бесшовном переходе), иначе при первом `onPlayingChanged(true)`. Трек, который только стоит в очереди или у которого не получилась ссылка, не начинался. Новый старт с новым `play-id` — рестарт первого трека «назад» без повтора (TR-01), повтор очереди из одного трека, «плей» после «стоп» (`stop()`) или после конца трека (в том числе после «назад» в конце конечной очереди). Пауза с продолжением и перемотка внутри трека — не новый старт, и «назад» после 3 с тоже: это перемотка в 0 (TR-02). Ожидание сети (ERR-01…03) — тоже не новый старт, а та же игра (ERR-09): ни `skip`, когда ожидание начинается, ни второго `trackStarted` и `/play-audio`, когда трек продолжается, а секунды прослушивания считаются дальше. Путь ожидания (`waitForNetwork`, потом `engine.prepare()`) не зовёт ни `PlayTracker.onItemChanged`, ни `onRestart`, ни `closeAsSkip`, поэтому игра остаётся открытой; у начатого трека `startPending` уже снят, и `onPlayingChanged(true)` после повтора ничего не начинает. Трек, у которого ссылка упала до старта, сохраняет `startPending` и начинается один раз, когда заиграет. Отправка best-effort, ошибки игнорируются.
  - ERR-09 держится, только пока повтор не даёт событий смены трека, а `support/FakeEngine` на `prepare()` событий не шлёт. Так ведёт себя Media3 1.4.1 (сверено по байткоду AAR через `javap`, на устройстве не проверялось): `prepare()` из `STATE_IDLE` после ошибки не сообщает ни `onMediaItemTransition`, ни разрыва позиции и не доходит до `STATE_ENDED`, поэтому `Media3Engine` не зовёт ни `onItemChanged`, ни `onEnded`. Сетевая ошибка приписывается играющему элементу, так что повтор не попадает на другой трек. В одном обновлении `onPlayerError` приходит раньше `onIsPlayingChanged(false)`: «ошибка, потом стоп» — путь ERR-01, «стоп (кончился буфер), потом ошибка» — путь ERR-03; тесты гоняют оба порядка (`support/NetworkLoss`).
  - Предел: во время ожидания плеер в `STATE_IDLE`, и сервис не на переднем плане (в Media3 1.4.1 `MediaNotificationManager.shouldRunInForeground` требует `playWhenReady` и `STATE_READY` или `STATE_BUFFERING`). Если Android остановит сервис во время долгого ожидания в фоне, `onDestroy` → `Media3Engine.detach` → `closeAsSkip` закроет игру как `skip`, а восстановленная очередь начнёт трек как новую игру (`attach` → `setTracks`, `NEW_QUEUE`); по спеке это «выход из приложения» TRK-06. Бывает ли так на устройстве, не проверено.

**Ошибки источников и лайков.** Упавший запрос даёт `QueueEvent.Failed(stage, error)`, где `error` — `yandex/ErrorKind.of(failed)`, а само исключение уходит в `logFailure(stage, failed)`; в приложении это `Log.w` из `AppGraph`. Текста исключения в событии нет. Ошибка воспроизведения приходит уже с видом: `onFailure(kind, error)` от `playback/PlaybackFailures`. Ошибка догрузки заменённой волны пишется в лог, но события не даёт (WAVE-07).

`events` — `MutableSharedFlow(extraBufferCapacity = 8)` с `tryEmit`: без подписчика события теряются, это нормально для тостов.

## Что играет следующим: `QueueWalk`

```kotlin
object QueueWalk {
    fun next(entries: List<QueueEntry>, order: List<Int>, current: Int, repeatHoldsHead: Boolean, leaving: Set<Int> = emptySet()): Int?   // null — дальше ничего; leaving — строки, которые сейчас уходят
    fun remaining(entries: List<QueueEntry>, order: List<Int>, current: Int, repeatHoldsHead: Boolean): Int   // вместе с текущим; Int.MAX_VALUE, пока повтор держит голову
}
```

Что играет следующим, решает обход очереди, как `Queue::next` десктопа. `order` — `engine.playOrder()`, `current` — `engine.currentIndex`, `repeatHoldsHead` — «повтор держит голову» (выше), `leaving` — строки, которые никогда не цель: выбранные для удаления вместе с текущим треком (HOST-36). `next`:
1. первый по индексу ждущий элемент (`isWaiting`), кроме текущей записи, — в том числе элемент закончившегося джема;
2. повтор держит голову — следующая запись `HEAD` после текущей в порядке воспроизведения, а если её нет — первая запись `HEAD` в этом порядке (заворот; у головы из одного трека — сам текущий трек);
3. иначе — следующая после текущей в порядке воспроизведения запись, которая не отыграна (`isSpent`: `OTHER` и элементы, которые уже не ждут);
4. иначе null.

`remaining` — сколько осталось вместе с текущим: `Int.MAX_VALUE`, пока повтор держит голову (CONT-10), иначе 1 + ждущие элементы + неотыгранные записи после текущей в порядке воспроизведения. По нему догружаются волна и волна по истории (`LOAD_MORE_WHEN_LEFT`).

**Порядок движка — быстрый путь обхода.** Естественный следующий трек движка (`naturalNext`) — следующий в `playOrder()`, а после последнего — первый, если в движке включён повтор. Обычно он и есть цель обхода, и ExoPlayer переходит сам, без шва. Где они расходятся, работает пауза в конце: `applyModes()` ставит `pauseAtEndOfCurrent = (цель обхода != естественный следующий)`. Движок встаёт на паузу в конце текущего трека и зовёт `onPausedAtEnd()`:
- цель равна естественному следующему (пока трек играл, всё вернулось) — `play()`;
- цели нет — игра закрывается как дослушанная, дальше то же, что в `onEnded` (ждать продолжения или остановиться в конце);
- иначе — игра закрывается как дослушанная (`playTracker.onEnded()`), `wrapTo(цель)` и `play()`.

«Вперёд» и пропуск сломанного трека (`ErrorAction.SkipToNext`) идут через `skipForward(цель)`: цель равна естественному следующему — `skipToNext()`, иначе `wrapTo(цель)`. «Есть ли следующий» для `next()`, `ErrorPolicy.decide(hasNext = …)` и остановки ERR-05 — тоже по обходу (`цель != null`), а не `engine.hasNext()`. `wrapTo(target)`: цель — сам текущий трек — `restart()`, иначе `seekTo(target)`. «Назад» (`previous()`) обход не спрашивает.

Расходятся они, когда отыгранные записи стоят в порядке движка впереди (круг повтора или переход назад по списку: обход их пропускает, а ExoPlayer сыграл бы), когда остались только отыгранные записи (цели нет) и когда ждущий элемент не стоит сразу за текущей. Последнего почти не бывает: контроллер собирает ждущие элементы за текущей строкой при каждом движении курсора («Режим джема»), так что первый ждущий элемент — и цель обхода, и естественный следующий, стык бесшовный. Пока в очереди только голова и продолжение, они расходятся в одном случае: повтор держит голову, а за ней уже есть продолжение (заворот головы, CONT-10). Движку тогда ставится `repeatEnabled = false`: повтор в ExoPlayer включён, только пока держит голову и в очереди нет ни одной записи `CONTINUATION` (TR-05).

## `PlayerEngine`

```kotlin
interface PlayerEngine {
    val itemCount: Int;  val currentIndex: Int;  val positionMs: Long;  val isEnded: Boolean
    var shuffleEnabled: Boolean;  var repeatEnabled: Boolean
    var pauseAtEndOfCurrent: Boolean   // встать на паузу в конце текущего трека и сообщить onPausedAtEnd()
    fun hasNext(): Boolean;  fun hasPrevious(): Boolean;  fun playOrder(): List<Int>
    fun setTracks(tracks: List<Track>, playWhenReady: Boolean, startIndex: Int = 0, startPositionMs: Long = 0, head: List<Int> = tracks.indices.toList(), lead: List<Int> = listOf(startIndex))
    fun shuffleHead(head: List<Int>, lead: List<Int>)   // новый проход головы: сначала lead, затем остальная голова
    fun appendTracks(tracks)              // после всего, головой не становятся (продолжение, CONT-09)
    fun insertTracks(index, tracks)       // сразу за треком index - 1 в порядке воспроизведения («играть следующим»)
    fun removeAt(index);  fun clear()
    fun seekTo(index);  fun seekToPosition(positionMs);  fun skipToNext();  fun skipToPrevious()
    fun prepare();  fun play();  fun pause();  fun stop()
}
```

Голова — индексы `head`, не обязательно префикс; контроллер передаёт индексы записей `HEAD` (у волны их нет, у обычной очереди — все, кроме продолжения). `lead` — с чего начинается проход: контроллер передаёт трек, с которого очередь играет (`startIndex` в `setTracks`, текущий трек в `shuffleHead`), и за ним ждущие элементы, если курсор в голове (`inHead`), иначе пусто. Так новый проход (включение shuffle, восстановление) всё равно играет ждущие элементы первыми. Контракт порядка: с shuffle `playOrder()` — сначала `lead`, затем остальная голова в случайном порядке, затем остальные индексы по возрастанию. `appendTracks` дописывает треки в конец: головой они не становятся, и продолжение идёт за всей головой. `insertTracks(index, …)` ставит треки сразу за треком `index - 1` в порядке воспроизведения: если тот в проходе головы, вставленные встают в проход прямо за ним, и проход идёт дальше за ними; если в остатке — они и так следуют за ним по возрастанию. Так вставленный трек — следующий и для ExoPlayer, который заранее грузит следующий. Вставка в пустой плейлист делает вставленные треки головой. Удаление сохраняет порядок остальных. Движок держит этот порядок уже тогда, когда сообщает о смене трека, вызванной правкой (`onItemChanged` из `setTracks`): контроллер читает `playOrder()` прямо в колбэке. Вставка в пустой плейлист сообщает новый текущий трек (`onItemChanged`, `NEW_QUEUE`), а `seekTo` на текущий индекс — только перемотку (`onSeeked()`), как ExoPlayer. `pauseAtEndOfCurrent`: дойдя до конца текущего трека, движок не переходит к следующему, а ставит `playWhenReady = false` и зовёт `onPausedAtEnd()`; контроллер держит флаг включённым, пока цель обхода не совпадает с естественным следующим движка («Что играет следующим»), и пересчитывает его в `applyModes()`. Адаптер Media3 и `HeadShuffleOrder` — в `playback/README.md`.

## Режим джема

Пока идёт джем, очередь плеера — текущий трек, **часть джема** (треки гостей в порядке сервера) и под ними **база** — собственная очередь хозяина: остаток её головы и продолжение (`spec/jam/host.md`, «The base»). Своей волны у джема нет. Сеть джема очередь не знает: `playback/JamHost` зовёт `startJam`, передаёт очередь сервера через `onJamQueue` и получает в ответ `JamPlaybackListener`: `onItemStarted(itemId)`, `onPlayback(playback)` и `onRemoveItems(itemIds)` (HOST-36). Что есть что, говорит сама запись (`QueueEntry`), отдельного списка слотов нет:

| Запись | Часть | Метки |
|---|---|---|
| Остаток головы базы (лайки, плейлист…) | `HEAD` | — |
| Продолжение базы: её своя волна («Моя волна», станция) или волна по истории (во время джема — волна джема) | `CONTINUATION` | `wave` всегда; `seedsVersion` — версия сидов `state`, если сессия начата по сидам джема, иначе null |
| Трек гостя, который ждёт (часть джема) | `ITEM` | `ItemMark(itemId, addedBy, waiting = true)` |
| Трек гостя, который стал текущим или сыграл | `ITEM` | `waiting = false` (отыгран) |
| Элемент закончившегося джема | `ITEM` | `itemId = null`; ждёт, пока не заиграет |
| Строка файла старого джема, кроме элементов и его волны | `OTHER` | — (отыгран) |

Инварианты:
- **Ждущие элементы стоят сразу за текущей строкой** и по индексу, и в порядке движка: сначала элементы джема (с `itemId`) в порядке сервера, за ними элементы прошлого джема. Их собирает `onItemChanged` при каждом движении курсора, в джеме и вне его (`gatherWaiting`, как `select` → `gatherPending` десктопа): выбор строки, «назад», «вперёд», конец трека, переход ExoPlayer, команда сессии. Элементы, которые стоят не там, удаляются (сначала из `state`) и вставляются `insertTracks` за текущей строкой, в прежнем порядке. Поэтому «следующая после текущей» обхода верна, а ExoPlayer заранее грузит именно элемент.
- Сначала `state`, потом движок — при каждой правке, как везде.

- **Старт** (HOST-14). `startJam(listener, waveFeedback)` очередь не трогает: записи, название, флаг «продолжать волной», shuffle, повтор, история стартов, сессия базы и её остановка остаются. Поколение не растёт, так что ответ догрузки, который в пути, принадлежит базе: он дописывается, а в конце очереди играет (WAVE-08). Билет источников не берётся: выбор источника, который ещё в пути, придёт новой базой (HOST-21). Открытый контекст фидбека текущего трека сбрасывается, если трек в джеме не учит ротор (всё, кроме трека волны джема при `waveFeedback`): трек, который играл при старте, закрывается без фидбека (HOST-15: «начинается или закрывается»). Затем `applyModes()`, отчёт каждые 10 с, `onPlayback` (текущий трек как `BASE` или `IDLE`) и сохранение. Пустая очередь — пустая база, и, когда кончится часть джема, решает её флаг; у ещё не заполненной очереди нового контроллера он из настройки.
- **Часть джема** (HOST-01…04, HOST-12). `onJamQueue(entries, seeds, seedsVersion)`:
  1. сиды и версия запоминаются (`SeedHint`); сиды с другой версией снимают остановку волны (HOST-11, CONT-07);
  2. «нечего играть» (`nothingToPlay`) берётся до правки: нет движка или строк, конец (`isEnded`), остановка в конце (`stoppedAtEnd`) или ожидание продолжения без цели обхода (HOST-13, `nothingToPlay` десктопа);
  3. `JamTail.edit`: часть джема — строки за текущей, пока это ждущие элементы с `itemId`. Общий префикс остаётся на месте (буфер следующего трека не трогается), остальное удаляется `removeAt` и вставляется `insertTracks` на `текущая + 1 + префикс`, то есть впереди остатка базы и элементов прошлого джема (HOST-12; десктоп `72195c2`). Текущий элемент в хвост не попадает, даже если `state` его ещё перечисляет;
  4. `dropStaleTail()` (ниже);
  5. если было «нечего играть»: правка сделала элемент текущим в пустом движке (вставка в пустой плейлист сообщает `NEW_QUEUE`, как ExoPlayer) — `prepare()` и `play()`: ExoPlayer после `clear()` и новый — в `STATE_IDLE`; иначе — перемотка к первому ждущему элементу, `prepare()`, `play()`, а ожидание продолжения снимается, чтобы ответ волны в пути не увёл с элемента (HOST-08). Иначе, если плеер не в конце и не остановлен, — проверка догрузки: `state` догружает, только пока трек играет или на паузе (WAVE-09);
  6. `applyModes()`, сохранение и `onPlayback`, если следующий трек обхода сменился.

  Без движка правится только `state`; если очередь была пуста, ставится точка возврата `(0, 0, играть)`, и `attach` кладёт всю очередь одним `setTracks`, первый элемент играет сразу. `JamPlaybackListener` элементы не хранит: `continueStored` может подключиться раньше сервиса.
- **Переходы** (HOST-05…08, HOST-10). Элемент перестаёт ждать, когда становится текущим (`onItemChanged`, в джеме и вне его); `onItemStarted(itemId)` уходит только за элемент джема, который ждал, элемент прошлого джема просто перестаёт ждать. `onPlayback`: `IDLE`, когда нечего играть; `ITEM`, когда текущая запись — элемент с `itemId`; `BASE` для любого другого трека (трек базы, элемент прошлого джема): `JamHost` шлёт его как `playing{source: wave, track}`. `nextTrack` — цель обхода (LISTEN-03). `onPlayback` уходит также при паузе, продолжении, перемотке и каждые 10 с игры (`PLAYING_REPORT_MS`) (HOST-06); перемотку сообщает движок через `onSeeked()`: ползунок экрана и уведомления, «назад», перемотка в 0 у «стоп»; на паузе тоже, с `paused = true`. «Назад» в джеме — всегда перемотка текущего трека в 0, при любой позиции (HOST-07): ни второго `started`, ни `skip` и нового `trackStarted` в фидбеке волны джема (HOST-16). «Вперёд» и конец трека — обычные: сначала элементы, потом база по своим правилам (HOST-10); в конце продолжение ждёт ответа (WAVE-08/09, CONT-03/07) или очередь останавливается (TR-04) и сообщает `IDLE` (HOST-13).
- **Волна джема** (HOST-11) — волна по истории базы, пока идёт джем. «Моя волна» и станция как база — своя волна (WAVE-05…09), а не волна джема. Проверка догрузки та же, что вне джема (CONT-04), плюс сиды джема:
  - сиды новой сессии — сиды последнего `state`, если они есть (с его версией), иначе `history.seeds()` (без версии), иначе устаревшая станция (#79);
  - сессия продолжается (`moreWave`), если `state` ещё не было, а сессия начата не по сидам джема; если в `state` нет сидов; или если версия сессии (`waveSeedsVersion`) равна версии `state`. Иначе следующий запрос — `startWave` с новыми сидами вместо догрузки, и он считается первым запросом волны по истории: неудача — `Failed(Stage.WAVE)` и остановка, пустой ответ — остановка без статуса (CONT-07). Снимают её, как в #79, «вперёд» в конце, включение флага, новая очередь и новая версия сидов, так что на каждой смене трека запрос не повторяется;
  - **устаревший ответ**: версия запроса волны по истории (`outdated(version)`, `Queue::isStale` десктопа: без `state` — сессия на сидах джема, иначе — сиды в `state` есть, а версия не та) проверяется, когда ответ пришёл. Такой ответ отбрасывается вместе со своей ошибкой, сессия не принимается, запрос идёт снова; если запроса нет, а очередь ждала, ожидание кончается остановкой в конце;
  - новая сессия запоминает id, станцию (первый сид) и версию; её треки дописываются как `CONTINUATION` с контекстом порции и `seedsVersion`;
  - **`dropStaleTail()`** (`dropStaleWave` десктопа) — после каждого `state` и каждой смены трека, если в `state` есть сиды, ни один элемент не ждёт и текущая запись — не трек волны джема: из базы без своей волны удаляются (сначала из `state`) записи `CONTINUATION` после текущей, чья `seedsVersion` не та (null тоже). Голова и своя волна не трогаются никогда;
  - `continuationFollows()` в базе без своей волны считает и сиды джема: пустая база (пустая очередь при старте) с сидами в `state` ждёт волну джема, а не останавливается.
- **Ничего больше** (HOST-13) — TR-04 плюс `IDLE`: флаг выключен, сидов нет ни в `state`, ни в истории (CONT-06), или первый запрос остановился (CONT-07). Элемент, который придёт потом, играет сразу (HOST-08). Своего правила у джема нет.
- **Ошибки** (HOST-09) — `ErrorPolicy`, как вне джема: сломанный последний трек ждёт продолжения, если оно следует, и продолжает с его первого трека.
- **Без обучения** (HOST-15, HOST-16). `/play-audio` — только без джема. Фидбек ротора открывается при старте трека, только если джема нет или это трек волны джема (`CONTINUATION` базы без своей волны) при `waveFeedback`. Контексты хранятся в записях всегда, так что после конца джема треки базы снова шлют фидбек (HOST-33). `radioStarted` сессии, начатой во время джема: волна джема при `waveFeedback` — сразу; своя волна (новая сессия восстановленной) и волна джема без `waveFeedback` — откладывается (`radioStartedPending`) и уходит в `endJam`, если сессия всё ещё очереди и начата не по сидам джема, то есть раньше фидбека следующего трека (`begin(true)` десктопа). История стартов пишет всё, кроме `CONTINUATION` (CONT-05): элементы джема — сиды, треки волны джема — нет (SEED-09).
- **Выбор источника** (HOST-21, D5). `loadSource`, `playWave`, `search` и `setQueue` работают, как вне джема: те же билеты и события (`SourceLoading`, `SourceLoaded`, `SourceEmpty`, `Failed`, `WaveStarted`), так что пустой или упавший выбор оставляет базу как есть. Поиск из библиотеки во время джема — тоже выбор (D5); добавить трек в джем — это экран джема (HOST-20). Вместо замены очереди `replaceQueue` зовёт `replaceBase` (`Queue::replaceBase` десктопа, `8cfe9f3`):
  - **остаются** текущая запись (элемент остаётся элементом, всё остальное становится `OTHER`) и ждущие элементы джема (с `itemId`);
  - **уходят** все остальные строки: сыгранные, старая база вместе с продолжением, элементы прошлого джема. По убыванию, сначала из `state`. Текущая строка не удаляется, поэтому ничего не останавливается и ExoPlayer никуда не переходит;
  - **дописываются** голова нового источника или первая порция его волны (`appendTracks`, только доступные треки);
  - **сбрасываются** название, `isWave`, `activeSourceId`, флаг «продолжать волной» (из настройки, CONT-01), выделение, история стартов, остановка (`stalled`), запрос в пути и ожидание продолжения. Поколение растёт, так что ответ старой базы, который ещё в пути, отбрасывается (WAVE-07). Сессия — от нового источника; `radioStarted` своей волны откладывается до конца джема (HOST-15, `radioStartedPending`). `inHead` — есть ли у новой базы голова: база начинается до первого трека головы. С действующим shuffle — новый проход `shuffleHead(голова, lead = текущий + ждущие элементы)`. Затем `applyModes()`, сохранение и `onPlayback`;
  - **ничего не начинается**: текущий трек доигрывает, потом элементы, потом новая база. Очередь, остановленная в конце, стоит до «вперёд» или «плей»: `stoppedAtEnd` не сбрасывается, а ожидание продолжения, пока трек не играл, становится остановкой. Пустой движок получает строки, но не `prepare()`, и тоже ждёт «плей»;
  - без движка меняется только `state`, а точка возврата переезжает на оставшуюся текущую строку с её позицией и `playWhenReady` (у пустой очереди — `(0, 0, не играть)`).
- **Правка** (HOST-36, D9). `removeIndices(indices)`:
  - ждущие элементы джема (`isJamItem`: ждут и с `itemId`, удержанный элемент тоже) уходят в `JamPlaybackListener.onRemoveItems(itemIds)` и покидают плейлист только со следующим `state`, как если бы их убрал гость. `JamHost` шлёт `remove{itemId}`, а без связи отдаёт `JamHostEvent.NotConnected` (HOST-25). REM при этом доступен: строки базы убираются и без связи;
  - любая другая выбранная строка (трек базы, сыгранная строка, элемент прошлого джема, текущий трек) удаляется сразу, как вне джема, и база играет дальше по своим правилам;
  - выделение снимается целиком.
- **«Очистить»** в джеме (HOST-36): `newSourceRequest()`, чтобы выбор в пути не заполнил очередь, затем `replaceBase(пусто, title = "", isWave = false)`: текущий трек и часть джема остаются, база пуста, с флагом новой очереди, и, когда кончится часть джема, решает он (HOST-11, HOST-13).
- **Удаление текущего трека** (`removeCurrent`, в джеме и вне его):
  1. сначала берётся цель обхода: `QueueWalk.next` с `leaving` = все выбранные строки, и повтор держит голову, только если среди остающихся строк есть `HEAD`;
  2. в джеме — `pause()`: удаление текущего трека останавливает воспроизведение (HOST-36), и ExoPlayer не должен играть дальше. Затем игра закрывается как `skip`;
  3. удаляются остальные выбранные строки по убыванию, текущая — последней. ExoPlayer сам встаёт на следующую строку старого порядка воспроизведения (`resolveSubsequentPeriod`, с повтором по кругу), без неё — на первую строку нового порядка, а если удалённая строка была последней по индексу, уходит в `STATE_ENDED` (`playback/README.md`, `Media3Engine`). Пока идёт удаление (`movingCursor`), `onItemChanged` не отмечает элемент начавшимся, не снимает удержание, и `PlayTracker` не начинает игру;
  4. цель найдена (по ссылке на запись, `===`: сбор ждущих элементов мог сдвинуть строки) — если движок встал не на неё или в конце, `seekTo(цель)`, и `stoppedAtEnd` снимается. Цели нет — курсор на последнюю строку порядка воспроизведения и `stopAtEnd()` (TR-04, в джеме — `IDLE`): «вперёд» оттуда снова останавливает, а не играет строку, на которую встал ExoPlayer;
  5. в джеме новая текущая запись, если это ждущий элемент, **удерживается** (ниже), а трек базы стоит на паузе в 0 и сообщается как `BASE` на паузе. Вне джема (D8) воспроизведение идёт дальше: элемент прошлого джема перестаёт ждать, а игра (`trackStarted`, `/play-audio`) начинается один раз — у цели, а не у строки, на которую ExoPlayer встал на миг.
- **Удержанный элемент** (`holding`, D11, десктоп `72195c2`) — текущий элемент ExoPlayer на паузе, который всё ещё ждёт. Он не шлёт `started`, `onPlayback` сообщает `IDLE`, `state` оставляет его на месте и в часть джема не возвращает (HOST-04), `jamSkip` и дизлайк его не пропускают, догрузка на `state` не идёт (десктоп в `Stopped` тоже не догружает), и пришедший элемент сам не начинает играть: HOST-08 — только когда играть нечего, а удержание — это «стоит». Отпускают его «плей» (`onPlayingChanged(true)`) и «вперёд» (без перемотки: `started`, затем `play()`); после этого он обычный текущий элемент. Выбор другой строки снимает удержание, а элемент ждёт дальше и собирается за новой строкой. Если `state` его больше не перечисляет, он удаляется тем же `removeCurrent`, и удерживается следующий ждущий элемент (или трек базы стоит на паузе в 0). `attach` нового движка ставит плейлист под тем же `movingCursor`, так что элемент остаётся удержанным. `endJam` удержание не снимает: элемент становится элементом прошлого джема, ждёт и начинается по «плей» без `started`.
- **Переходы по списку** (HOST-12, D10). Выбор строки в плейлисте (`ui/PlayerViewModel.playIndex` → `MediaController.seekTo(i, 0)`, затем `play()`), очередь Android Auto и любой контроллер сессии идут прямо в ExoPlayer: `QueueForwardingPlayer` `seekTo(index, …)` не перехватывает (примечание 5 второго ревью плана). Ждущие элементы переезжают за новую строку в `onItemChanged` (сбор выше), в джеме и вне его. Удержанный элемент из движка при этом не удаляется: перемотка идёт первой, сбор — после.
- **Лайк и дизлайк** работают (HOST-17), в том числе из плейлиста: дизлайк текущего элемента — «вперёд», другого — только дизлайк (TR-10).
- **Пропуск гостя** (HOST-18, HOST-19). `jamSkip(itemId)` = «вперёд», только если этот элемент — текущий.
- **Конец** (HOST-32, HOST-33). `endJam()` работает и без джема (восстановленная очередь, «Нет» на HOST-23, HOST-24): отчёт останавливается; каждый `ITEM` теряет `itemId` — ждущие элементы ждут дальше и играют первыми без `started`, отыгранные остаются отыгранными. В голову они не входят, проход не перестраивается, повтор их не повторяет (решение 1 владельца в Kickoman/QiYaa#28). Записи `CONTINUATION` после текущей с `seedsVersion` удаляются: сиды джема кончились. Сессия, начатая по сидам джема, забывается: следующий запрос — новая сессия по истории очереди, а ответ старой, который ещё в пути, устарел и отбрасывается. Отложенный `radioStarted` уходит (выше). Текущий трек доигрывает; `/play-audio` и фидбек — для треков, которые начнутся теперь. Затем `applyModes()` и сохранение.

## `ErrorPolicy`

```kotlin
sealed interface ErrorAction { WaitForNetwork; Hold; SkipToNext; WaitForMore; Stop }
object ErrorPolicy {
    const val MAX_CONSECUTIVE_TRACK_FAILURES = 3
    fun decide(kind: FailureKind, consecutiveTrackFailures: Int, hasNext: Boolean, endless: Boolean = false): ErrorAction   // endless: за последним треком идёт продолжение
    suspend fun awaitRetry(connectivity: Flow<Boolean>, attempt: Int)
    fun retryDelayMs(attempt: Int): Long         // 2, 4, 8 … 60 с, те же пределы, что у yandex/Session
}
```

| Вид | Действие контроллера |
|---|---|
| `SESSION` | `Hold`: остаться на месте, `Failed(PLAYBACK)`; `yandex/Session` уведёт на вход |
| `NETWORK` | `WaitForNetwork`: пауза на текущем треке, один раз `WaitingForNetwork`; когда `awaitRetry` вернулся — `engine.prepare()` |
| `TRACK` | 3-я неудача подряд — `Stop` и `StoppedAfterFailures(3)` (ERR-05, и в волне тоже); иначе есть следующий трек — `SkipToNext` с `Failed(PLAYBACK)` (ERR-04); нет следующего, но продолжение следует (`endless`: волна, джем, волна по истории, которая может спросить) — `WaitForMore`: `Failed(PLAYBACK)`, догрузка и продолжение с первого нового трека (ERR-07); иначе — `Stop` |

`awaitRetry`: если сети нет, ждёт её и возвращается сразу, как только она появилась; если сеть есть, а загрузка всё равно падает, ждёт `retryDelayMs(attempt)`. Счётчики и ожидание сбрасываются, когда трек реально заиграл (`onPlayingChanged(true)`), и при `setQueue`/`clear`.

## Формат сохранённой очереди

`QueueSnapshotCodec.encode` — компактный JSON (`kotlinx.serialization`), `version` = 1:

```json
{"version":1,"title":"Моя волна","sourceId":"user:onyourwave","isWave":true,"waveSessionId":"S1","waveStationId":"user:onyourwave","index":1,"positionMs":42000,"shuffle":false,"repeat":true,
 "tracks":[{"id":"1","title":"Кукушка","artists":["Кино"],"albumId":"4053","durationMs":398000,"available":true,"coverUrl":"https://…","batchId":"B1"}]}
```

В джеме добавляются `"jam":true` (`QueueSnapshot.jam`) и у треков `jamItemId`, `jamAddedBy` (запись `ITEM`, `QueueSnapshot.items`) или `"jamWave":true` (запись `CONTINUATION`); без них трек файла джема — `OTHER`. Вне джема этих полей нет. Признак очереди джема для файла — приватный `jamQueue`: ставят `startJam` и восстановление файла с `"jam":true`, снимают `endJam`, новая очередь и `clear()` вне джема (новая база в джеме его не трогает). Пока формат не различает части `item` и `other` (шаг HOST-23 QiYaa-android#80), голова базы, сохранённая во время джема, читается как `OTHER`, а `seedsVersion` не сохраняется. Части `ITEM` и `OTHER` ключом `part` не пишутся, ждёт ли элемент — тоже: при чтении элемент ждёт, если стоит после сохранённого текущего (`index`), иначе отыгран. `QueueSnapshot.items` пуст, если элементов нет.

У трека может быть `"part":"head"` или `"part":"continuation"` (`EntryPart.key`; другие ключи читаются как незнакомые): часть записи, только если она отличается от того, что следует из `isWave` (`EntryPart.defaultFor`: волна — `continuation`, иначе `head`). Так пишутся треки волны по истории и треки волны джема (`continuation` в очереди без `isWave`). `save()` сводит части, которые все совпадают с этим значением, к пустому `QueueSnapshot.parts`. `decode`: ни у одного трека нет `part` — `parts` пуст, то есть всё по `isWave`, как в файлах до появления частей; незнакомое значение — тоже по `isWave`. `version` остаётся 1: поле необязательное, и файл без него читается как раньше (`QueueSnapshotCodecTest` держит такие файлы буквально).

Флаг «продолжать волной» — `"continueWithVibe":true|false` на верхнем уровне (`QueueSnapshot.continueWithVibe: Boolean?`); контроллер пишет его всегда, а `null` (поля нет, файл до появления флага) при восстановлении значит «как в настройке». История стартов — `"history":["<id>", …]` (до 5 id, последний старт первым, `QueueSnapshot.history`); пустая не пишется, при чтении `StartHistory` отбрасывает пустые id и повторы и берёт не больше 5. Оба поля необязательные и при значениях по умолчанию не пишутся, поэтому файлы версии 1 пишутся и читаются как раньше.

`shuffle` и `repeat` — выбор пользователя (`WaveModeRule.wanted`), а не режим плеера в волне. `sourceId`, `coverUrl` могут отсутствовать; `batchId` пуст у записей без порции (голова), `waveSessionId` и `waveStationId` — пока у очереди нет сессии своей волны или волны по истории (у волны по истории станция — первый сид, `track:<id>`). `decode` зажимает `index` в границы треков, неизвестные поля пропускает, при другой `version` возвращает null.

## Тесты

`app/src/test/.../queue/`: `QueueSourcesTest`, `QueueWaveTest`, `QueueContinuationTest`, `QueueErrorsTest`, `QueueEditingTest`, `QueueJamTest` гоняют контроллер с `support/FakeEngine` (плейлист, курсор, конец, проход головы по контракту `PlayerEngine`, синхронные колбэки, в том числе `onSeeked()` внутри `seekToPosition` и `seekTo` на текущий индекс — как ExoPlayer) и `support/FakeMusicSource` (ответы — лямбды, в том числе отложенные `CompletableDeferred`). Имена тестов начинаются с ID сценария. `support/QueueHarness` по умолчанию собирает контроллер с выключенной настройкой «продолжать волной» (`continueWithVibe = false`), чтобы короткие очереди старых тестов (TR-04, TRK, ERR) кончались, как раньше; тесты продолжения включают её явно.

**Traps:**
- Отыгранные записи (`OTHER`, элементы, которые уже не ждут) остаются в плейлисте ExoPlayer, и сам он их сыграл бы. Их пропускает только обход: пауза в конце и переход к цели. Этот стык не бесшовный, и ExoPlayer заранее грузит строку, которую не сыграет. «Плей» сразу после такой паузы, когда цели нет (остались только отыгранные), играет следующую отыгранную строку.
- Элемент перестаёт ждать в `onItemChanged` раньше всей остальной работы (`inHead`, сбор ждущих элементов, `dropStaleTail`, `applyModes`, `save`, `started`): обход не должен считать текущий элемент ждущим, а `started` уходит только за тот, что ждал. Элемент, на который вернулись выбором строки, второго `started` не шлёт.
- Курсор, который двигает сам контроллер (удаление текущего трека, `attach` при удержании), двигается под `movingCursor`: `onItemChanged` тогда не отмечает элемент начавшимся, не снимает удержание и не начинает игру в `PlayTracker`. Новый путь, который в джеме удаляет текущую строку или ставит плейлист заново, должен ставить этот флаг, иначе строка, на которую ExoPlayer встаёт на миг, получит `started` или `/play-audio`.
- Текущая строка удаляется последней, а цель ищется по ссылке на запись: колбэк смены трека из самого удаления собирает ждущие элементы и может сдвинуть строки, так что индексы, посчитанные заранее, к этому моменту неверны. Поэтому `markStarted` во время удаления и не зовётся: он заменил бы запись копией, и поиск по ссылке её бы не нашёл.
- Удержание переживает `endJam` и `detach`; его снимают только выбор строки, «плей», «вперёд», новая очередь и `clear()` вне джема. Сохранённая очередь удержание не хранит (шаг HOST-23 QiYaa-android#80).
- ExoPlayer готовит текущий элемент и на паузе, поэтому ошибка трека удержанного элемента идёт по `ErrorPolicy`, как ошибка любого трека на паузе: `SkipToNext` переходит к следующему и включает игру. На устройстве не проверялось.
- Сбор ждущих элементов и `dropStaleTail` правят плейлист изнутри `onItemChanged`, то есть из колбэка `onMediaItemTransition` ExoPlayer. Они удаляют и вставляют только другие строки, не текущую, поэтому нового перехода это не даёт (так же правил плейлист старый `ensureJamWave`). Если сбор начнёт трогать текущую строку, ExoPlayer сам выберет следующую.
- Обход ищет первый ждущий элемент где угодно, поэтому сломанный инвариант «элементы сразу за текущей» стоит паузы в конце и шва, а не потерянного элемента. Без сбора выбор строки ниже элемента прошлого джема вернул бы к элементу, а за ним — к строкам между ними второй раз.
- Устаревание ответа волны по истории решает версия сидов запроса (`outdated(version)`), а не id сессии или трека (решение 4 владельца в Kickoman/QiYaa#28): версия берётся при запросе, проверка — когда ответ пришёл, до остальной обработки.
- `stopWaiting()` в `onPlayingChanged(true)` — только пока счётчик неудач не ноль (ERR-07): «вперёд» на играющем последнем треке ждёт ответа, пока трек играет, и новое `onIsPlayingChanged(true)` (например, после буферизации) это ожидание снимать не должно.
- Повтор держит голову, только пока в очереди есть записи `HEAD` (пустая очередь — исключение, для режима движка): иначе в пустой базе с одними элементами `remaining` был бы `Int.MAX_VALUE` и волна джема не спросилась бы никогда, а обходу некуда было бы заворачивать.
- Начальное `QueueState` нового контроллера берёт флаг из настройки, как `clear()`: пустая очередь в джеме — пустая база, и её флаг решает (HOST-14). `QueueHarness` по умолчанию выключает настройку, поэтому `QueueState()` в тестах по-прежнему равно свежему контроллеру.
- История стартов пишет всё, кроме `CONTINUATION`: элементы джема — треки этой очереди (CONT-05), как `noteStarted` десктопа. Если вернуть условие «только `HEAD`», элементы и `OTHER` перестанут быть сидами.
- `QueueEntry` требует метку ровно у `ITEM` (`require` в `init`): часть из файла, которая говорит `ITEM` без метки, читается как часть по умолчанию.
- Секунды прослушивания считаются по часам `clock` только между `onPlayingChanged(true)` и `(false)` открытого трека; перемотка времени не добавляет. В тестах часы — виртуальное время `runTest`.
- Повтор после ожидания сети должен остаться голым `engine.prepare()` (ERR-09). Если повтор заново поставит плейлист (`setMediaItems`, в терминах `PlayerEngine` — `setTracks`) или заменит элемент на другой URI, Media3 сообщит смену трека, контроллер получит `onItemChanged`, и ожидание станет новой игрой: `skip`, новый `trackStarted` и `/play-audio`. `seekTo` на тот же индекс в Media3 1.4.1 даёт только разрыв позиции (SEEK, то есть `onSeeked`: отчёт джема и сохранение, игра та же), и `support/FakeEngine.seekTo` на тот же индекс ведёт себя так же; `replaceMediaItem` с тем же `qiyaa://track/<id>` обновляет элемент на месте.
- «Назад» после 3 с и «назад» в джеме должны остаться `seekToPosition` (`Player.seekTo(ms)`). `skipToPrevious` (`seekToPreviousMediaItem`) на тот же элемент идёт в Media3 через `repeatCurrentMediaItem` и сообщает смену трека с причиной `SEEK`, а это `skip` и новая игра. Так сейчас работает «назад» в пределах 3 с в очереди из одного трека с повтором, и это совпадает с `playIndex(0)` десктопа.
- `title` — данные из UI или сервера (имя плейлиста, `getString(R.string.library_my_wave)`), не константа этого пакета.
- `state.tracks` и плейлист плеера пишет только контроллер, поэтому сверять их не нужно; если в плеер начнёт писать кто-то ещё (например, команда удаления из уведомления), это должно идти через контроллер.
- `removeIndices` удаляет по убыванию индексов, иначе сдвиг сломает выборку, и по одному: `state` раньше движка. Если сначала удалить из движка, колбэк смены текущего трека прочитает старый `state`, и старт припишется не той записи (чужой контекст фидбека или никакого).
- `QueueState.tracks` — производное от `entries`. Новую очередь или правку задают записями, а не треками: трек без записи теряет часть и контекст.
- Порядок shuffle — свой (`HeadShuffle`, в ExoPlayer — `playback/HeadShuffleOrder`), а не `DefaultShuffleOrder`: тот вставляет дописанные треки в случайные места перемешанного порядка, а новая очередь начиналась с индекса 0, который стоит в случайном месте прохода, так что перемешанная очередь кончалась, не сыграв часть треков. В волне shuffle по-прежнему не действует (WAVE-10): это правило спеки, а не обход порядка. Выбор shuffle и повтора хранится в `WaveModeRule` и в сохранённой очереди.
- Новый проход нужен только тогда, когда shuffle начинает действовать: `setShuffle(true)` при уже включённом shuffle проход не трогает, иначе каждое нажатие перемешивало бы оставшееся.
- Повтор головы с продолжением в очереди нельзя выразить одним порядком ExoPlayer: `REPEAT_MODE_ALL` заворачивает весь порядок и доходит до продолжения, а зацикленный `ShuffleOrder` сломал бы `Timeline.toBundle` (сессия строит список перемешанных индексов обходом порядка). Поэтому пауза в конце и заворот контроллером. Если вернуть «повтор = выбор пользователя», треки волны пойдут после головы при включённом повторе.
- Курсор вернулся из продолжения в голову (пользователь выбрал трек головы) и голова доиграла: порядок ExoPlayer линейный, поэтому дальше снова идёт первый дописанный трек продолжения, а не тот, на котором продолжение остановилось. Десктоп продолжает с места остановки (`continuationMark`); спека этот случай не описывает.
- Режим ExoPlayer — не выбор пользователя: в запертой очереди контроллер сам ставит «выключено», а повтор выключен и там, где его держит контроллер (заворот головы) или где он не действует (курсор в продолжении). Если снова начать читать выбор из событий плеера, это «выключено» станет неотличимо от выбора пользователя. Команды сессии перехватывает `playback/QueueForwardingPlayer`, `support/FakeEngine` на смену режима контроллер не зовёт.
- `restore` идёт в блоке `init` после объявления всех полей: инициализатор поля, объявленного ниже `init`, затёр бы восстановленное значение. Это касается и `history`, `stalled`, `asking`, `stoppedAtEnd`, `inHead`, `waveSeedsVersion`, `radioStartedPending`, `jam`.
- `QueueState.loadingMore` — не защита от второго запроса, а строка в плейлисте: для волны по истории она горит только в ожидании, а запрос в пути может быть и без него. Защита — приватный `asking`; если проверять `loadingMore`, тихий запрос CONT-04 пустит второй.
- Ожидание снимают `stop()`, `onItemChanged` с треком, `onSeeked` и «плей» после ERR-07, поэтому тот, кто начинает ждать, ставит флаг после своих перемоток и остановок, а ответ читает его до своих: `next()` в конце зовёт `stopAtEnd()` → `stop()` только тогда, когда запроса нет, а ответ берёт `continueAtEnd` до `appendEntries` (вставка в пустой плейлист сообщает о смене трека) и до `seekTo`. Если позвать `stop()` после `waitForMore` или читать флаг после вставки, «вперёд» в конце перестанет ждать, а ответ — играть первый новый трек (WAVE-08).
- Ответ догрузки играет первый новый трек только при `continueAtEnd`. Если вернуть прежнее «плеер в конце — играть» (`isEnded`), включение флага в остановленной в конце очереди само начнёт воспроизведение, а CONT-03 требует «вперёд».
- История стартов пишется в `onStarted` по записи из `state`, а не по id: волна может вернуть трек, который есть и в голове, и запись волны сидом стать не должна.
- Файл без треков, с другой версией или битый читается как «сохранённой очереди нет»; пустая очередь после `clear` сохраняется и тоже ничего не восстанавливает.
- `QueueController` не должен импортировать `yandex/Library` напрямую: только `MusicSource`, иначе тесты потеряют фейк, а `yandex` — место внизу графа.
