# `playback/` — воспроизведение

ExoPlayer внутри `MediaSessionService`, адаптер между ExoPlayer и очередью, хозяин джема, классификация ошибок воспроизведения, ленивое разрешение ссылок и два аудиопроцессора, которые вставляют `audio/` в звуковой конвейер. Пакет **не** решает, что играть дальше (это `queue/`), **не** ходит в сеть сам (это `yandex/`), **не** считает DSP (это `audio/`) и **не** показывает текст.

```bash
grep -rln 'qiyaa\.ui\.' app/src/main/java/io/github/kickoman/qiyaa/playback/   # ничего не печатает
```

## Конвейер

`QueueController.setQueue` → `Media3Engine.setTracks` → `MediaItems.toMediaItem` → ExoPlayer → `ExpiredLinkDataSource` → `ResolvingDataSource(TrackResolver → TrackUrlCache)` → `OkHttpDataSource` → декодер → `DefaultAudioSink[EqualizerProcessor, VisualizerTapProcessor]` → `AudioTrack`. Ссылка на mp3 подписывается в момент открытия потока, поэтому очередь из 300 треков не делает 300 запросов заранее.

## `PlaybackService`

Собирает `ExoPlayer` с `DefaultRenderersFactory`, у которого `buildAudioSink` подменён на `DefaultAudioSink` с двумя процессорами и `enableFloatOutput = false` (процессоры принимают только `ENCODING_PCM_16BIT`); третий аргумент `buildAudioSink` уходит в `setEnableAudioOutputPlaybackParameters` как есть (до Media3 1.9 — `setEnableAudioTrackPlaybackParams`). Атрибуты `USAGE_MEDIA`/`AUDIO_CONTENT_TYPE_MUSIC` с `handleAudioFocus = true`, `handleAudioBecomingNoisy`, `WAKE_MODE_NETWORK`, User-Agent `QiYaa/Android`. Громкость сервис берёт из `Settings.volume` и следит за ней сам (`serviceScope`, `AudioBus.volumeGain`), поэтому она применяется и без открытого экрана.volumeGain`. Тап по уведомлению открывает launcher-intent пакета (сервис не знает про `ui/`). Иконка уведомления — `R.drawable.ic_notification`.

Сервис объявлен `exported="true"` с `tools:ignore="ExportedService"`: так требует Media3, чтобы система и гарнитуры могли привязаться к `MediaSessionService`. `onCreate` создаёт `Media3Engine(player, appGraph.queue, onAudioFailure = { appGraph.telemetry?.audioFailed(it) })` (ошибки звука уходят в телеметрию, `error audio/…`; в сборке без неё `telemetry` — `null`), подключает его и отдаёт сессии `QueueForwardingPlayer(player, appGraph.queue)`; сессия получает `SessionCallback` (кнопки лайка и дизлайка, «играть» после выгрузки процесса); `onTaskRemoved` зовёт `pauseAllPlayersAndStopSelf()`, если ничего не играет (нет `playWhenReady` или очередь пуста); `onDestroy` отключает движок (контроллер запоминает, где остановились), освобождает плеер и сессию. Оба сообщают `appGraph.jamHost` (`onServiceStarted`/`onServiceStopped`), см. `JamHost`. После подключения движка `onCreate` следит за `appGraph.qualityInEffect`: каждое новое значение (`drop(1)`) — `QueueController.onFilesChanged(trackLinks::askedInOtherQuality)` на `serviceScope`, то есть на главном потоке, потоке ExoPlayer и контроллера (QUAL-05, «Traps (качество)» ниже). Подписка запускается `UNDISPATCHED`, как и подписка на громкость: `drop(1)` отбрасывает значение, которое действует сразу после `attach()`, ещё внутри `onCreate`, а не то, что будет к первому обороту главного цикла, так что смена качества в этот оборот (`attach()` уже мог запустить восстановленную очередь у самого конца трека) не теряется. Без сервиса плеера нет и подгружать нечего. `attachBaseContext` даёт сервису язык интерфейса (`AppLocale.wrap`), а смена языка во время работы перестраивает кнопки уведомления (см. `ui/README.md`, «Язык интерфейса»).

`SessionCallback.onConnect` строит ответ через `AcceptedResultBuilder(session, controller)`: конструктор без контроллера в Media3 1.11 устарел. Новый конструктор недоверенному контроллеру (не система, не само приложение, без `MEDIA_CONTENT_CONTROL` и без включённого слушателя уведомлений) по умолчанию даёт только команды чтения, поэтому `setAvailablePlayerCommands(DEFAULT_PLAYER_COMMANDS)` возвращает всем контроллерам полный набор команд плеера, как в 1.4.1, а `setAvailableSessionCommands` — команды сессии по умолчанию плюс лайк и дизлайк (ниже).

**Traps:**
- С Media3 1.6.0 сервис после паузы, «стоп», ошибки или конца очереди ещё 10 минут остаётся на переднем плане (`MediaSessionService.DEFAULT_FOREGROUND_SERVICE_TIMEOUT_MS = 600_000`; `MediaNotificationManager.shouldRunInForeground` держит его, пока не истёк таймаут после того, как плеер перестал быть `playWhenReady` в `STATE_READY`/`STATE_BUFFERING`). Всё это время `isPlaybackOngoing()` — `true`, и голый `stopSelf()` сервис не останавливает (так в javadoc `isPlaybackOngoing`); `pauseAllPlayersAndStopSelf()` сначала снимает таймаут. Поэтому `onTaskRemoved` зовёт его, а не `stopSelf()`.
- Уведомление плеера, который ушёл в `STATE_IDLE` после «стоп» или ошибки, с Media3 1.6.0 остаётся (`SHOW_NOTIFICATION_FOR_IDLE_PLAYER_AFTER_STOP_OR_ERROR` по умолчанию; в 1.4.1 оно пропадало сразу). Плеер с треками, который ни разу не готовился (`prepare`), уведомления не показывает, как и раньше.
- Media3 1.11 проверяет поток у методов сессии (`MediaSession.getPlayer` и других) и на чужом потоке бросает `IllegalStateException`. Сервис зовёт их только на главном: `onConnect`, `onTaskRemoved`, `onDestroy` и `serviceScope` (`MainScope`).

## Один хозяин плеера

У плеера один хозяин — `QueueController` из `AppGraph` (вариант «синглтон» из Kickoman/QiYaa-android#6; приложение однопроцессное, поэтому очередь не сериализуется в команды и `sessionExtras` сессии). Все пути к плееру сходятся в нём:

| Откуда | Путь |
|---|---|
| Кнопки приложения | `ui/PlayerViewModel` → `MediaController` → `MediaSession` → `QueueForwardingPlayer` → `QueueController.next()`/`previous()`; SHF и RPT — `QueueController.setShuffle()`/`setRepeat()` напрямую |
| Уведомление, экран блокировки, гарнитура, Bluetooth | `MediaSession` → `QueueForwardingPlayer` → `QueueController`: «вперёд», «назад», shuffle, повтор |
| Выбор источника, правка очереди, лайки | `ui/AppViewModel` → `QueueController` напрямую |
| Выбор строки (плейлист, очередь Android Auto, любой контроллер сессии) | `MediaController.seekTo(i, 0)` → `MediaSession` → ExoPlayer, мимо `QueueForwardingPlayer` → `onMediaItemTransition` → `QueueController.onItemChanged`, который собирает ждущие элементы за новой строкой (HOST-12, `queue/README.md`) |
| События ExoPlayer | `Media3Engine` (листенер) → `QueueController` |

Сервис может пересоздаваться при живом процессе (смахнули из недавних → `onTaskRemoved` → `pauseAllPlayersAndStopSelf`, потом приложение открыли снова). `onDestroy` отключает движок, и контроллер запоминает трек и позицию; новый `Media3Engine` получает ту же очередь на паузе в том же месте. Источник, выбранный, пока сервис ещё не поднялся, применяется, как только движок подключится. После выгрузки процесса очередь восстанавливает сам `QueueController` из `data/QueueFile` (см. `queue/README.md`), и новый сервис при `attach` получает её на паузе в том же месте.

## «Играть» после выгрузки процесса

Кнопка гарнитуры или карточка возобновления в системе доходят до приложения через `androidx.media3.session.MediaButtonReceiver` в манифесте (`exported`, `android.intent.action.MEDIA_BUTTON`). Он поднимает `PlaybackService`, `onCreate` подключает движок, и очередь уже стоит в плеере. Если плеер всё же пуст, Media3 вызывает `MediaSession.Callback.onPlaybackResumption(session, controller, isForPlayback)` (вариант без `isForPlayback` в Media3 1.11 устарел; у `MediaSession` `isForPlayback` всегда `true`, `false` бывает только у `MediaLibrarySession`, и ответ от него не зависит): `ResumptionCallback` отдаёт треки, индекс и позицию из `QueueController.resumePoint()`, а при пустой очереди — неудачный `Future`, и команда ничего не делает. Эти треки сессия ставит в ExoPlayer мимо `Media3Engine`; `HeadShuffleOrder`, поставленный при `attach`, делает из них случайный проход, и все они — голова.

## Лайк и дизлайк в уведомлении

```kotlin
object NotificationButtons {
    const val ACTION_LIKE = "io.github.kickoman.qiyaa.LIKE";  const val ACTION_DISLIKE = "io.github.kickoman.qiyaa.DISLIKE"
    fun withCustomCommands(commands: SessionCommands): SessionCommands
    fun layout(context: Context, liked: Boolean): List<CommandButton>   // [♥ залитое или пустое, 👎]
}
```

Две пользовательские команды сессии без аргументов (`Bundle.EMPTY`). `SessionCallback.onConnect` добавляет их к `DEFAULT_SESSION_COMMANDS` каждому контроллеру (уведомление, экран блокировки, `ui/PlayerViewModel`) и отдаёт текущую раскладку. `onCustomCommand` передаёт `ACTION_LIKE` в `QueueController.likeCurrent()`, `ACTION_DISLIKE` — в `dislikeCurrent()`; сам трек выбирает очередь, поэтому дизлайк ведёт себя как кнопка на экране плеера (TR-07, TRK-07: запрос, `skip` в фидбек волны, «вперёд»). Незнакомая команда — `ERROR_NOT_SUPPORTED`.

Состояние ♥: сервис держит `mediaId` текущего трека (листенер `onMediaItemTransition`) и объединяет его с `Library.likedIds`; при изменении вызывает `MediaSession.setCustomLayout`. Так ♥ меняется при смене трека, при лайке из шторки и при лайке с экрана плеера. Экран плеера читает те же `likedIds`, поэтому лайк из шторки виден там сразу после ответа сервера.

Значки — встроенные `CommandButton.ICON_HEART_FILLED`/`ICON_HEART_UNFILLED` и `ICON_THUMB_DOWN_UNFILLED`. Подписи (для TalkBack) — строки `notification_like`, `notification_unlike`, `notification_dislike` из `res/values*/strings.xml`: сервис — точка входа Android и берёт ресурсы, как и иконку уведомления; событий и текста для тостов пакет по-прежнему не производит.

Где стоят кнопки, решает система: в развёрнутом уведомлении — после «назад», «плей», «вперёд»; в медиапанели Android 13+ и на экране блокировки — в двух свободных слотах. Media3 1.11.1 переводит `setCustomLayout` в media button preferences (`CommandButton.getMediaButtonPreferencesFromCustomLayout`): пока «назад» и «вперёд» доступны, а `QueueForwardingPlayer` при непустой очереди добавляет их всегда, ♥ и 👎 получают слот `SLOT_OVERFLOW` и в компактный вид уведомления не попадают. `setCustomLayout` в 1.11.1 не устарел, только помечен «будет устаревшим» в пользу `setMediaButtonPreferences`.

**Traps:**
- `CommandButton.Builder(icon)` и значки `ICON_*` стабильны с Media3 1.6.0 (в 1.4.1 были `@UnstableApi`), поэтому `NotificationButtons` больше не помечен `@UnstableApi`. Устарели `CommandButton.Builder()` без значка и `setIconResId`: их не брать.
- Команда, которой нет в `setAvailableSessionCommands`, не доходит до `onCustomCommand`, а кнопка с ней не показывается.

## `QueueForwardingPlayer`

`ForwardingPlayer` над ExoPlayer: `seekToNext`/`seekToNextMediaItem` → `QueueController.next()`, `seekToPrevious`/`seekToPreviousMediaItem` → `previous()`, `setShuffleModeEnabled(on)` → `setShuffle(on)`, `setRepeatMode(mode)` → `setRepeat(mode != REPEAT_MODE_OFF)`. Всё остальное (play, pause, seek по позиции и по строке, громкость) уходит в ExoPlayer как есть. `seekTo(index, …)` и `seekToDefaultPosition(index)` не перехватываются: переход на строку и так приходит в контроллер через `onMediaItemTransition`, а ждущие элементы джема собирает `onItemChanged` (второе ревью плана QiYaa-android#80, примечание 5). Режимы ExoPlayer ставит только контроллер (`queue/README.md`).

**Отклонённый выбор публикуется заново.** Если после `setShuffle`/`setRepeat` режим ExoPlayer не равен запрошенному, ExoPlayer события не даёт, и контроллер сессии (уведомление, Bluetooth) остался бы со своим замаскированным значением. Так бывает, когда выбор отклонён (волна, станция), когда повтор выбран, но в ExoPlayer не включён (курсор в продолжении — CONT-11 — или голову с продолжением за ней заворачивает сам контроллер — CONT-10, `queue/README.md`), или когда запрошен `REPEAT_MODE_ONE`: повтор бывает только всей очереди (TR-06), и действует `REPEAT_MODE_ALL`. Тогда `QueueForwardingPlayer` сам зовёт `onShuffleModeEnabledChanged`/`onRepeatModeChanged` с действующим значением у всех слушателей сессии. `MediaSessionImpl.PlayerListener` в Media3 1.11.1 на каждый такой вызов обновляет `PlayerInfo` и рассылает его контроллерам, не сравнивая со старым значением (сверено по исходникам `onShuffleModeEnabledChanged`/`onRepeatModeChanged`, так же было в 1.4.1; на устройстве не проверялось); рассылка асинхронная и склеивается в одно сообщение за проход лупера. Старые контроллеры платформенной `MediaSessionCompat` получают режим, только если он изменился: `MediaSessionCompat.setRepeatMode`/`setShuffleMode` сравнивают со старым. Внешние контроллеры поэтому видят режим, который действует в ExoPlayer; экран приложения показывает выбор пользователя (`QueueController.modes`). При завороте головы контроллером это значит, что Bluetooth и уведомление показывают повтор выключенным, хотя голова повторяется; нажатие «повтор» там снова включает выбор, ничего не меняет и снова публикует «выключено».

`getAvailableCommands` добавляет `COMMAND_SEEK_TO_NEXT(_MEDIA_ITEM)` и `COMMAND_SEEK_TO_PREVIOUS(_MEDIA_ITEM)`, когда в очереди есть треки: сам ExoPlayer убирает «вперёд» на последнем треке, и тогда сессия отбросила бы команду, а в конце волны она значит «догрузить» (WAVE-09), а в конце конечной очереди — «стоп» (TR-04).

**Traps:**
- `MediaSession` берёт набор команд и из `getAvailableCommands`, и из события `onAvailableCommandsChanged`; поэтому листенеры оборачиваются (`TransportCommandsListener`), и событие несёт тот же расширенный набор.
- `TransportCommandsListener` пересылает каждый из 37 методов `Player.Listener` явно, включая устаревшие (`@Suppress("OVERRIDE_DEPRECATION", "DEPRECATION")`: их пересылает и `ForwardingListener` из Media3). Делегирование Kotlin `Player.Listener by listener` не годится: для default-методов Java-интерфейса Kotlin пересылку не генерирует, а в `Player.Listener` все методы такие. Так было в v0.2.0: сессия получала только смену команд, и контроллеры (экран плеера, уведомление Media3, экран блокировки) навсегда оставались со снимком состояния на момент подключения — не шёл прогресс и спектр, не появлялось уведомление, сервис не уходил в foreground и умирал при выходе из приложения. `playback/QueueForwardingPlayerTest` сверяет доставку каждого события с обычным `ForwardingPlayer`; новый метод слушателя в Media3 уронит этот тест, пока его не перешлют.
- `Media3Engine` управляет самим ExoPlayer, а не `QueueForwardingPlayer`: иначе `QueueController.next()` → `skipToNext()` вернулся бы в `next()`, а `applyModes()` — в `setShuffle()`.

## `Media3Engine`

```kotlin
@OptIn(UnstableApi::class)
class Media3Engine(player: ExoPlayer, controller: QueueController, random: Random = Random.Default,
    onAudioFailure: (AudioFailure) -> Unit = {}) : PlayerEngine {
    fun attach()     // addListener + HeadShuffleOrder на пустой плеер + controller.attach(this)
    fun detach()
}
```

Тонкий: ни одного решения, только перевод. Команды `PlayerEngine` → вызовы `ExoPlayer` (`setTracks` = заранее поставленный проход (см. `HeadShuffleOrder`) + `setMediaItems(…, startIndex, startPositionMs)` + `prepare()` + `playWhenReady`; `shuffleHead(head, lead)` = `setShuffleOrder(HeadShuffleOrder(HeadShuffle.pass(head, mediaItemCount, lead)))`; `appendTracks` = `addMediaItems(mediaItemCount, …)`, порядок ExoPlayer клонирует сам (`HeadShuffle.inserted`); `insertTracks(i, …)` = заранее поставленный порядок со вставкой за соседом (`staging(…, at = i)`, `HeadShuffle.insertedAfter`) + `addMediaItems(i, …)`, текущий трек и буфер не трогаются; `removeAt` = `removeMediaItem` (см. ловушку про текущий трек); `reload(i)` = заранее поставленный порядок замены (`HeadShuffleOrder.replacing`) + `replaceMediaItem(i, …)` с URI новой ревизии (ниже, «Загрузить элемент заново»); `clear` = `clearMediaItems`; `seekTo(i)` = `seekTo(i, 0)`; `seekToPosition` = `seekTo(ms)`; `skipToNext`/`skipToPrevious` = `seekToNext/PreviousMediaItem`; `pauseAtEndOfCurrent` = `pauseAtEndOfMediaItems`). Движок держит копию порядка ExoPlayer (`order: HeadShuffle`) и меняет её до каждого вызова плеера так же, как ExoPlayer меняет свой: `HeadShuffleOrder` клонируется детерминированно. Вставка в пустой плеер ставит свой порядок заранее, как `setTracks`, иначе ExoPlayer сделал бы случайный проход, которого копия не знает. `insertTracks` ставит его всегда: сам ExoPlayer клонирует порядок детерминированно, но кладёт вставленные треки в остаток по возрастанию, а не в проход за соседом. События `Player.Listener` → методы контроллера:

| Событие ExoPlayer | Вызов |
|---|---|
| `onMediaItemTransition(item, reason)` | `onItemChanged(MediaItems.toTrack(item), transition, player.isPlaying)`; причина: `AUTO` → `AUTO`, `REPEAT` → `REPEAT`, `SEEK` → `SEEK`, остальное (`PLAYLIST_CHANGED`) → `NEW_QUEUE` |
| `onPlaybackStateChanged(STATE_ENDED)` | `onEnded()` |
| `onPositionDiscontinuity(old, new, reason)` | `onSeeked()`, только при `DISCONTINUITY_REASON_SEEK` и одном `mediaItemIndex` у `old` и `new`; перемотка на другой элемент приходит как `onMediaItemTransition(SEEK)`. `seekToPrevious/NextMediaItem` на тот же элемент (повтор текущего, `repeatCurrentMediaItem` в Media3) даёт и `onSeeked()`, и сразу за ним `onMediaItemTransition(SEEK)` — это безвредно (вне джема лишнее сохранение, в джеме повтор выключен), так что фильтр «тот же элемент» остаётся как есть |

`onShuffleModeEnabledChanged` и `onRepeatModeChanged` не пересылаются: режимы ExoPlayer пишет только контроллер (`shuffleEnabled` = `shuffleModeEnabled`, `repeatEnabled = true` — это `REPEAT_MODE_ALL`: повтора одного трека нет, TR-06), а выбор пользователя приходит командами через `QueueForwardingPlayer`.

`playOrder()` обходит `currentTimeline` через `getFirstWindowIndex`/`getNextWindowIndex(…, REPEAT_MODE_OFF, shuffle)`.

**Загрузить элемент заново** (`reload(i)`, QUAL-05). Нужно, когда ExoPlayer уже начал грузить следующий трек в старом качестве: элемент заменяется своей копией с другим URI, ExoPlayer бросает загруженное и грузит элемент с нуля, а плейлист, порядок, текущий трек и курсор остаются. `reload(i)` ничего не делает, если `i` вне плейлиста, равен `currentMediaItemIndex` или URI элемента не `qiyaa://track/…`. Иначе копия порядка берёт длину плеера (`fitted`), затем `setShuffleOrder(HeadShuffleOrder.replacing(order, mediaItemCount, i, random))`, строка в logcat `Reloading track <id> at <i> as revision <n>` (тег `QiYaa`, debug: так в logcat видно, что следующая подпись этого трека — от `reload`, а не повтор) и `replaceMediaItem(i, MediaItems.revised(item, id, n))`. `n` — счётчик движка, с 1: новый URI всегда отличается от нынешнего, в том числе после пересоздания сервиса, потому что заново поставленные элементы ревизии не несут. Копия `order` после замены не меняется: ExoPlayer приходит ровно к ней (`HeadShuffleOrder`, «Замена элемента»).

Путь в Media3 1.11.1 (сверено по исходникам; на устройстве не проверялось, Kickoman/QiYaa-android#91):
- `BasePlayer.replaceMediaItem(i, item)` = `replaceMediaItems(i, i + 1, [item])` (`BasePlayer.java:81–84`). `ExoPlayerImpl.replaceMediaItems` (`ExoPlayerImpl.java:790–823`) сначала спрашивает `canUpdateMediaSourcesWithMediaItems` (`:3187`): `ProgressiveMediaSource.canUpdateMediaItem` сравнивает URI, `imageDurationMs` и `customCacheKey` (`ProgressiveMediaSource.java:387–394`), `MaskingMediaSource` (`:81`) и `WrappingMediaSource` (`:111`) отдают вопрос ему. С тем же URI элемент обновляется на месте вместе с загруженным периодом, и заново ничего не грузится; поэтому URI другой.
- С другим URI — `addMediaSourcesInternal(i + 1)` → `cloneAndInsert(i + 1, 1)` (`:2699`), затем `removeMediaItemsInternal(i, i + 1)` → `cloneAndRemove(i, i + 1)` (`:2759`) и один `updatePlaybackInfo`. Поток воспроизведения хранит порядки, которые ему передали, и сам их не клонирует (`MediaSourceList.java:147–150`, `197–199`).
- На потоке воспроизведения `handleMediaSourceListInfoRefreshed` (`ExoPlayerImplInternal.java:2589`) оставляет играющий период: окно текущего элемента то же. `MediaPeriodQueue.updateQueuedPeriods` (`MediaPeriodQueue.java:653`) за играющим периодом ждёт период нового элемента с новым uid, не находит его (`canKeepMediaPeriodHolder`, `:1052`) и зовёт `removeAfter` (`:679`, `:553`): освобождаются подгруженный период и все после него. Отменённая загрузка прерывает свой поток (`Loader.java:420–428`): подпись, которая ещё шла в старом качестве, обрывается (`runBlocking` отменяет корутину) и запись кэша не пишет, а успевшая запись старого качества просто не подходит новому старту. `maybeUpdateLoadingPeriod` (`ExoPlayerImplInternal.java:2769`) создаёт период нового элемента с позиции 0, и `TrackResolver` зовёт `get(id, continuing = false)` — в действующем качестве. Периоды за ним создаются заново со своими старыми URI, и кэш подписывает их заново, если качество записи не то.
- `Util.inferContentType` смотрит на последний сегмент пути (`Util.java:3051`), поэтому `?r=` оставляет элемент прогрессивным источником. Кэша данных и `customCacheKey` в цепочке источников нет: каждый заново созданный период открывается через `TrackUrlCache.get`.
- Событий нет: окно текущего элемента то же — нет `onMediaItemTransition` (`ExoPlayerImpl.evaluateMediaItemTransitionReason`, `:2553`); играющий период тот же — нет разрыва позиции (`:813–814`); `onTimelineChanged` движок не пересылает. Исключение — последние 1–2 с трека, когда рендереры уже читают следующий период: `removeAfter` сообщает `UPDATE_PERIOD_QUEUE_ALTERED_READING_PERIOD`, и ExoPlayer делает `seekToCurrentPosition(false)` (`ExoPlayerImplInternal.java:2638–2639`). Играющий трек перечитывается со своей позиции из буфера (без сети, тот же файл, короткий сброс звука — щелчок), а `seekToPeriodPosition` переводит `READY` в `BUFFERING` (`:1840–1842`): контроллер получает `onIsPlayingChanged(false)` и потом `(true)`, то есть сохранение, а в джеме — `playing{paused: true}` и сразу `paused: false`, мигание у слушателей. Это та же цена, что у паузы в конце (ловушка выше), и у любой буферизации. Пока стоит `pauseAtEndOfMediaItems`, чтение в следующий период не уходит (`:2925`), и щелчка нет.

**Traps:**
- Все вызовы — с главного потока ExoPlayer; листенеры ExoPlayer срабатывают после завершения команды, так что контроллер видит уже обновлённое состояние.
- Пауза в конце трека (Media3 1.11.1, сверено по исходникам `ExoPlayerImplInternal`, так же было в 1.4.1; на устройстве не проверялось): когда играющий период дорендерен и стоит `pendingPauseAtEndOfPeriod`, `doSomeWork` делает `setPlayWhenReadyInternal(false, …, END_OF_MEDIA_ITEM)`, а в `STATE_ENDED` уходит только последний период; следующий период рендерерам не отдаётся. Флаг ставится, когда последний трек головы становится текущим; если чтение к этому моменту уже ушло в следующий период, цена — один `seekToCurrentPosition` (щелчок, не чужой трек). ExoPlayer при этом всё равно подгружает первый трек продолжения (`download-info` и байты) на каждом круге головы. Пока длится пауза, `playWhenReady = false`, и уведомление Media3 на миг считает воспроизведение остановленным; держится ли сервис на переднем плане в фоне с выключенным экраном — проверка на телефоне.
- Удаление текущего элемента (Media3 1.11.1, сверено по исходникам, на устройстве не проверялось): `removeMediaItemsInternal` → `getPeriodPositionUsAfterTimelineChanged` → `ExoPlayerImplInternal.resolveSubsequentPeriod(…, repeatMode, shuffleModeEnabled, …)` по старому таймлайну, то есть следующий элемент старого порядка воспроизведения (с `REPEAT_MODE_ALL` — по кругу), с позиции по умолчанию; без него — первый элемент нового порядка (`getFirstWindowIndex(shuffle)`) и `STATE_ENDED`. С Media3 1.9.1 (androidx/media#2873) конец решает тот же `resolveSubsequentPeriod`, что и внутренний плеер: в 1.4.1 `STATE_ENDED` маскировался, когда удалён хвост, а текущий индекс был последним по индексу, даже если в перемешанном порядке за ним ещё что-то было. Теперь удаление текущей строки, последней по индексу, но не по порядку, переводит ExoPlayer на следующую строку порядка без конца, а удаление последней по порядку, но не по индексу, — заканчивает. Отыгранную строку или `STATE_ENDED` правит контроллер: перемоткой к цели обхода или остановкой в конце (`queue/README.md`, «Удаление текущего трека»); `support/FakeEngine.removeAt` повторяет поведение 1.11.1.
- Граница трека. Главный поток отстаёт от потока воспроизведения на одно сообщение: если `reload` следующего элемента придёт через несколько мс после того, как ExoPlayer на нём уже начал играть, удаление уберёт играющий элемент, ExoPlayer начнёт замену с 0, а контроллер получит второй переход. Это окно есть у любой правки плейлиста; на устройстве не проверялось.
- Предзагрузка плейлиста выключена: `ExoPlayer.PreloadConfiguration` остаётся по умолчанию (`DEFAULT`, `targetPreloadDurationUs = C.TIME_UNSET`, `ExoPlayer.java:195–196`), и вперёд грузится только то, что за играющим периодом. Если её включить, ExoPlayer начнёт грузить и дальние элементы, и правило «заново — только следующий» (`queue/README.md`, QUAL-05) надо будет пересмотреть.
- `ShuffleOrder`, `setShuffleOrder`, `pauseAtEndOfMediaItems` в Media3 1.4.1 и 1.11.1 — `@UnstableApi`: `HeadShuffleOrder` помечен `@UnstableApi`, `Media3Engine` — `@OptIn(UnstableApi::class)` (`androidx.annotation.OptIn`), иначе lint с `warningsAsErrors` падает.
- `onSeeked` опирается на код Media3 1.11.1 (сверено по исходникам `ExoPlayerImpl.seekTo` и `updatePlaybackInfo`, так же было в 1.4.1; на устройстве не проверялось). `seekTo` заканчивается `updatePlaybackInfo(…, DISCONTINUITY_REASON_SEEK)` и `flushEvents()`, поэтому разрыв доходит до листенера внутри самого вызова, уже с новой позицией и без `STATE_ENDED` (перемотка из `READY` или `ENDED` сначала показывает `BUFFERING`); исключение — перемотка из колбэка ExoPlayer, тогда разрыв приходит после остальных событий того же обновления (`ListenerSet.flushEvents` ставит их в хвост очереди). `QueueController` перематывает только из команд сессии, UI и сокета джема, поэтому `support/FakeEngine.seekToPosition` зовёт `onSeeked()` синхронно. `setMediaItems` даёт разрыв с причиной `REMOVE`, повтор после ошибки (`prepare()`) разрыва не даёт, так что `onSeeked` приходит только на перемотку внутри текущего трека: ползунок экрана и уведомления, «назад», перемотка в 0 у «стоп», а также любой `seekTo` на текущий элемент (тап по текущей строке плейлиста, «плей» в конце очереди из одного трека, в том числе из уведомления). Всем им нужно одно и то же: отчёт джему, сохранение позиции и конец ожидания продолжения (`queue/README.md`, «Ждёт продолжения»).

## `HeadShuffleOrder`

```kotlin
@UnstableApi
class HeadShuffleOrder(val shuffle: HeadShuffle, random: Random, val staged: HeadShuffle? = null, val stagedAt: Int = 0) : ShuffleOrder {
    override fun getLength();  getNextIndex(i);  getPreviousIndex(i);  getFirstIndex();  getLastIndex()   // по shuffle.order; C.INDEX_UNSET на концах и в пустом
    override fun cloneAndInsert(at, count);  cloneAndRemove(from, until);  cloneAndClear()               // staged или HeadShuffle.inserted / removed / EMPTY
    override fun cloneAndSet(count, startIndex)                                                           // staged при stagedAt = 0, иначе свежий проход (Media3 1.9+)
    companion object {
        fun staging(installed: HeadShuffle, itemCount: Int, pass: HeadShuffle, random: Random, at: Int = 0): HeadShuffleOrder
        fun fitted(copy: HeadShuffle, itemCount: Int): HeadShuffle                  // copy, если её длина = itemCount, иначе порядок по возрастанию
        fun afterInsert(copy: HeadShuffle, itemCount: Int, index: Int, count: Int): HeadShuffle   // копия после addMediaItems(index, …)
        fun afterSplice(copy: HeadShuffle, itemCount: Int, index: Int, count: Int): HeadShuffle   // то же со вставкой за соседом (insertedAfter)
        fun afterRemove(copy: HeadShuffle, itemCount: Int, index: Int): HeadShuffle               // копия после removeMediaItem(index)
        fun replacing(installed: HeadShuffle, itemCount: Int, index: Int, random: Random): HeadShuffleOrder   // перед replaceMediaItem(index): после замены порядок тот же
    }
}
```

Порядок ExoPlayer для контракта `queue.PlayerEngine`: проход головы, затем остальные индексы по возрастанию (`queue/README.md`, «`PlayerEngine`»). Поиск следующего и предыдущего — O(1) по заранее посчитанным массивам. Клоны детерминированы: вставка в непустой порядок не делает треки головой, удаление сохраняет порядок остальных. Вставка в пустой порядок делает из вставленных треков проход, случайный, если заранее ничего не поставлено. Заранее поставленный порядок (`staged`) `cloneAndInsert(at, count)` возвращает вместо всего этого, если `at == stagedAt` и длина `staged` равна длине порядка плюс `count`, а `cloneAndSet(count, startIndex)` — если `stagedAt == 0` и длина `staged` равна `count`; иначе `cloneAndSet` делает то же, что по умолчанию в Media3: `cloneAndClear().cloneAndInsert(0, count)`, свежий случайный проход. `cloneAndMove` не переопределён (ниже).

**Заранее поставленный порядок** (`staged`, `stagedAt`). `setMediaItems` в `ExoPlayerImpl` (Media3 1.11.1, сверено по исходникам: `setMediaSourcesInternal` → `setMediaSourceHolders` → `shuffleOrder.cloneAndSet(n, startIndex)`, `ExoPlayerImpl.java:2684`) клонирует порядок ровно один раз, до того как листенеры получат `onMediaItemTransition`; `ExoPlayerImplInternal.setMediaSources` → `MediaSourceList.setMediaSources` хранит тот порядок, который ему передали. Поэтому `Media3Engine.setTracks` сначала ставит `staging(…)`: текущий порядок той же длины, что у плеера, с проходом новой очереди в `staged` и `stagedAt = 0`, и `cloneAndSet(n, …)` возвращает именно этот проход. `startIndex` при этом не смотрится: проход уже начинается с того, что выбрал контроллер (`lead`). Контроллер, которому ExoPlayer синхронно сообщает смену трека изнутри `setMediaItems`, уже видит настоящий порядок, а не случайный промежуточный (`onItemChanged` → `playOrder()`). Отдельного `setShuffleOrder` после `setMediaItems` нет. До Media3 1.9 `setMediaItems` звал вместо этого `cloneAndRemove(0, size)` (если плейлист не пуст) и `cloneAndInsert(0, n)`; эти клоны держат `staged` по-прежнему: удаление всего его сохраняет, вставка в 0 той же длины берёт. `addMediaItems(index, …)` в непустой плейлист клонирует порядок ровно один раз, `cloneAndInsert(min(index, size), n)` в `addMediaSourceHolders`, и `MediaSourceList.addMediaSources` хранит переданный порядок; в пустой плейлист он идёт путём `setMediaSources`, то есть `cloneAndSet(n, C.INDEX_UNSET)` (Media3 1.11.1: `addMediaSources` проверяет `playbackInfo.timeline.isEmpty()`). Поэтому `Media3Engine.insertTracks` ставит `staging(…, at = index)` со вставкой за соседом (`afterSplice`), и ExoPlayer берёт её вместо своего клона, а `appendTracks` и `insertTracks` в пустой плеер ставят `staging` с `stagedAt = 0`, который берёт `cloneAndSet`. Какой клон зовёт ExoPlayer, JVM-тест показать не может: `HeadShuffleOrderTest` проверяет каждый клон отдельно, а путь вызова сверен по исходникам Media3 1.11.1 (на устройстве не проверялось).

**Замена элемента** (`replacing`, QUAL-05). `replaceMediaItem(i, …)` с другим URI клонирует порядок дважды: `cloneAndInsert(i + 1, 1)`, затем `cloneAndRemove(i, i + 1)` (`Media3Engine`, «Загрузить элемент заново»). Сам `cloneAndInsert` положил бы новый индекс в остаток, и с shuffle следующим стал бы другой трек. `replacing(installed, itemCount, i, random)` — это `staging(fitted(installed, itemCount), itemCount, S, random, at = i + 1)`, где `S = fitted(…).insertedAfter(i + 1, 1)`: новый индекс `i + 1` стоит в порядке сразу за `i`, в проходе головы или в остатке. Вставка берёт `S`, удаление убирает `i` и сдвигает `i + 1` на его место, и получается ровно поставленный порядок (`HeadShuffleOrderTest` проверяет каждый индекс прохода и остатка). Между двумя клонами (поток воспроизведения может сделать шаг между сообщениями) за текущим треком по-прежнему стоит старый следующий, в том числе на завороте к первому, а за ним — новый элемент: чужой трек следующим не становится ни на миг. Если старый следующий уже скачан целиком, ExoPlayer в этот миг может начать грузить новый элемент за ним: это подпись того же трека в новом качестве, и удаление тут же сбрасывает период, а ссылка остаётся в кэше. `stagedAt = i + 1 ≥ 1`, поэтому `cloneAndSet` (берёт только `stagedAt == 0`) этот порядок не возьмёт; на деле замена тратит его в том же вызове: URI всегда другой, а плейлист не пуст.

**Traps:**
- `ExoPlayerImpl.setShuffleOrder` требует `getLength() == mediaItemCount` (`checkArgument`). Порядок, который ставится перед `setMediaItems`, берёт длину у плеера, а не у копии в `Media3Engine`: сессия разрешает контроллерам все команды плеера, и `removeMediaItem` извне меняет плейлист мимо копии. При расхождении `staging` ставит порядок по возрастанию длины плеера. Расхождение той же длины так не видно, и `insertTracks` и `reload` ставят копию движка поверх настоящего порядка ExoPlayer: если плейлист изменили мимо `Media3Engine`, не меняя длины (`moveMediaItem` контроллера сессии, ловушка про `cloneAndMove` ниже и Kickoman/QiYaa-android#101, или `onPlaybackResumption`, который ставит треки в пустой плеер: копия тогда — `fitted(EMPTY, n)`, порядок по возрастанию, а у ExoPlayer — случайный проход `cloneAndSet`), то с включённым shuffle вставка или загрузка заново молча меняет порядок воспроизведения ExoPlayer, колбэка об этом нет, и флаг паузы `applyModes` не пересчитывается.
- Вставка и удаление в `Media3Engine` меняют копию через `afterInsert`/`afterRemove`, а не прямо через `HeadShuffle.inserted`/`removed`: те требуют индекс внутри длины, а ExoPlayer (`addMediaItems`, `removeMediaItems`) индекс за концом прижимает к концу и удаление за концом пропускает. После правки плейлиста извне (та же причина) индекс контроллера может оказаться за концом, и удаление последней строки в приложении иначе уронило бы сервис. Обе функции сначала берут длину у плеера (`fitted`), как `staging`.
- Ключ поставленного порядка — индекс, уже прижатый к длине плейлиста: ExoPlayer прижимает индекс `addMediaItems` до `cloneAndInsert`, и неприжатый ключ молча потерял бы вставку за соседом. `Media3Engine.insertTracks` прижимает индекс один раз и отдаёт его и `afterSplice`, и `staging`, и `addMediaItems`.
- Поставленный порядок используется один раз: порядок, который вернули `cloneAndInsert` или `cloneAndSet`, его уже не несёт, и любой клон, кроме удаления всего, его отбрасывает. Иначе следующий `setMediaItems` той же длины (например, сессии при возобновлении) получил бы старый проход, а не свежий.
- `cloneAndClear` даёт пустой порядок без `staged`. `MediaSourceList.setShuffleOrder` зовёт его только при несовпадении длины, а его исключает проверка выше; `cloneAndSet` по умолчанию тоже начинается с `cloneAndClear`, поэтому без переопределения каждый `setMediaItems` в Media3 1.9+ получал бы случайный проход (CONT-09).
- `cloneAndMove` не переопределён. В Media3 1.11.1 его зовёт `moveMediaItems`, а по умолчанию он возвращает тот же порядок (`return this`): перестановка той же длины, но уже не по контракту `PlayerEngine`, и копия в `Media3Engine` с ней разойдётся. Так же было в 1.4.1, где `moveMediaItems` порядок вовсе не трогал. Приложение `moveMediaItems` не зовёт, но контроллер сессии может (`COMMAND_CHANGE_MEDIA_ITEMS` среди команд по умолчанию) — это старая дыра, не новая. Если приложение начнёт переставлять строки через `moveMediaItems`, нужен `cloneAndMove`, который двигает индексы, как `HeadShuffle`, и такая же правка копии в `Media3Engine`.

## Классификация ошибок

`PlaybackFailures.classify` определяет вид по коду `PlaybackException` и по цепочке `cause`, никогда по тексту. Проверки идут сверху вниз:

| Вид | Признак |
|---|---|
| `SESSION` | в цепочке `HttpException` с `isTokenRejected` |
| `NETWORK` | код 2001/2002 (`IO_NETWORK_CONNECTION_*`) или в цепочке `NetworkException`, `UnknownHost`, `Connect`, `SocketTimeout`, `NoRouteToHost` |
| `TRACK` | всё остальное: 2004 (статус хранилища), `HttpException` 4xx/5xx от API, `MalformedResponseException`, парсинг 3xxx, декодер 4xxx |

Что делать с каждым видом, решает `queue/ErrorPolicy` (см. `queue/README.md`).

`PlaybackFailures.audioFailure(errorCode)` — для телеметрии (`error audio/…`, `telemetry/README.md`), тоже только по коду и через константы `PlaybackException.ERROR_CODE_*`, а не числа (сверено с исходниками `PlaybackException` Media3 1.11.1: коды те же, что в 1.4.1, ни одного нового или устаревшего):

| `AudioFailure` | Коды |
|---|---|
| `INIT` (не открылось устройство вывода) | 5001 `AUDIO_TRACK_INIT_FAILED`, 5004 `AUDIO_TRACK_OFFLOAD_INIT_FAILED` |
| `DEVICE` (устройство отказало во время игры) | 5002 `AUDIO_TRACK_WRITE_FAILED`, 5003 `AUDIO_TRACK_OFFLOAD_WRITE_FAILED`, 4006 `DECODING_RESOURCES_RECLAIMED` |
| `UNDECODABLE` | 3001–3004 `PARSING_*`, 4001–4005 `DECODER_INIT_FAILED`, `DECODER_QUERY_FAILED`, `DECODING_FAILED`, `DECODING_FORMAT_EXCEEDS_CAPABILITIES`, `DECODING_FORMAT_UNSUPPORTED` |
| `null` | всё остальное: сеть и HTTP (2xxx — это `api` и `playback`), DRM, неизвестные коды |

Эта же ошибка идёт и в `queue` как `FailureKind` (обычно `TRACK`), поэтому битый файл даёт два события: `audio/undecodable` и `playback/track`. `Media3Engine` зовёт `onAudioFailure` до `controller.onFailure`; по умолчанию это `{}`, `PlaybackService` передаёт `AppTelemetry.audioFailed`.

`PlaybackFailures.errorKind` говорит, что показать: `SESSION` → `TokenRejected`, `NETWORK` → `NoNetwork`, `TRACK` → `ServerError(status)`, если в цепочке есть `HttpException` или `HttpDataSource.InvalidResponseCodeException` хранилища, иначе `TrackUnplayable` (нет вариантов, декодер, парсинг). Подробности ошибки — только в logcat.

**Traps:**
- ExoPlayer сам повторяет сетевые ошибки загрузчика (около 3 попыток с паузой до 5 с) до `onPlayerError`, поэтому пауза наступает через несколько секунд после пропажи сети, а не сразу. Пока в буфере есть звук, трек доигрывает.
- Ошибки `TrackResolver` приходят с общим кодом 2000 (`IO_UNSPECIFIED`): отличить сеть от битого трека можно только по причине, поэтому `yandex` бросает типизированные исключения.
- `ERROR_CODE_DECODING_RESOURCES_RECLAIMED` стабилен с Media3 1.6.0 (в 1.4.1 был `@UnstableApi`), поэтому `PlaybackFailures` без `@OptIn`. При следующем обновлении Media3 коды надо сверить заново: новый код без строки в таблице даст `null`, то есть ничего в `audio`.
- С Media3 1.9 ExoPlayer сам останавливает зависший плеер (`StuckPlayerDetector`): буферизация без прогресса 10 мин, игра без движения позиции 10 с, позиция за длительностью трека 1 мин, подавление звука 10 мин. Это ошибка `ERROR_CODE_TIMEOUT` (1003) с причиной `StuckPlayerException`: `classify` даёт `TRACK` (трек пропускается, `TrackUnplayable`), `audioFailure` — `null`. Внутренняя проверка «буферизация без загрузки» 4 с даёт `ERROR_CODE_FAILED_RUNTIME_CHECK` (1004), как и в 1.4.1. Переназначать их или нет — вопрос к спеке, не к этому пакету.

## `MediaItems`, `TrackResolver`, кэш ссылок

URI трека виртуальный (`MediaItems.SCHEME = "qiyaa"`):

| URI | У какого элемента | Что из него читается |
|---|---|---|
| `qiyaa://track/{id}` | у каждого (`uriFor(track)` = `uriText(track.id)`) | `trackIdOf` → `{id}` |
| `qiyaa://track/{id}?r=<n>` | у элемента, загруженного заново (`Media3Engine.reload`, QUAL-05); `PARAM_REVISION = "r"`, `n ≥ 1` — счётчик движка | `trackIdOf` → `{id}`; запрос ничего не значит, он только делает URI другим |

`uriText(id, revision = 0)` строит текст (`require(revision >= 0)`), `revised(item, id, revision)` — тот же `MediaItem` (`buildUpon`) с новым URI: `mediaId`, метаданные и `extras` те же. `trackIdOf(uri)` — `uri.lastPathSegment` при схеме `qiyaa`: путь `qiyaa://track/42?r=3` — `/42`, запрос в путь не входит, так что `TrackResolver` и `ExpiredLinkDataSource` ревизии не видят. URI с ревизией живёт только в плейлисте ExoPlayer: `QueueSnapshot` хранит треки, `onPlaybackResumption` строит обычные элементы, а кроме `trackIdOf` URI в приложении никто не читает. `mediaId = track.id`, поэтому `PlaybackService.currentTrackId`, ♥ и `CurrentBitrate` замены не замечают. В `MediaMetadata.extras` (`Bundle`) лежат `id`, `albumId`, `durationMs` (long), `artists` (string array list), `cover` (nullable string), `title`, чтобы `toTrack` восстанавливал `Track` из уведомления и после пересоздания процесса без сети. `artworkUri` = `coverUrl`.

`TrackResolver.resolveDataSpec` вызывается на loading-потоке ExoPlayer при каждом открытии источника: старт, перемотка за скачанное, повтор после обрыва, предзагрузка следующего трека. `runBlocking { links.get(id, continuing = dataSpec.position > 0) }` там допустим: открытие с середины файла (перемотка за скачанное, повтор после обрыва) продолжает тот же файл. URI с другой схемой проходит без изменений.

```kotlin
class TrackUrlCache(
    clock: () -> Long,
    quality: () -> Quality = { Quality.STANDARD },   // качество, действующее сейчас
    ttlMs: Long = TTL_MS,
    capacity: Int = CAPACITY,
    resolve: suspend (String, Quality) -> ResolvedUrl,
) {
    suspend fun get(trackId: String, continuing: Boolean = false): ResolvedUrl
    fun peek(trackId: String): String?              // свежая ссылка из кэша без подписи; для слушателей джема
    fun invalidate(trackId: String)                 // отказ хранилища: следующий get подпишет заново, в том же качестве
    fun askedInOtherQuality(trackId: String): Boolean   // последний get этого трека (подписан или ещё подписывается) просил не quality(); false, если не просили
    companion object { TTL_MS = 15 * 60 * 1_000; CAPACITY = 64 }
}
```

**Качество** (`spec/player/quality.md`). Запись помнит качество, в котором ссылка подписана. `get(id)` — новый старт файла: берётся `quality()` и запись того же качества, пока она свежая; запись другого качества подписывается заново (QUAL-01, QUAL-02). `get(id, continuing = true)` — чтение с середины: берётся качество записи, даже если выбор уже другой, потому что файл другого кодека не продолжит начатый (QUAL-08); устаревшая запись подписывается заново в том же качестве. `invalidate` не удаляет запись, а делает её устаревшей, чтобы повторное открытие после 403/410 осталось в своём качестве. `peek` отдаёт ссылку любого качества: это файл, который играет.

**Какое качество просили** (QUAL-05). Вторая карта `asked: trackId → Quality` той же ёмкости (64) и с тем же порядком доступа, что и записи, помнит, в каком качестве трек спросили последним. `get` пишет её в первом `synchronized`-блоке, сразу как решено `wanted`, и **до** подписи: попадание в кэш тоже считается, чтение с середины пишет качество записи (то есть файла), а не `quality()`, подпись, которая ещё идёт или упала, — качество, в котором её начали. `askedInOtherQuality(id)` — `true`, если последний `get` этого трека просил качество, отличное от `quality()` сейчас; трек, который не спрашивали (или вытесненный), — `false`. Так видно, что ExoPlayer уже начал грузить файл в старом качестве. `asked` пишется в том же блоке, что читает `quality()`: подпись либо записала старое качество до проверки (проверка скажет «другое»), либо прочла уже новое; середины нет. `AppGraph` передаёт `quality = { qualityInEffect.value }`. `AppGraph.qualityInEffect: StateFlow<Quality>` — `combine(Settings.quality, Settings.qualityMetered, NetworkMonitor.metered)` → `stateIn(applicationScope, Eagerly, …)` с начальным значением из трёх `.value`: `Settings.qualityMetered` на лимитной сети (мобильная или лимитный Wi-Fi), иначе `Settings.quality` (QUAL-07). Это единственный источник действующего качества: подпись и всё, что следит за его сменой, читают одно значение и разойтись не могут.

Кэш один на процесс — `AppGraph.trackLinks`: его берут и сервис, и хозяин джема. `resolve` — `YandexApi.resolveTrackUrl(id, quality)`: в стандартном качестве два запроса, `download-info` к API и `download-info` хранилища; в экономии `get-file-info` (см. `yandex/README.md`). Часы — `SystemClock.elapsedRealtime`. Каждая настоящая подпись пишет в logcat `Signing the link of track <id>` (тег `QiYaa`, уровень debug): по ней видно, что перемотка и повторное открытие обходятся без API. Без кэша эти два запроса шли на каждое открытие; с кэшем перемотка и предзагрузка того же трека обходятся без API. Срок жизни подписанной ссылки Яндекс не документирует; проверено 2026-10-02: ссылка живёт час (параметр `ts` — время истечения в микросекундах), потом хранилище отвечает 401. 15 минут выбраны, чтобы перемотка в любое место почти любого трека шла по той же ссылке. Если ссылка истекла раньше, хранилище отвечает 403 или 410, и `ExpiredLinkDataSource` сбрасывает запись, заново открывает источник, а `TrackResolver` подписывает новую ссылку: цена слишком длинного срока — один лишний запрос. `CAPACITY` ограничивает память в длинной волне; вытесняется давно не использованная ссылка. Упавшая подпись не кэшируется. Доступ к кэшу синхронизирован: предзагрузка и текущий трек открываются с разных потоков; два одновременных промаха по одному треку подпишут ссылку дважды, это допустимо.

`ExpiredLinkDataSource` оборачивает `ResolvingDataSource` и повторяет открытие один раз, только для `HttpDataSource.InvalidResponseCodeException` 403/410 у `qiyaa://`-трека; второй отказ уходит в ExoPlayer как обычно (трековая ошибка, `queue/ErrorPolicy`). Все методы `DataSource` пересылаются явно: `getResponseHeaders` — default-метод Java, и делегирование Kotlin `by` его бы не переслало (см. ловушку `TransportCommandsListener`).

**Битрейт.** В экономии показание — `64K`. `TrackResolver` сообщает битрейт выбранного варианта в `CurrentBitrate.onResolved(id, kbps)`, а сервис — смену текущего трека (`onMediaItemTransition` → `currentTrackId` → `onCurrentChanged`). В `AudioBus.bitrateKbps` попадает битрейт текущего трека: предзагрузка следующего за ~50 с до конца его не меняет, показание меняется ровно на переходе; пока ссылка текущего трека не подписана — 0 (`--K`). Битрейты помнятся для последних 64 треков. Исключения `yandex` — `IOException`, поэтому ExoPlayer превращает их в `PlaybackException`, а не падает (см. `yandex/README.md`).

**Traps (URI):**
- `android.net.Uri` в JVM-тестах — заглушка с пустыми значениями (`unitTests.isReturnDefaultValues`), поэтому `MediaItemsTest` проверяет текст `uriText`, а то, что `lastPathSegment` не включает запрос, держится на документации Android (`Uri.getLastPathSegment` — последний сегмент пути) и проверке на телефоне (#91). Строить URI ревизии иначе, чем запросом (например, сегментом пути), нельзя: `trackIdOf` прочёл бы ревизию как id.

**Traps (качество):**
- Смена действующего качества (выбор для сети, которая сейчас, или переход между лимитной и безлимитной сетью, QUAL-07) доходит и до следующего трека, который ExoPlayer уже начал грузить (QUAL-05): если его ссылку уже спрашивали в другом качестве (подписанную или ещё подписываемую, `askedInOtherQuality`), `Media3Engine.reload` грузит его заново, и ExoPlayer выбрасывает вместе с ним всё подгруженное после (`queue/README.md`, «Смена качества»; `Media3Engine`, «Загрузить элемент заново»). Трек, которого ещё не спрашивали, загрузится в новом качестве сам. Трек, который играет, доигрывает своим файлом. Смена выбора для другой сети ничего не делает. На устройстве не проверялось (Kickoman/QiYaa-android#91).
- Бесшовность: `reload` идёт сразу при смене, обычно задолго до перехода; если до конца трека остаётся хотя бы время подписи и первых байтов (на деле несколько секунд), следующий трек идёт без паузы. В последние 1–2 с — щелчок, мигание `playing` в джеме и, может быть, короткая буферизация следующего трека (`Media3Engine`, «Загрузить элемент заново»). Порога нет: иначе следующий трек остался бы в старом качестве.
- Цена: до 50 с уже скачанного следующего трека (`DEFAULT_MAX_BUFFER_MS`, около 1,2 МБ при 192 кбит/с) выбрасывается и качается снова (около 0,4 МБ при 64 кбит/с); переход с Wi-Fi на мобильную сеть качает его заново по мобильной, так и задумано (QUAL-07). Подавления дребезга сети нет: каждое переключение стоит не больше одной такой загрузки. Быстрый возврат (A → B → A) ничего не стоит, только если он пришёл до подписи после `reload`: заново созданный период ещё не спросил ссылку, `asked` по-прежнему A, то есть действующее качество, и период загрузится в A. Если подпись уже началась, `asked` — B (`get` пишет его до подписи), и возврат загружает трек заново ещё раз. Трек, который спросили в экономии, а получили стандарт (QUAL-03), при выборе «Стандарта» загрузится заново один раз без нужды.
- Без сети смена качества выбрасывает и целиком скачанный следующий трек, а новую ссылку не подписать: на переходе будет ERR-01, хотя без смены трек сыграл бы из буфера. Этого требуют QUAL-05 и QUAL-04, и так же делает десктоп. Ожидание сети (ERR-09) от этого не меняется: текущий элемент `reload` не трогает.
- Слушать вместе (LISTEN-03, LISTEN-13): `listenNextUrl` — `peek` следующего трека. Пока подпись после `reload` не заменила запись (около секунды), `peek` отдаёт старую ссылку — она свежая и того же трека; потом переход на экономию убирает поле (файл не `/get-mp3/`), а на стандарт — даёт mp3. Новое значение уходит с ближайшим 10-секундным `playing`; отдельного `playing` при `reload` нет, новой ссылки тогда ещё нет. Ссылка текущего трека не меняется, поэтому при экономии слушатели и дальше встают на паузу до следующего трека в стандарте (LISTEN-10).
- Одна запись на id (Kickoman/QiYaa-android#94). Следующая строка с тем же треком, что играет, не перезагружается и играет в старом качестве (QUAL-08, выше). Но `reload` выбрасывает и периоды за следующим, а период, созданный заново, может нести id текущего трека: очередь из двух строк с повтором или текущий трек через строку за коротким следующим. Он подпишет текущий id в новом качестве и перезапишет запись, по которой читается играющий файл, и перемотка за скачанное получит файл другого кодека (ERR-04). Так же без `reload` делает собственная предзагрузка ExoPlayer у одной строки с повтором. Это редко; правило «качество по игре, а не по id» — #94.
- «С середины» определяется по `dataSpec.position > 0`. Открытие с позиции 0 считается новым стартом и берёт действующее качество. Если ExoPlayer перечитает с нуля уже начатый mp3 без тега ID3 после смены качества, он получит файл другого кодека, и трек кончится ошибкой (ERR-04). У файлов Яндекса ID3 есть, а первый сэмпл MP4 лежит после `moov`, так что на практике чтение с нуля не происходит.
- `NetworkMonitor.metered` — `StateFlow<Boolean>` на втором `registerDefaultNetworkCallback`: на каждый `onCapabilitiesChanged` сети по умолчанию он заново спрашивает `ConnectivityManager.isActiveNetworkMetered`. Колбэк только сообщает, что что-то изменилось, а определение лимитной сети то же, с каким QUAL-07 проверен на телефоне, когда его читали прямо при подписи (`isMetered()`). Это важно на API 26–28 под VPN: там, по AOSP, `isActiveNetworkMetered` смотрит на нижележащую сеть VPN, а возможности сети по умолчанию — это возможности самого VPN (ревью плана QiYaa-android#76, пункт 3). `onLost` значения не меняет: без сети действует прежний выбор, а следующая сеть сообщит своё (на API 26+ `onCapabilitiesChanged` идёт сразу за `onAvailable`). Начальное значение — `isActiveNetworkMetered` при создании, повторы отсекает `distinctUntilChanged`. Если смена сети не даст колбэка у сети по умолчанию (например, VPN не сообщит о смене нижележащей), действующее качество останется прежним до следующего колбэка: раньше подпись спрашивала заново каждый раз. На устройстве не проверялось (Kickoman/QiYaa-android#91).
- Подпись читает `qualityInEffect.value` на loading-потоке ExoPlayer: `StateFlow.value` потокобезопасен. Сразу после смены выбора или сети производное значение обновляется не мгновенно (`combine` на `Dispatchers.Default`), и подпись в эти миллисекунды ещё возьмёт старое качество. Это не страшно: сигнал QUAL-05 приходит уже после обновления, а такая подпись записала старое качество в `asked`, так что следующий трек всё равно будет загружен заново.

## `TimedAudioSink`

`buildAudioSink` оборачивает `DefaultAudioSink` в `TimedAudioSink(sink, audioBus.visualizerTap)`. `handleBuffer(buffer, presentationTimeUs, …)` сначала сообщает кольцу `announceInput(presentationTimeUs)`: процессоры вызываются внутри этого же `handleBuffer`, и отвод пишет кадры буфера с его временем. `getCurrentPositionUs`, который рендерер ExoPlayer спрашивает, пока играет, отдаёт звучащую позицию в тех же единицах и уже с учётом задержки `AudioTrack` и Bluetooth; `TimedAudioSink` передаёт её в `reportPlaying` с `System.nanoTime()`. Раз в 5 с пишет в logcat `Visualizer: the newest written audio sounds in N ms`.

**Traps:**
- С Media3 1.11 ExoPlayer по умолчанию планирует работу рендереров динамически (`dynamicSchedulingEnabled`), а PCM-буфер `AudioTrack` по умолчанию 500 мс (в 1.4.1 — четыре минимальных буфера в пределах 250–750 мс). `getCurrentPositionUs` поэтому может спрашиваться реже, и `VisualizerTap` чаще досчитывает позицию по часам (не больше 0,5 с, `audio/README.md`). Если на телефоне спектр начнёт отставать или дёргаться, выключатель — `ExoPlayer.Builder.experimentalSetDynamicSchedulingEnabled(false)` (`@ExperimentalApi`). На устройстве не проверялось.

## Процессоры

Оба — `BaseAudioProcessor` и работают только с `ENCODING_PCM_16BIT`. На другой формат (float, 24 бит) `onConfigure` возвращает `AudioFormat.NOT_SET`: процессор выключается, и `DefaultAudioSink` его пропускает, а звук идёт без EQ и визуализации, но играет. Раньше они бросали `UnhandledAudioFormatException`, и падало всё воспроизведение. `enableFloatOutput = false` держит декодеры в PCM16, так что это страховка. `EqualizerProcessor.onConfigure` сообщает формат в `AudioBus.setFormat`. `queueInput`: пустой буфер возвращается сразу — `replaceOutputBuffer(0)` в Media3 1.4–1.11 отдаёт общий `EMPTY_BUFFER`, и `put(inputBuffer)` на нём бросает «The source buffer is this buffer». `onFlush(streamMetadata)`/`onReset` сбрасывают состояние EQ и очищают кольцо; `onFlush()` без аргумента и `flush()` в Media3 1.11 устарели.

**Traps:**
- С Media3 1.8.0 `BaseAudioProcessor.reset()` больше не зовёт `onFlush`. В плеере это ничего не меняет: `AudioProcessingPipeline.reset()` сначала зовёт `flush(StreamMetadata.DEFAULT)`, потом `reset()`. Но прямой `reset()` (в тесте) кольцо `VisualizerTapProcessor` не очищает: у него нет `onReset`.

## `JamHost`

```kotlin
class JamHost(transport: JamTransport, connectivity: Flow<Boolean>, queue: QueueController, catalog: JamCatalog, store: JamSessionStore,
              config: () -> JamHostConfig, scope: CoroutineScope, io: CoroutineContext, appVersion: String,
              signedLink: (trackId: String) -> String? = { null }, newId: () -> String = UUID, clock: () -> Long = System::currentTimeMillis, log: (String, Throwable?) -> Unit = …) : JamHandler, JamPlaybackListener {
    val state: StateFlow<JamHostState>      // phase NONE/CREATING/ACTIVE, connection, connected, room, joinUrl, storedSession
    val events: SharedFlow<JamHostEvent>    // Refused(reason), Ended(BY_HOST | BY_SERVER | EXPIRED | GONE), NotConnected
    fun create(hostName: String, settings: JamSettingsPatch? = null): Boolean;  fun cancelCreate()
    fun continueStored();  fun discardStored()          // «Продолжить джем?» (HOST-23)
    fun end()
    fun add(track: Track): Boolean;  fun playNext(track: Track): Boolean
    fun pin(itemId);  fun remove(itemId);  fun kick(publicId);  fun changeSettings(patch);  fun rotateLink()   // Boolean: false без связи
    fun onServiceStarted();  fun onServiceStopped()
    override fun onItemStarted(itemId);  override fun onPlayback(playback);  override fun onRemoveItems(itemIds)   // JamPlaybackListener очереди
}
interface JamCatalog { suspend fun searchTracks(text: String): List<Track>; suspend fun tracks(ids: List<String>): List<Track> }
data class JamHostConfig(serverUrl: String, waveFeedback: Boolean, shareAudio: Boolean = false)
```

Сценарии — `spec/jam/host.md`. `AppGraph` создаёт один `JamHost` на процесс (`scope` — `Dispatchers.Main.immediate`, `io` — `Dispatchers.IO`, `catalog` — `Library.searchTracks` и `tracksByIds`, хранилище — `data/JamFile`, настройки — `jam/server`, `jam/waveFeedback`). Ключа хозяина нет: комнату может создать любое приложение, сервер ограничивает их число на IP (ROOM-02).

- **Сессия.** `create` проверяет имя и настройки тем же `JamCodec`, что и входящие сообщения: сообщение, которое сервер отвергнет и закроет соединение, не уходит вовсе (иначе переподключение слало бы его снова). После `welcome` — `create`, а если сессия уже есть — `resume` со снимком и `outbox`. `created` сохраняет `roomId`, `hostSecret`, `joinUrl` и включает режим джема очереди (`startJam(this, waveFeedback)`; очередь хозяина становится базой и названия не меняет, `jam_queue_title` больше нет); `resumed` очищает `outbox` и отправляет `playing` (HOST-26). **Связь** (`connected`) — это принятый `create` или `resume` на текущем соединении, а не просто `welcome`: до неё `started` идёт в `outbox`, а `playing` и действия хозяина не отправляются (HOST-25).
- **Хранение** (HOST-22). Сессия, последний `snapshot`, новая ссылка из `linkRotated` и каждое изменение `outbox` пишутся в `JamSessionStore` на `io` через `Channel.CONFLATED`.
- **«Продолжить джем?»** (HOST-23). Сохранённая сессия видна как `state.storedSession`; вопрос задаёт UI. «Да» — режим джема очереди сразу (`QueueController.startJam(…, afterRestart = true)`: база пустеет, восстановленный текущий трек на паузе и ждущие элементы остаются, D7, D17), потом `resume`. «Нет» — хранилище очищается сразу, очередь заканчивает джем (`QueueController.endJam`: элементы теряют `itemId`, хвост волны на сидах джема уходит), потом `resume` и `end` только чтобы гости увидели конец.
- **Отказы.** `resume` с `room-not-found` или `bad-secret` заканчивает джем здесь (HOST-24, `Ended(GONE)`); с другой причиной — `Refused` и новая попытка через 30 с (`RESUME_RETRY_MS`). Отказ `create` (например, `rate-limited`: с этого IP уже 2 живые комнаты) — `Refused` и никакой сессии. Отказ действия — `Refused(reason)`.
- **`state`**: версия не больше последней на этом соединении пропускается, первая после переподключения берётся как есть. Очередь уходит в `QueueController.onJamQueue` с сидами и `seedsVersion`.
- **Гости** (HOST-28…31). `searchRequest` — `Library.searchTracks` (`type=track`), доступные, до 20, `JamTracks.toJam`; ошибка — `failed`, 401/403 — `unauthorized` (сам вход покажет `yandex/Session`). `validateRequest` — `POST /tracks`: по ответу на каждый id по порядку, недоступный или пропавший — `track-unavailable`, упавший запрос — `failed` для всех. Оба запроса идут отдельными корутинами на `io` и не ждут плеер.
- **`command{skip}`** — `QueueController.jamSkip` (HOST-18, HOST-19).
- **Убрать элементы** (HOST-36, HOST-25). `onRemoveItems(itemIds)` зовёт очередь, когда REM плейлиста выбрал ждущие элементы джема: при связи — `remove{itemId}` на каждый, элементы уйдут со следующим `state`; без связи — ничего не уходит, и событие `JamHostEvent.NotConnected` (тост `jam_no_connection`). Остальные выбранные строки очередь удаляет сама и без связи.
- **`playing`** — из `onPlayback` очереди, только при связи (HOST-25: `playing` не копится). `ITEM` — `playing{source: item, itemId}`; `BASE` — любой трек базы, в том числе трек волны джема и элемент прошлого джема, — `playing{source: wave, track}` (HOST-10, HOST-14: протокол 1 сохраняет имя `wave`, `spec/jam/protocol/README.md` говорит, что оно покрывает любой трек базы); трек, который протокол не несёт (`JamTracks.toJam` — null), не сообщается вовсе; `IDLE` — `playing{source: idle}`.
- **Добавить** (HOST-20). `add` шлёт `add{track}`; трек попадает в хвост только со следующим `state`. `playNext` — `pin` для уже ждущего трека, иначе `add` и `pin`, когда элемент с этим треком от хозяина появится в `state`.
- **Конец** (HOST-32). `end()` отправляет `end`, если есть связь, и в любом случае заканчивает локально: `QueueController.endJam`, хранилище очищается, соединение закрывается. `ended` от сервера — то же без `end`.
- **Слушать вместе** (`spec/jam/listen.md`, LISTEN-01–05, LISTEN-13). С `JamHostConfig.shareAudio` (`Settings.jamShareAudio`, по умолчанию выключено) `playing` трека джема и трека базы несёт `listenUrl` — ссылку на файл, который играет, и `listenNextUrl` — на следующий (`JamPlayback.nextTrack`). Ссылки берутся из `TrackUrlCache.peek` — уже подписанные, без новых запросов к Яндексу; кэш теперь общий (`AppGraph.trackLinks`) для плеера и хозяина джема. Ссылка не из хранилища Яндекса (`JamCodec.isListenUrl`) не уходит: сервер отказал бы во всём `playing`. Поэтому файл экономии (`strm*.strm.yandex.net`, не `/get-mp3/`) слушателям не передаётся (LISTEN-13).
- **Соединение живёт с `PlaybackService`**: `onCreate` сервиса зовёт `onServiceStarted` (идёт джем — `resume`), `onDestroy` — `onServiceStopped` (соединение закрывается, джем остаётся в памяти и на диске, комната ждёт хозяина час, REC-05). На переднем плане ради джема сервис не держим.

## `JamTracks`

`toJam(track)` — `null`, если трек не проходит протокол (id не `^[0-9A-Za-z_-]{1,64}$`, пустое название); управляющие символы → пробелы, название ≤ 150, исполнители ≤ 10 по ≤ 64 символа, длительность 0…24 ч. `coverUri` восстанавливается из `coverUrl`: без схемы, `400x400` в конце → `%%`; адрес без размера — без обложки. `fromJam` — обратно через `TrackParsing.coverUrl`.

Тем же `toJam` строит трек для своего `add{track}` гость в приложении (GUEST-07, `jam/JamGuest`), как хозяин строит треки для гостей (`spec/jam/host.md`, «Search and check for guests»). Пределы считаются в знаках UTF-16, поэтому худший случай для кадра — трёхбайтовые знаки (CJK) во всех полях: такой `add` весит около 3,6 КБ и влезает в 4 КиБ кадра гостя (`limits.md`, `JamTracksTest`).
