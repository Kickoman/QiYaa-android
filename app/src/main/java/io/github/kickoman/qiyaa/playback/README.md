# `playback/` — воспроизведение

ExoPlayer внутри `MediaSessionService`, адаптер между ExoPlayer и очередью, хозяин джема, классификация ошибок воспроизведения, ленивое разрешение ссылок, копия скачанного текущей игрой на диске, загрузчик обложек сессии на Coil и два аудиопроцессора, которые вставляют `audio/` в звуковой конвейер. Пакет **не** решает, что играть дальше (это `queue/`), **не** ходит в сеть сам (это `yandex/`), **не** считает DSP (это `audio/`) и **не** показывает текст.

```bash
grep -rln 'qiyaa\.ui\.' app/src/main/java/io/github/kickoman/qiyaa/playback/   # ничего не печатает
```

## Конвейер

`QueueController.setQueue` → `Media3Engine.setTracks` → `MediaItems.toMediaItem` → ExoPlayer (10 мин позади, 50 с впереди) → `PlaybackDataSources`, своя цепочка на каждый период: `CacheDataSource` (`PlaybackCache`, ключ игры) → `ExpiredLinkDataSource` → `ResolvingDataSource(TrackResolver → PlayLink → TrackUrlCache)` → `InterruptibleDataSource` (`ReadInterrupts`) → `OkHttpDataSource` поверх `CallTracker` → декодер → `DefaultAudioSink[EqualizerProcessor, VisualizerTapProcessor]` → `AudioTrack`. Ссылка на mp3 подписывается в момент открытия сети, поэтому очередь из 300 треков не делает 300 запросов заранее; то, что игра уже скачала, читается с диска без подписи.

## `PlaybackService`

Собирает `ExoPlayer` с `DefaultRenderersFactory`, у которого `buildAudioSink` подменён на `DefaultAudioSink` с двумя процессорами и `enableFloatOutput = false` (процессоры принимают только `ENCODING_PCM_16BIT`); третий аргумент `buildAudioSink` уходит в `setEnableAudioOutputPlaybackParameters` как есть (до Media3 1.9 — `setEnableAudioTrackPlaybackParams`). Атрибуты `USAGE_MEDIA`/`AUDIO_CONTENT_TYPE_MUSIC` с `handleAudioFocus = true`, `handleAudioBecomingNoisy`, `WAKE_MODE_NETWORK`, источники данных — `PlaybackDataSources(appGraph.httpClient, appGraph.trackLinks, bitrate, appGraph.playbackCache, appGraph.readInterrupts)` (ниже), `LoadControl` — `PlayerBuffer.loadControl()` («Перемотка и буфер» ниже). Громкость сервис берёт из `Settings.volume` и следит за ней сам (`serviceScope`, `AudioBus.volumeGain`), поэтому она применяется и без открытого экрана. Тап по уведомлению открывает launcher-intent пакета (сервис не знает про `ui/`). Иконка уведомления — `R.drawable.ic_notification`.

Сервис объявлен `exported="true"` с `tools:ignore="ExportedService"`: так требует Media3, чтобы система и гарнитуры могли привязаться к `MediaSessionService`. `onCreate` создаёт `Media3Engine(player, appGraph.queue, onAudioFailure = { appGraph.telemetry?.audioFailed(it) })` (ошибки звука уходят в телеметрию, `error audio/…`; в сборке без неё `telemetry` — `null`), подключает его и отдаёт сессии `QueueForwardingPlayer(player, appGraph.queue)`; сессия получает `SessionCallback` (кнопки лайка и дизлайка, «играть» после выгрузки процесса) и `CoverBitmapLoader` (ниже, «Обложка в уведомлении»); `onTaskRemoved` зовёт `pauseAllPlayersAndStopSelf()`, если ничего не играет (нет `playWhenReady` или очередь пуста); `onDestroy` отключает движок (контроллер запоминает, где остановились), освобождает плеер и сессию, а затем стирает диск плеера (`appGraph.playbackCache.clear()`). Листенер `onMediaItemTransition` сервиса на каждой смене трека зовёт `appGraph.playbackCache.keepFor(player)` («`PlaybackCache`» ниже). Оба сообщают `appGraph.jamHost` (`onServiceStarted`/`onServiceStopped`), см. `JamHost`. После подключения движка `onCreate` следит за `appGraph.qualityInEffect`: каждое новое значение (`drop(1)`) — `QueueController.onFilesChanged(trackLinks::askedInOtherQuality)` на `serviceScope`, то есть на главном потоке, потоке ExoPlayer и контроллера (QUAL-05, «Traps (качество)» ниже). Подписка запускается `UNDISPATCHED`, как и подписка на громкость: `drop(1)` отбрасывает значение, которое действует сразу после `attach()`, ещё внутри `onCreate`, а не то, что будет к первому обороту главного цикла, так что смена качества в этот оборот (`attach()` уже мог запустить восстановленную очередь у самого конца трека) не теряется. Без сервиса плеера нет и подгружать нечего. `attachBaseContext` даёт сервису язык интерфейса (`AppLocale.wrap`), а смена языка во время работы перестраивает кнопки уведомления (см. `ui/README.md`, «Язык интерфейса»).

`SessionCallback.onConnect` строит ответ через `AcceptedResultBuilder(session, controller)`: конструктор без контроллера в Media3 1.11 устарел. Новый конструктор недоверенному контроллеру (не система, не само приложение, без `MEDIA_CONTENT_CONTROL` и без включённого слушателя уведомлений) по умолчанию даёт только команды чтения, поэтому `setAvailablePlayerCommands(ControllerCommands.withoutPlaylistEdits(DEFAULT_PLAYER_COMMANDS))` даёт всем контроллерам, доверенным и нет, все команды плеера, кроме правки плейлиста (`ControllerCommands`, ниже), а `setAvailableSessionCommands` — команды сессии по умолчанию плюс лайк и дизлайк (ниже).

**Traps:**
- С Media3 1.6.0 сервис после паузы, «стоп», ошибки или конца очереди ещё 10 минут остаётся на переднем плане (`MediaSessionService.DEFAULT_FOREGROUND_SERVICE_TIMEOUT_MS = 600_000`; `MediaNotificationManager.shouldRunInForeground` держит его, пока не истёк таймаут после того, как плеер перестал быть `playWhenReady` в `STATE_READY`/`STATE_BUFFERING`). Всё это время `isPlaybackOngoing()` — `true`, и голый `stopSelf()` сервис не останавливает (так в javadoc `isPlaybackOngoing`); `pauseAllPlayersAndStopSelf()` сначала снимает таймаут. Поэтому `onTaskRemoved` зовёт его, а не `stopSelf()`.
- Уведомление плеера, который ушёл в `STATE_IDLE` после «стоп» или ошибки, с Media3 1.6.0 остаётся (`SHOW_NOTIFICATION_FOR_IDLE_PLAYER_AFTER_STOP_OR_ERROR` по умолчанию; в 1.4.1 оно пропадало сразу). Плеер с треками, который ни разу не готовился (`prepare`), уведомления не показывает, как и раньше.
- Media3 1.11 проверяет поток у методов сессии (`MediaSession.getPlayer` и других) и на чужом потоке бросает `IllegalStateException`. Сервис зовёт их только на главном: `onConnect`, `onTaskRemoved`, `onDestroy` и `serviceScope` (`MainScope`).

## Один хозяин плеера

У плеера один хозяин — `QueueController` из `AppGraph` (вариант «синглтон» из Kickoman/QiYaa-android#6; приложение однопроцессное, поэтому очередь не сериализуется в команды и `sessionExtras` сессии). Все пути к плееру сходятся в нём:

| Откуда | Путь |
|---|---|
| Кнопки приложения | `ui/PlayerViewModel` → `MediaController` → `MediaSession` → `QueueForwardingPlayer` → `QueueController.next()`/`previous()`; SHF и RPT — `QueueController.setShuffle()`/`setRepeat()` напрямую |
| Уведомление, экран блокировки, гарнитура, Bluetooth | `MediaSession` → `QueueForwardingPlayer` → `QueueController`: «вперёд», «назад», shuffle, повтор |
| Выбор источника, правка очереди, лайки | `ui/AppViewModel` → `QueueController` напрямую |
| Выбор строки (плейлист, очередь Android Auto, любой контроллер сессии) | `MediaController.seekTo(i, 0)` → `MediaSession` → ExoPlayer, мимо `QueueForwardingPlayer` → `onMediaItemTransition` → `QueueController.onItemChanged`, который собирает ждущие элементы за новой строкой (HOST-12, `queue/README.md`) |
| Правка плейлиста извне (другое приложение, Bluetooth, часы, Assistant) | запрещена: ни у одного контроллера нет `COMMAND_CHANGE_MEDIA_ITEMS`, `COMMAND_SET_MEDIA_ITEM`, `COMMAND_SET_PLAYLIST_METADATA`; плейлист ExoPlayer меняют только `Media3Engine` и возобновление сессии |
| События ExoPlayer | `Media3Engine` (листенер) → `QueueController` |

Сервис может пересоздаваться при живом процессе (смахнули из недавних → `onTaskRemoved` → `pauseAllPlayersAndStopSelf`, потом приложение открыли снова). `onDestroy` отключает движок, и контроллер запоминает трек и позицию; новый `Media3Engine` получает ту же очередь на паузе в том же месте. Источник, выбранный, пока сервис ещё не поднялся, применяется, как только движок подключится. После выгрузки процесса очередь восстанавливает сам `QueueController` из `data/QueueFile` (см. `queue/README.md`), и новый сервис при `attach` получает её на паузе в том же месте.

## «Играть» после выгрузки процесса

Кнопка гарнитуры или карточка возобновления в системе доходят до приложения через `androidx.media3.session.MediaButtonReceiver` в манифесте (`exported`, `android.intent.action.MEDIA_BUTTON`). Он поднимает `PlaybackService`, `onCreate` подключает движок, и очередь уже стоит в плеере. Если плеер всё же пуст, Media3 вызывает `MediaSession.Callback.onPlaybackResumption(session, controller, isForPlayback)` (вариант без `isForPlayback` в Media3 1.11 устарел; у `MediaSession` `isForPlayback` всегда `true`, `false` бывает только у `MediaLibrarySession`, и ответ от него не зависит): `SessionCallback` отдаёт треки, индекс и позицию из `QueueController.resumePoint()`, а при пустой очереди — неудачный `Future`, и команда ничего не делает. Эти треки сессия ставит в ExoPlayer мимо `Media3Engine`; `HeadShuffleOrder`, поставленный при `attach`, делает из них случайный проход, и все они — голова. Возобновлению нужны `COMMAND_SET_MEDIA_ITEM` или `COMMAND_CHANGE_MEDIA_ITEMS` у плеера сессии, а у нажавшего «плей» контроллера — только `COMMAND_PLAY_PAUSE` (Media3 1.11.1, `MediaSessionImpl.handleMediaControllerPlayRequestInternal`, сверено по исходникам, на устройстве не проверялось); поэтому `ControllerCommands` убирает правку у контроллеров, а не у плеера.

## Лайк и дизлайк в уведомлении

```kotlin
object NotificationButtons {
    const val ACTION_LIKE = "io.github.kickoman.qiyaa.LIKE";  const val ACTION_DISLIKE = "io.github.kickoman.qiyaa.DISLIKE"
    fun withCustomCommands(commands: SessionCommands): SessionCommands
    fun layout(context: Context, liked: Boolean): List<CommandButton>   // [♥ залитое или пустое, 👎]
}
```

Две пользовательские команды сессии без аргументов (`Bundle.EMPTY`). `SessionCallback.onConnect` добавляет их к `DEFAULT_SESSION_COMMANDS` каждому контроллеру (уведомление, экран блокировки, `ui/PlayerViewModel`) и отдаёт текущую раскладку. `onCustomCommand` передаёт `ACTION_LIKE` в `QueueController.likeCurrent()`, `ACTION_DISLIKE` — в `dislikeCurrent()`; сам трек выбирает очередь, поэтому дизлайк ведёт себя как кнопка на экране плеера (TR-07, TRK-07: запрос, `skip` в фидбек волны, «вперёд»). Незнакомая команда — `ERROR_NOT_SUPPORTED`.

Состояние ♥: сервис держит `mediaId` текущего трека (листенер `onMediaItemTransition`) и объединяет его с `Library.likedIds`; при изменении вызывает `MediaSession.setCustomLayout`. Так ♥ меняется при смене трека, при лайке из шторки и при лайке с экрана плеера. Экран плеера читает те же `likedIds`, поэтому лайк из шторки виден там сразу после ответа сервера.

Значки — встроенные `CommandButton.ICON_HEART_FILLED`/`ICON_HEART_UNFILLED` и `ICON_THUMB_DOWN_UNFILLED`. Подписи (для TalkBack) — строки `notification_like`, `notification_unlike`, `notification_dislike` из `res/values*/strings.xml`: сервис — точка входа Android и берёт ресурсы, как и иконку уведомления; событий и текста для тостов пакет по-прежнему не производит.

Где стоят кнопки, решает система: в развёрнутом уведомлении — после «назад», «плей», «вперёд»; в медиапанели Android 13+ и на экране блокировки — в двух свободных слотах. Media3 1.11.1 переводит `setCustomLayout` в media button preferences (`CommandButton.getMediaButtonPreferencesFromCustomLayout`): пока «назад» и «вперёд» доступны, а `QueueForwardingPlayer` при непустой очереди добавляет их всегда, ♥ и 👎 получают слот `SLOT_OVERFLOW` и в компактный вид уведомления не попадают. `setCustomLayout` в 1.11.1 не устарел, только помечен «будет устаревшим» в пользу `setMediaButtonPreferences`.

**Traps:**
- `CommandButton.Builder(icon)` и значки `ICON_*` стабильны с Media3 1.6.0 (в 1.4.1 были `@UnstableApi`), поэтому `NotificationButtons` больше не помечен `@UnstableApi`. Устарели `CommandButton.Builder()` без значка и `setIconResId`: их не брать.
- Команда, которой нет в `setAvailableSessionCommands`, не доходит до `onCustomCommand`, а кнопка с ней не показывается.

## Обложка в уведомлении

```kotlin
@UnstableApi
class CoverBitmapLoader(context: Context, images: ImageLoader, scope: CoroutineScope) : BitmapLoader {
    override fun supportsMimeType(mimeType: String): Boolean    // Util.isBitmapFactorySupportedMimeType, как у загрузчика Media3
    override fun decodeBitmap(data: ByteArray): ListenableFuture<Bitmap>
    override fun loadBitmap(uri: Uri): ListenableFuture<Bitmap>
    companion object { const val MAX_DECODED_SIDE_PX = 1024 }
}
```

Обложку уведомления, экрана блокировки, медиапанели системы и Bluetooth Media3 грузит загрузчиком картинок сессии по `MediaMetadata.artworkUri` (= `coverUrl`, `MediaItems`). Сервис ставит его сам: `MediaSession.Builder.setBitmapLoader(CoverBitmapLoader(this, SingletonImageLoader.get(this), serviceScope))`. Это тот же `ImageLoader` Coil, что рисует обложку на экране плеера, с тем же дисковым кэшем (`ui/README.md`, «Дисковый кэш обложек»). Ключ записи в нём — URL, а `loadBitmap` отдаёт Coil `uri.toString()`, то есть ту же строку `coverUrl`, что и экран. Поэтому обложка, которую видел экран, есть и у уведомления, в том числе без сети после перезапуска. Без своего загрузчика Media3 1.11.1 берёт `DataSourceBitmapLoader` над `DefaultDataSource` (`MediaSession.java:2847–2865`): он качает каждую обложку заново, на диск её не кладёт, и после перезапуска без сети уведомление оставалось без обложки.

Запрос — `ImageRequest.Builder(context).data(data).size(1024).precision(Precision.INEXACT).allowHardware(false)`, `ImageLoader.execute` внутри `scope.future(Dispatchers.Default)` (`kotlinx-coroutines-guava`). Сверено по исходникам Coil 3.6.3 и Media3 1.11.1; на устройстве не проверялось (Kickoman/QiYaa-android#91).
- **`allowHardware(false)`.** Coil с API 26 по умолчанию декодирует в `Bitmap.Config.HARDWARE`, картинку в памяти GPU (`utils.android.kt:82–86`). Media3 оборачивает загрузчик сессии в `SizeLimitedBitmapLoader(…, makeShared = true)` и `CacheBitmapLoader` (`MediaSession.java:2857–2864`), а `DefaultMediaNotificationProvider` — ещё раз в свои (`DefaultMediaNotificationProvider.java:341–349`): каждая обложка масштабируется, копируется в общую память (`Bitmap.asShared()` на API 31+, `BitmapUtil.java:112–113`) и уходит в другие процессы. Аппаратной картинке для этого пришлось бы читать пиксели обратно из GPU (AOSP `Bitmap.createAshmemBitmap`, «very slow operation»). Загрузчик Media3 по умолчанию тоже декодирует в обычную память. Аппаратную картинку, которую экран оставил в кэше памяти, Coil такому запросу не отдаёт (`MemoryCacheService.kt:90–91`) и декодирует файл с диска заново. Ключ кэша памяти у обоих запросов — один URL, потому что преобразований нет (`MemoryCacheService.kt:60–66`), так что обычная картинка уведомления ложится поверх аппаратной записи экрана (`:221`), и экран дальше рисует её. Это безвредно: около 640 КБ кучи на обложку 400×400.
- **`size(1024)` и `Precision.INEXACT`.** Запрос без цели и без размера декодирует в исходном размере (`SizeResolver.ORIGINAL`, `ImageRequest.kt:227`). С размером и точностью по умолчанию (`Precision.EXACT`, `ImageRequest.kt:229`) Coil растянул бы обложку 400×400 до 1024×1024 (около 4 МБ вместо 640 КБ), и только потом Media3 уменьшил бы её до своего предела. `INEXACT` не даёт увеличивать (`BitmapFactoryDecoder.kt:155–156`, `StaticImageDecoder.kt:70–73`): обложка 400×400 остаётся 400×400, а встроенная картинка больше 1024 точек уменьшается к 1024. Окончательный размер ставит Media3: `config_mediaMetadataBitmapMaxSize` системы, до API 27 — не меньше 320 dp (`MediaSessionImpl.java:2418–2452`).
- **`Dispatchers.Default`.** `SizeLimitedBitmapLoader` масштабирует и копирует на потоке, который завершил future (`directExecutor`, `SizeLimitedBitmapLoader.java:62–96`); на `serviceScope` без диспетчера это был бы главный поток. Ответ вызывающие Media3 всё равно передают на поток приложения (`DefaultMediaNotificationProvider.java:373`, `MediaSessionLegacyStub.java:1662`, `:1822`).
- **Неудача** — неудачный future с `IOException("The cover <url> did not load", причина Coil)`. Media3 пишет предупреждение в logcat и показывает уведомление без обложки, как и раньше без сети. `serviceScope` — `MainScope()` с `SupervisorJob`, поэтому упавшая загрузка роняет только свой future, а отмена future отменяет запрос Coil. `onDestroy` отменяет `serviceScope`, а с ним и незаконченные загрузки.

Встроенная картинка файла (ID3 `APIC`) до уведомления не доходит, когда у трека есть `coverUrl`. `ExoPlayer.getMediaMetadata()` кладёт метаданные элемента поверх метаданных файла (`ExoPlayerImpl.java:2971–2979`), а `MediaMetadata.Builder.populate` с непустым `artworkUri` ставит и `artworkData` элемента, то есть `null` (`MediaMetadata.java:570–573`). `BitmapLoader.loadBitmapFromMetadata` берёт `artworkData`, только если он есть (`common/util/BitmapLoader.java:47–57`), поэтому `decodeBitmap` зовётся лишь для трека без обложки в API, файл которого несёт картинку.

**Traps:**
- `CacheBitmapLoader` Media3 помнит последний запрос вместе с его future, даже неудачным или отменённым (`CacheBitmapLoader.java:70–90`). Обложка, которая не загрузилась без сети, не появится в уведомлении до смены трека, даже когда сеть вернётся. Загрузчик по умолчанию ведёт себя так же.
- Без `allowHardware(false)` в уведомление шли бы аппаратные картинки (выше). Без `precision(Precision.INEXACT)` `size(1024)` растягивает каждую обложку.
- Общий кэш держится на одиночке: загрузчик со своим `ImageLoader` (или `ImageLoader.Builder` без `SingletonImageLoader`) завёл бы второй кэш памяти, а с другим `diskCache` — и второй дисковый (`ui/README.md`, «Traps (Coil)»).

## `QueueForwardingPlayer`

`ForwardingPlayer` над ExoPlayer: `seekToNext`/`seekToNextMediaItem` → `QueueController.next()`, `seekToPrevious`/`seekToPreviousMediaItem` → `previous()`, `setShuffleModeEnabled(on)` → `setShuffle(on)`, `setRepeatMode(mode)` → `setRepeat(mode != REPEAT_MODE_OFF)`. Всё остальное (play, pause, seek по позиции и по строке, громкость) уходит в ExoPlayer как есть. `seekTo(index, …)` и `seekToDefaultPosition(index)` не перехватываются: переход на строку и так приходит в контроллер через `onMediaItemTransition`, а ждущие элементы джема собирает `onItemChanged` (второе ревью плана QiYaa-android#80, примечание 5). Режимы ExoPlayer ставит только контроллер (`queue/README.md`).

**Отклонённый выбор публикуется заново.** Если после `setShuffle`/`setRepeat` режим ExoPlayer не равен запрошенному, ExoPlayer события не даёт, и контроллер сессии (уведомление, Bluetooth) остался бы со своим замаскированным значением. Так бывает, когда выбор отклонён (волна, станция), когда повтор выбран, но в ExoPlayer не включён (курсор в продолжении — CONT-11 — или голову с продолжением за ней заворачивает сам контроллер — CONT-10, `queue/README.md`), или когда запрошен `REPEAT_MODE_ONE`: повтор бывает только всей очереди (TR-06), и действует `REPEAT_MODE_ALL`. Тогда `QueueForwardingPlayer` сам зовёт `onShuffleModeEnabledChanged`/`onRepeatModeChanged` с действующим значением у всех слушателей сессии. `MediaSessionImpl.PlayerListener` в Media3 1.11.1 на каждый такой вызов обновляет `PlayerInfo` и рассылает его контроллерам, не сравнивая со старым значением (сверено по исходникам `onShuffleModeEnabledChanged`/`onRepeatModeChanged`, так же было в 1.4.1; на устройстве не проверялось); рассылка асинхронная и склеивается в одно сообщение за проход лупера. Старые контроллеры платформенной `MediaSessionCompat` получают режим, только если он изменился: `MediaSessionCompat.setRepeatMode`/`setShuffleMode` сравнивают со старым. Внешние контроллеры поэтому видят режим, который действует в ExoPlayer; экран приложения показывает выбор пользователя (`QueueController.modes`). При завороте головы контроллером это значит, что Bluetooth и уведомление показывают повтор выключенным, хотя голова повторяется; нажатие «повтор» там снова включает выбор, ничего не меняет и снова публикует «выключено».

`getAvailableCommands` добавляет `COMMAND_SEEK_TO_NEXT(_MEDIA_ITEM)` и `COMMAND_SEEK_TO_PREVIOUS(_MEDIA_ITEM)`, когда в очереди есть треки: сам ExoPlayer убирает «вперёд» на последнем треке, и тогда сессия отбросила бы команду, а в конце волны она значит «догрузить» (WAVE-09), а в конце конечной очереди — «стоп» (TR-04).

**Traps:**
- `MediaSession` берёт набор команд и из `getAvailableCommands`, и из события `onAvailableCommandsChanged`; поэтому листенеры оборачиваются (`TransportCommandsListener`), и событие несёт тот же расширенный набор.
- `TransportCommandsListener` пересылает каждый из 37 методов `Player.Listener` явно, включая устаревшие (`@Suppress("OVERRIDE_DEPRECATION", "DEPRECATION")`: их пересылает и `ForwardingListener` из Media3). Делегирование Kotlin `Player.Listener by listener` не годится: для default-методов Java-интерфейса Kotlin пересылку не генерирует, а в `Player.Listener` все методы такие. Так было в v0.2.0: сессия получала только смену команд, и контроллеры (экран плеера, уведомление Media3, экран блокировки) навсегда оставались со снимком состояния на момент подключения — не шёл прогресс и спектр, не появлялось уведомление, сервис не уходил в foreground и умирал при выходе из приложения. `playback/QueueForwardingPlayerTest` сверяет доставку каждого события с обычным `ForwardingPlayer`; новый метод слушателя в Media3 уронит этот тест, пока его не перешлют.
- `Media3Engine` управляет самим ExoPlayer, а не `QueueForwardingPlayer`: иначе `QueueController.next()` → `skipToNext()` вернулся бы в `next()`, а `applyModes()` — в `setShuffle()`.

## `ControllerCommands`

```kotlin
@UnstableApi
object ControllerCommands {
    val PLAYLIST_EDITS: List<Int>   // COMMAND_CHANGE_MEDIA_ITEMS, COMMAND_SET_MEDIA_ITEM, COMMAND_SET_PLAYLIST_METADATA
    fun withoutPlaylistEdits(commands: Player.Commands): Player.Commands   // commands без PLAYLIST_EDITS
}
```

Команды плеера, которые `SessionCallback.onConnect` отдаёт каждому контроллеру сессии: `DEFAULT_PLAYER_COMMANDS` (все команды, `addAllCommands()`) без трёх команд правки плейлиста (Kickoman/QiYaa-android#101). Плейлист ExoPlayer меняет только `Media3Engine` по командам `QueueController`: правка извне разошлась бы с очередью (голова и продолжение, ждущие элементы джема, `queue.json`, отчёты хозяина гостям) и с копией порядка shuffle в `Media3Engine` (`HeadShuffleOrder`, ловушка про `cloneAndMove`). Остальные команды контроллеры получают, как раньше. `QueueForwardingPlayer` и ExoPlayer эти три команды сохраняют: по ним работает возобновление («Играть» после выгрузки процесса).

Сессия проверяет команду контроллера по пересечению его ответа `onConnect` с `getAvailableCommands()` плеера (`ConnectedControllersManager.isPlayerCommandAvailable`). Без трёх команд в ответе (Media3 1.11.1, сверено по исходникам, на устройстве не проверялось):
- `MediaController` Media3 (например, в другом приложении) видит их недоступными, и `setMediaItem(s)`, `addMediaItems`, `removeMediaItems`, `moveMediaItems`, `replaceMediaItems`, `clearMediaItems` и `setPlaylistMetadata` ничего не отправляют (`MediaControllerImplBase`); вызов в обход него получает `ERROR_PERMISSION_DENIED` (`MediaSessionStub`).
- Платформенная сессия (System UI, Bluetooth, часы, Assistant, любой `MediaControllerCompat`; каждый её контроллер тоже проходит `onConnect`) молча отбрасывает `addQueueItem`, `removeQueueItem`, `playFrom*` и `prepareFrom*` (`MediaSessionLegacyStub`). Раньше из них работало только удаление по `mediaId`: элемент из `addQueueItem` и `playFrom*` несёт `mediaId` и `requestMetadata` (у `playFromSearch` — ещё запрос и `extras`), но без `localConfiguration`, и `onAddMediaItems` по умолчанию его отвергал (`MediaSession.java:1958–1966`).
- Из действий платформенной сессии пропадают `ACTION_PLAY_FROM_MEDIA_ID`/`SEARCH`/`URI` и `ACTION_PREPARE_FROM_MEDIA_ID`/`SEARCH`/`URI`: действия — пересечение команд контроллера уведомления Media3 с командами плеера, а эти шесть даёт `COMMAND_SET_MEDIA_ITEM`. Пропадают они, когда подключится контроллер уведомления: до того платформенная сессия начинает с `DEFAULT_PLAYER_COMMANDS` (`MediaSessionImpl`) и их рекламирует, но вызовы всё равно отбрасываются — у каждого контроллера свой ответ `onConnect`.
- Переход на строку (`seekTo(i, …)`, платформенный `skipToQueueItem`), сама очередь в платформенной сессии и транспорт (play, pause, «вперёд», «назад», перемотка) остаются.

**Traps:**
- Эти команды не убирать у `QueueForwardingPlayer`: возобновление смотрит на команды плеера, а не контроллера. Без `COMMAND_SET_MEDIA_ITEM` и `COMMAND_CHANGE_MEDIA_ITEMS` оно не запускается, а без одной `COMMAND_CHANGE_MEDIA_ITEMS` ставит только первый трек (`MediaUtils.setMediaItemsWithStartIndexAndPosition`).
- `FLAG_HANDLES_QUEUE_COMMANDS` у платформенной сессии остаётся: Media3 берёт его из команд плеера, а не контроллера (`MediaSessionLegacyStub.maybeUpdateFlags`). Старые контроллеры поэтому видят очередь изменяемой, а их правка молча отбрасывается. Снять флаг можно, только убрав `COMMAND_CHANGE_MEDIA_ITEMS` у плеера (ловушка выше).
- `DEFAULT_PLAYER_COMMANDS` — это `addAllCommands()`, поэтому новая команда следующей версии Media3 сама дойдёт до контроллеров. `ControllerCommandsTest` сверяет все константы `COMMAND_*` в `Player` с известными 1…35 и падает на новой, пока её не отнесут к правке плейлиста или нет.
- Запрет живёт только в ответе `onConnect`: `Callback.onPlayerCommandRequest` устарел, а предупреждения — ошибки сборки, и `@Suppress` нельзя.
- Собранный `Player.Commands` на JVM не проверить (`app/src/test/README.md`), поэтому тест сверяет список `PLAYLIST_EDITS`; ответ `onConnect` и действия платформенной сессии проверяются на устройстве (Kickoman/QiYaa-android#91).

## `Media3Engine`

```kotlin
@OptIn(UnstableApi::class)
class Media3Engine(player: ExoPlayer, controller: QueueController, random: Random = Random.Default,
    onAudioFailure: (AudioFailure) -> Unit = {}) : PlayerEngine {
    fun attach()     // addListener + HeadShuffleOrder на пустой плеер + controller.attach(this)
    fun detach()
}
```

Тонкий: ни одного решения, только перевод. Команды `PlayerEngine` → вызовы `ExoPlayer` (`setTracks` = заранее поставленный проход (см. `HeadShuffleOrder`) + `setMediaItems(…, startIndex, startPositionMs)` + `prepare()` + `playWhenReady`; `shuffleHead(head, lead)` = `setShuffleOrder(HeadShuffleOrder(HeadShuffle.pass(head, mediaItemCount, lead)))`; `appendTracks` = `addMediaItems(mediaItemCount, …)`, порядок ExoPlayer клонирует сам (`HeadShuffle.inserted`); `insertTracks(i, …)` = заранее поставленный порядок со вставкой за соседом (`staging(…, at = i)`, `HeadShuffle.insertedAfter`) + `addMediaItems(i, …)`, текущий трек и буфер не трогаются; `removeAt` = `removeMediaItem` (см. ловушку про текущий трек); `reload(i)` = заранее поставленный порядок замены (`HeadShuffleOrder.replacing`) + `replaceMediaItem(i, …)` с URI новой ревизии (ниже, «Загрузить элемент заново»); `clear` = `clearMediaItems`; `seekTo(i)` = `seekTo(i, 0)`; `seekToPosition` = `seekTo(ms)`; `skipToNext`/`skipToPrevious` = `seekToNext/PreviousMediaItem`; `pauseAtEndOfCurrent` = `pauseAtEndOfMediaItems`). Движок держит копию порядка ExoPlayer (`order: HeadShuffle`) и меняет её до каждого вызова плеера так же, как ExoPlayer меняет свой: `HeadShuffleOrder` клонируется детерминированно. Вставка в пустой плеер ставит свой порядок заранее, как `setTracks`, иначе ExoPlayer сделал бы случайный проход, которого копия не знает. `insertTracks` ставит его всегда: сам ExoPlayer клонирует порядок детерминированно, но кладёт вставленные треки в остаток по возрастанию, а не в проход за соседом. События `Player.Listener` → методы контроллера:

| Событие ExoPlayer | Вызов |
|---|---|
| `onMediaItemTransition(item, reason)` | `onItemChanged(MediaItems.toTrack(item), transition, player.isPlaying)`; причина: `AUTO` → `AUTO`, `REPEAT` → `REPEAT`, `SEEK` → `SEEK`, остальное (`PLAYLIST_CHANGED`) → `NEW_QUEUE` |
| `onPlaybackStateChanged(STATE_ENDED)` | `onEnded()` |
| `onPositionDiscontinuity(old, new, reason)` | `onSeeked()`, только при `DISCONTINUITY_REASON_SEEK` и одном `mediaItemIndex` у `old` и `new`; перемотка на другой элемент приходит как `onMediaItemTransition(SEEK)`. `seekToPrevious/NextMediaItem` на тот же элемент (повтор текущего, `repeatCurrentMediaItem` в Media3) даёт и `onSeeked()`, и сразу за ним `onMediaItemTransition(SEEK)` — это безвредно (вне джема лишнее сохранение, в джеме повтор выключен), так что фильтр «тот же элемент» остаётся как есть |
| `onIsPlayingChanged(playing)` | `onPlayingChanged(playing)` |
| `onPlayWhenReadyChanged(false, PLAY_WHEN_READY_CHANGE_REASON_END_OF_MEDIA_ITEM)` | `onPausedAtEnd()`: ExoPlayer встал на паузу в конце трека, потому что включён `pauseAtEndOfMediaItems` (заворот головы, CONT-10) |
| `onPlayerError(error)` | `Log.w("QiYaa", …, error)`, затем `onAudioFailure(it)`, если `PlaybackFailures.audioFailure(error.errorCode)` не `null`, затем `onFailure(PlaybackFailures.classify(error.errorCode, error.cause), PlaybackFailures.errorKind(error.errorCode, error.cause))` |

`onShuffleModeEnabledChanged` и `onRepeatModeChanged` не пересылаются: режимы ExoPlayer пишет только контроллер (`shuffleEnabled` = `shuffleModeEnabled`, `repeatEnabled = true` — это `REPEAT_MODE_ALL`: повтора одного трека нет, TR-06), а выбор пользователя приходит командами через `QueueForwardingPlayer`.

`playOrder()` обходит `currentTimeline` через `getFirstWindowIndex`/`getNextWindowIndex(…, REPEAT_MODE_OFF, shuffle)`.

**Загрузить элемент заново** (`reload(i)`, QUAL-05). Нужно, когда ExoPlayer уже начал грузить следующий трек в старом качестве: элемент заменяется своей копией с другим URI, ExoPlayer бросает загруженное и грузит элемент с нуля, а плейлист, порядок, текущий трек и курсор остаются. `reload(i)` ничего не делает, если `i` вне плейлиста, равен `currentMediaItemIndex` или URI элемента не `qiyaa://track/…`. Иначе копия порядка берёт длину плеера (`fitted`), затем `setShuffleOrder(HeadShuffleOrder.replacing(order, mediaItemCount, i, random))`, строка в logcat `Reloading track <id> at <i> as revision <n>` (тег `QiYaa`, debug: так в logcat видно, что следующая подпись этого трека — от `reload`, а не повтор) и `replaceMediaItem(i, MediaItems.revised(item, id, n))`. `n` — счётчик движка, с 1: новый URI всегда отличается от нынешнего, в том числе после пересоздания сервиса, потому что заново поставленные элементы ревизии не несут. Копия `order` после замены не меняется: ExoPlayer приходит ровно к ней (`HeadShuffleOrder`, «Замена элемента»).

Путь в Media3 1.11.1 (сверено по исходникам; на устройстве не проверялось, Kickoman/QiYaa-android#91):
- `BasePlayer.replaceMediaItem(i, item)` = `replaceMediaItems(i, i + 1, [item])` (`BasePlayer.java:81–84`). `ExoPlayerImpl.replaceMediaItems` (`ExoPlayerImpl.java:790–823`) сначала спрашивает `canUpdateMediaSourcesWithMediaItems` (`:3187`): `ProgressiveMediaSource.canUpdateMediaItem` сравнивает URI, `imageDurationMs` и `customCacheKey` (`ProgressiveMediaSource.java:387–394`), `MaskingMediaSource` (`:81`) и `WrappingMediaSource` (`:111`) отдают вопрос ему. С тем же URI элемент обновляется на месте вместе с загруженным периодом, и заново ничего не грузится; поэтому URI другой.
- С другим URI — `addMediaSourcesInternal(i + 1)` → `cloneAndInsert(i + 1, 1)` (`:2699`), затем `removeMediaItemsInternal(i, i + 1)` → `cloneAndRemove(i, i + 1)` (`:2759`) и один `updatePlaybackInfo`. Поток воспроизведения хранит порядки, которые ему передали, и сам их не клонирует (`MediaSourceList.java:147–150`, `197–199`).
- На потоке воспроизведения `handleMediaSourceListInfoRefreshed` (`ExoPlayerImplInternal.java:2589`) оставляет играющий период: окно текущего элемента то же. `MediaPeriodQueue.updateQueuedPeriods` (`MediaPeriodQueue.java:653`) за играющим периодом ждёт период нового элемента с новым uid, не находит его (`canKeepMediaPeriodHolder`, `:1052`) и зовёт `removeAfter` (`:679`, `:553`): освобождаются подгруженный период и все после него. Отменённая загрузка прерывает свой поток (`Loader.java:420–428`): подпись, которая ещё шла в старом качестве, обрывается (`runBlocking` отменяет корутину) и запись кэша не пишет, а успевшая запись старого качества просто не подходит новому старту. `maybeUpdateLoadingPeriod` (`ExoPlayerImplInternal.java:2769`) создаёт период нового элемента с позиции 0. У нового периода свой источник данных и свой `TrackResolver`, поэтому его первое открытие — новый старт в действующем качестве («Одна игра — один источник» ниже). Так же и периоды за ним, которые создаются заново со своими старыми URI: ссылка действующего качества берётся из кэша или подписывается, а ссылки, по которым читает играющий период, остаются.
- `Util.inferContentType` смотрит на последний сегмент пути (`Util.java:3051`), поэтому `?r=` оставляет элемент прогрессивным источником. `customCacheKey` нет, а ключ дискового кэша — у игры (`PlaybackCache`): заново созданный период — новый ключ, и его первое открытие идёт в сеть через `TrackUrlCache.get`.
- Событий нет: окно текущего элемента то же — нет `onMediaItemTransition` (`ExoPlayerImpl.evaluateMediaItemTransitionReason`, `:2553`); играющий период тот же — нет разрыва позиции (`:813–814`); `onTimelineChanged` движок не пересылает. Исключение — последние 1–2 с трека, когда рендереры уже читают следующий период: `removeAfter` сообщает `UPDATE_PERIOD_QUEUE_ALTERED_READING_PERIOD`, и ExoPlayer делает `seekToCurrentPosition(false)` (`ExoPlayerImplInternal.java:2638–2639`). Играющий трек перечитывается со своей позиции из буфера (без сети, тот же файл, короткий сброс звука — щелчок), а `seekToPeriodPosition` переводит `READY` в `BUFFERING` (`:1840–1842`): контроллер получает `onIsPlayingChanged(false)` и потом `(true)`, то есть сохранение, а в джеме — `playing{paused: true}` и сразу `paused: false`, мигание у слушателей. Это та же цена, что у паузы в конце (ловушка выше), и у любой буферизации. Пока стоит `pauseAtEndOfMediaItems`, чтение в следующий период не уходит (`:2925`), и щелчка нет.

**Traps:**
- Все вызовы — с главного потока ExoPlayer; листенеры ExoPlayer срабатывают после завершения команды, так что контроллер видит уже обновлённое состояние.
- **Случайный трек** (SHUF-05, SHUF-06; `queue/README.md`, «Случайный трек»). Контроллер зовёт `shuffleHead` на каждой смене трека головы, в том числе изнутри `onMediaItemTransition`, когда переход сделал сам ExoPlayer, и изнутри `setMediaItems`: `setTracks` ставит проход без вытянутого (`staging` для `cloneAndSet`), а колбэк смены трека из того же `setMediaItems` — проход с вытянутым. Так можно (Media3 1.11.1, сверено по исходникам; на устройстве не проверялось, Kickoman/QiYaa-android#91): `ExoPlayerImpl.setShuffleOrder` (`ExoPlayerImpl.java:826–847`) сверяет длину с `mediaSourceHolderSnapshots` (`:828`), а `mediaItemCount` внутри колбэка уже новый; обновление идёт с `positionDiscontinuity = false`, uid окна тот же, и `evaluateMediaItemTransitionReason` (`:2553–2606`) смены трека не находит, так что новый порядок нового вытягивания не вызывает. События этого вложенного обновления `ListenerSet.flushEvents` (`ListenerSet.java:340–361`) ставит в хвост очереди внешнего вызова и выходит (`:350–356`) — та же повторная входимость, что у сбора ждущих элементов. Сообщение `setShuffleOrder` уходит в поток воспроизведения после сообщений `setMediaItems` и до `prepare()`, так что первый следующий период ExoPlayer строит уже по проходу с вытянутым; `order` движка — тоже он (`setTracks` присваивает `order = pass` до `setMediaItems`, а `shuffleHead` из колбэка — после).
- **Подгруженный следующий сбрасывается**, когда новый порядок меняет следующий трек (выбор алгоритма, SHF, удаление строки головы, новое вытягивание): `setShuffleOrderInternal` (`ExoPlayerImplInternal.java:1129–1133`) → `handleMediaSourceListInfoRefreshed` (`:2589`) → `queue.updateQueuedPeriods` (`:2633`, `MediaPeriodQueue.java:653–717`): период за играющим, у которого теперь другой следующий, удаляется `removeAfter` (`MediaPeriodQueue.java:679`), и ExoPlayer грузит новый. Если чтение уже ушло в удалённый период (последние секунды трека), `seekToCurrentPosition(false)` (`ExoPlayerImplInternal.java:2639`) перематывает на текущую позицию: возможен щелчок, но не чужой трек. На обычной смене трека до этого почти не доходит: следующий период создаётся, только когда загружающийся загружен целиком (`MediaPeriodQueue.shouldLoadNextMediaPeriod`, `MediaPeriodQueue.java:209–215`), а предзагрузка плейлиста выключена (`PreloadConfiguration.DEFAULT`, `ExoPlayer.java:195`; `PlaybackService` её не задаёт), так что, когда тянется новый трек, следующего периода обычно ещё нет. Дело в коротких треках и в «начать заново» в последние секунды трека. Каждая смена порядка — `onTimelineChanged(TIMELINE_CHANGE_REASON_PLAYLIST_CHANGED)` у всех контроллеров сессии (экран, уведомление, Bluetooth, Auto), примерно раз за трек; как это выглядит на голове из 1000+ треков, проверяется на телефоне.
- Пауза в конце трека (Media3 1.11.1, сверено по исходникам `ExoPlayerImplInternal`, так же было в 1.4.1; на устройстве не проверялось): когда играющий период дорендерен и стоит `pendingPauseAtEndOfPeriod`, `doSomeWork` делает `setPlayWhenReadyInternal(false, …, END_OF_MEDIA_ITEM)`, а в `STATE_ENDED` уходит только последний период; следующий период рендерерам не отдаётся. Флаг ставится, когда последний трек головы становится текущим; если чтение к этому моменту уже ушло в следующий период, цена — один `seekToCurrentPosition` (щелчок, не чужой трек). ExoPlayer при этом всё равно подгружает первый трек продолжения (`download-info` и байты) на каждом круге головы. Пока длится пауза, `playWhenReady = false`, и уведомление Media3 на миг считает воспроизведение остановленным; держится ли сервис на переднем плане в фоне с выключенным экраном — проверка на телефоне.
- Удаление текущего элемента (Media3 1.11.1, сверено по исходникам, на устройстве не проверялось): `removeMediaItemsInternal` → `getPeriodPositionUsAfterTimelineChanged` → `ExoPlayerImplInternal.resolveSubsequentPeriod(…, repeatMode, shuffleModeEnabled, …)` по старому таймлайну, то есть следующий элемент старого порядка воспроизведения (с `REPEAT_MODE_ALL` — по кругу), с позиции по умолчанию; без него — первый элемент нового порядка (`getFirstWindowIndex(shuffle)`) и `STATE_ENDED`. С Media3 1.9.1 (androidx/media#2873) конец решает тот же `resolveSubsequentPeriod`, что и внутренний плеер: в 1.4.1 `STATE_ENDED` маскировался, когда удалён хвост, а текущий индекс был последним по индексу, даже если в перемешанном порядке за ним ещё что-то было. Теперь удаление текущей строки, последней по индексу, но не по порядку, переводит ExoPlayer на следующую строку порядка без конца, а удаление последней по порядку, но не по индексу, — заканчивает. Отыгранную строку или `STATE_ENDED` правит контроллер: перемоткой к цели обхода или остановкой в конце (`queue/README.md`, «Удаление текущего трека»); `support/FakeEngine.removeAt` повторяет поведение 1.11.1.
- Граница трека. Главный поток отстаёт от потока воспроизведения на одно сообщение: если `reload` следующего элемента придёт через несколько мс после того, как ExoPlayer на нём уже начал играть, удаление уберёт играющий элемент, ExoPlayer начнёт замену с 0, а контроллер получит второй переход. Это окно есть у любой правки плейлиста; на устройстве не проверялось.
- Предзагрузка плейлиста выключена: `ExoPlayer.PreloadConfiguration` остаётся по умолчанию (`DEFAULT`, `targetPreloadDurationUs = C.TIME_UNSET`, `ExoPlayer.java:195–196`), и вперёд грузится только то, что за играющим периодом. Если её включить, ExoPlayer начнёт грузить и дальние элементы, и правило «заново — только следующий» (`queue/README.md`, QUAL-05) надо будет пересмотреть.
- `ShuffleOrder`, `setShuffleOrder`, `pauseAtEndOfMediaItems` в Media3 1.4.1 и 1.11.1 — `@UnstableApi`: `HeadShuffleOrder` помечен `@UnstableApi`, `Media3Engine` — `@OptIn(UnstableApi::class)` (`androidx.annotation.OptIn`), иначе lint с `warningsAsErrors` падает.
- `onSeeked` опирается на код Media3 1.11.1 (сверено по исходникам `ExoPlayerImpl.seekTo` и `updatePlaybackInfo`, так же было в 1.4.1; на устройстве не проверялось). `seekTo` заканчивается `updatePlaybackInfo(…, DISCONTINUITY_REASON_SEEK)` и `flushEvents()`, поэтому разрыв доходит до листенера внутри самого вызова, уже с новой позицией и без `STATE_ENDED` (перемотка из `READY` или `ENDED` сначала показывает `BUFFERING`); исключение — перемотка из колбэка ExoPlayer, тогда разрыв приходит после остальных событий того же обновления (`ListenerSet.flushEvents` ставит их в хвост очереди). `QueueController` перематывает только из команд сессии, UI и сокета джема, поэтому `support/FakeEngine.seekToPosition` зовёт `onSeeked()` синхронно. `setMediaItems` даёт разрыв с причиной `REMOVE`, повтор после ошибки (`prepare()`) разрыва не даёт, так что `onSeeked` приходит только на перемотку внутри текущего трека: ползунок экрана и уведомления, «назад», перемотка в 0 у «стоп», а также любой `seekTo` на текущий элемент (тап по текущей строке плейлиста, «плей» в конце очереди из одного трека, в том числе из уведомления). Всем им нужно одно и то же: отчёт джему, сохранение позиции и конец ожидания продолжения (`queue/README.md`, «Ждёт продолжения»).

## `HeadShuffleOrder`

```kotlin
@UnstableApi
class HeadShuffleOrder(val shuffle: HeadShuffle, random: Random, val staged: HeadShuffle? = null, val stagedAt: Int = 0) : ShuffleOrder {
    override fun getLength();  getNextIndex(i);  getPreviousIndex(i);  getFirstIndex();  getLastIndex()   // по shuffle.order; C.INDEX_UNSET на концах и в пустом
    override fun cloneAndInsert(at, count);  cloneAndRemove(from, until);  cloneAndClear()               // staged или HeadShuffle.inserted / removed / EMPTY
    override fun cloneAndSet(count, startIndex)                                                           // staged при stagedAt = 0, иначе свежий проход (Media3 1.9+)
    companion object {
        fun staging(installed: HeadShuffle, itemCount: Int, pass: HeadShuffle, random: Random, at: Int = 0): HeadShuffleOrder
        fun fitted(copy: HeadShuffle, itemCount: Int): HeadShuffle                  // copy, если её длина = itemCount, иначе порядок по возрастанию
        fun afterInsert(copy: HeadShuffle, itemCount: Int, index: Int, count: Int): HeadShuffle   // копия после addMediaItems(index, …)
        fun afterSplice(copy: HeadShuffle, itemCount: Int, index: Int, count: Int): HeadShuffle   // то же со вставкой за соседом (insertedAfter)
        fun afterRemove(copy: HeadShuffle, itemCount: Int, index: Int): HeadShuffle               // копия после removeMediaItem(index)
        fun replacing(installed: HeadShuffle, itemCount: Int, index: Int, random: Random): HeadShuffleOrder   // перед replaceMediaItem(index): после замены порядок тот же
    }
}
```

Порядок ExoPlayer для контракта `queue.PlayerEngine`: проход головы, затем остальные индексы по возрастанию (`queue/README.md`, «`PlayerEngine`»). Поиск следующего и предыдущего — O(1) по заранее посчитанным массивам. Клоны детерминированы: вставка в непустой порядок не делает треки головой, удаление сохраняет порядок остальных. Вставка в пустой порядок делает из вставленных треков проход, случайный, если заранее ничего не поставлено. Заранее поставленный порядок (`staged`) `cloneAndInsert(at, count)` возвращает вместо всего этого, если `at == stagedAt` и длина `staged` равна длине порядка плюс `count`, а `cloneAndSet(count, startIndex)` — если `stagedAt == 0` и длина `staged` равна `count`; иначе `cloneAndSet` делает то же, что по умолчанию в Media3: `cloneAndClear().cloneAndInsert(0, count)`, свежий случайный проход. `cloneAndMove` не переопределён (ниже).

**Заранее поставленный порядок** (`staged`, `stagedAt`). `setMediaItems` в `ExoPlayerImpl` (Media3 1.11.1, сверено по исходникам: `setMediaSourcesInternal` → `setMediaSourceHolders` → `shuffleOrder.cloneAndSet(n, startIndex)`, `ExoPlayerImpl.java:2684`) клонирует порядок ровно один раз, до того как листенеры получат `onMediaItemTransition`; `ExoPlayerImplInternal.setMediaSources` → `MediaSourceList.setMediaSources` хранит тот порядок, который ему передали. Поэтому `Media3Engine.setTracks` сначала ставит `staging(…)`: текущий порядок той же длины, что у плеера, с проходом новой очереди в `staged` и `stagedAt = 0`, и `cloneAndSet(n, …)` возвращает именно этот проход. `startIndex` при этом не смотрится: проход уже начинается с того, что выбрал контроллер (`lead`). Контроллер, которому ExoPlayer синхронно сообщает смену трека изнутри `setMediaItems`, уже видит настоящий порядок, а не случайный промежуточный (`onItemChanged` → `playOrder()`). Отдельного `setShuffleOrder` после `setMediaItems` нет. До Media3 1.9 `setMediaItems` звал вместо этого `cloneAndRemove(0, size)` (если плейлист не пуст) и `cloneAndInsert(0, n)`; эти клоны держат `staged` по-прежнему: удаление всего его сохраняет, вставка в 0 той же длины берёт. `addMediaItems(index, …)` в непустой плейлист клонирует порядок ровно один раз, `cloneAndInsert(min(index, size), n)` в `addMediaSourceHolders`, и `MediaSourceList.addMediaSources` хранит переданный порядок; в пустой плейлист он идёт путём `setMediaSources`, то есть `cloneAndSet(n, C.INDEX_UNSET)` (Media3 1.11.1: `addMediaSources` проверяет `playbackInfo.timeline.isEmpty()`). Поэтому `Media3Engine.insertTracks` ставит `staging(…, at = index)` со вставкой за соседом (`afterSplice`), и ExoPlayer берёт её вместо своего клона, а `appendTracks` и `insertTracks` в пустой плеер ставят `staging` с `stagedAt = 0`, который берёт `cloneAndSet`. Какой клон зовёт ExoPlayer, JVM-тест показать не может: `HeadShuffleOrderTest` проверяет каждый клон отдельно, а путь вызова сверен по исходникам Media3 1.11.1 (на устройстве не проверялось).

**Замена элемента** (`replacing`, QUAL-05). `replaceMediaItem(i, …)` с другим URI клонирует порядок дважды: `cloneAndInsert(i + 1, 1)`, затем `cloneAndRemove(i, i + 1)` (`Media3Engine`, «Загрузить элемент заново»). Сам `cloneAndInsert` положил бы новый индекс в остаток, и с shuffle следующим стал бы другой трек. `replacing(installed, itemCount, i, random)` — это `staging(fitted(installed, itemCount), itemCount, S, random, at = i + 1)`, где `S = fitted(…).insertedAfter(i + 1, 1)`: новый индекс `i + 1` стоит в порядке сразу за `i`, в проходе головы или в остатке. Вставка берёт `S`, удаление убирает `i` и сдвигает `i + 1` на его место, и получается ровно поставленный порядок (`HeadShuffleOrderTest` проверяет каждый индекс прохода и остатка). Между двумя клонами (поток воспроизведения может сделать шаг между сообщениями) за текущим треком по-прежнему стоит старый следующий, в том числе на завороте к первому, а за ним — новый элемент: чужой трек следующим не становится ни на миг. Если старый следующий уже скачан целиком, ExoPlayer в этот миг может начать грузить новый элемент за ним: это подпись того же трека в новом качестве, и удаление тут же сбрасывает период, а ссылка остаётся в кэше. `stagedAt = i + 1 ≥ 1`, поэтому `cloneAndSet` (берёт только `stagedAt == 0`) этот порядок не возьмёт; на деле замена тратит его в том же вызове: URI всегда другой, а плейлист не пуст.

**Traps:**
- `ExoPlayerImpl.setShuffleOrder` требует `getLength() == mediaItemCount` (`checkArgument`). Порядок, который ставится перед `setMediaItems`, берёт длину у плеера, а не у копии в `Media3Engine`: возобновление сессии (`onPlaybackResumption`) ставит треки в ExoPlayer мимо копии; контроллерам сессии правка плейлиста не разрешена (`ControllerCommands`). При расхождении `staging` ставит порядок по возрастанию длины плеера. Расхождение той же длины так не видно, и `insertTracks` и `reload` ставят копию движка поверх настоящего порядка ExoPlayer: если плейлист изменили мимо `Media3Engine`, не меняя длины (`onPlaybackResumption`, который ставит треки в пустой плеер: копия тогда — `fitted(EMPTY, n)`, порядок по возрастанию, а у ExoPlayer — случайный проход `cloneAndSet`; `moveMediaItem` контроллерам сессии не разрешён, ловушка про `cloneAndMove` ниже), то с включённым shuffle вставка или загрузка заново молча меняет порядок воспроизведения ExoPlayer, колбэка об этом нет, и флаг паузы `applyModes` не пересчитывается.
- Вставка и удаление в `Media3Engine` меняют копию через `afterInsert`/`afterRemove`, а не прямо через `HeadShuffle.inserted`/`removed`: те требуют индекс внутри длины, а ExoPlayer (`addMediaItems`, `removeMediaItems`) индекс за концом прижимает к концу и удаление за концом пропускает. После возобновления (та же причина) копия может не совпасть с плейлистом по длине, и удаление последней строки в приложении иначе уронило бы сервис. Обе функции сначала берут длину у плеера (`fitted`), как `staging`.
- Ключ поставленного порядка — индекс, уже прижатый к длине плейлиста: ExoPlayer прижимает индекс `addMediaItems` до `cloneAndInsert`, и неприжатый ключ молча потерял бы вставку за соседом. `Media3Engine.insertTracks` прижимает индекс один раз и отдаёт его и `afterSplice`, и `staging`, и `addMediaItems`.
- Поставленный порядок используется один раз: порядок, который вернули `cloneAndInsert` или `cloneAndSet`, его уже не несёт, и любой клон, кроме удаления всего, его отбрасывает. Иначе следующий `setMediaItems` той же длины (например, сессии при возобновлении) получил бы старый проход, а не свежий.
- `cloneAndClear` даёт пустой порядок без `staged`. `MediaSourceList.setShuffleOrder` зовёт его только при несовпадении длины, а его исключает проверка выше; `cloneAndSet` по умолчанию тоже начинается с `cloneAndClear`, поэтому без переопределения каждый `setMediaItems` в Media3 1.9+ получал бы случайный проход (CONT-09).
- `cloneAndMove` не переопределён. В Media3 1.11.1 его зовёт `moveMediaItems`, а по умолчанию он возвращает тот же порядок (`return this`): перестановка той же длины, но уже не по контракту `PlayerEngine`, и копия в `Media3Engine` с ней разойдётся. Так же было в 1.4.1, где `moveMediaItems` порядок вовсе не трогал. Приложение `moveMediaItems` не зовёт, а контроллеры сессии не могут: `COMMAND_CHANGE_MEDIA_ITEMS` им не выдаётся (`ControllerCommands`, Kickoman/QiYaa-android#101), а у платформенной сессии перестановки нет вовсе. Если приложение начнёт переставлять строки через `moveMediaItems`, нужен `cloneAndMove`, который двигает индексы, как `HeadShuffle`, и такая же правка копии в `Media3Engine`.

## Классификация ошибок

`PlaybackFailures.classify` определяет вид по коду `PlaybackException` и по цепочке `cause`, никогда по тексту. Проверки идут сверху вниз:

| Вид | Признак |
|---|---|
| `SESSION` | в цепочке `HttpException` с `isTokenRejected` |
| `NETWORK` | код 2001/2002 (`IO_NETWORK_CONNECTION_*`) или в цепочке `NetworkException`, `UnknownHost`, `Connect`, `SocketTimeout`, `NoRouteToHost` |
| `TRACK` | всё остальное: 2004 (статус хранилища), `HttpException` 4xx/5xx от API, `MalformedResponseException`, парсинг 3xxx, декодер 4xxx |

Что делать с каждым видом, решает `queue/ErrorPolicy` (см. `queue/README.md`).

`PlaybackFailures.audioFailure(errorCode)` — для телеметрии (`error audio/…`, `telemetry/README.md`), тоже только по коду и через константы `PlaybackException.ERROR_CODE_*`, а не числа (сверено с исходниками `PlaybackException` Media3 1.11.1: коды те же, что в 1.4.1, ни одного нового или устаревшего):

| `AudioFailure` | Коды |
|---|---|
| `INIT` (не открылось устройство вывода) | 5001 `AUDIO_TRACK_INIT_FAILED`, 5004 `AUDIO_TRACK_OFFLOAD_INIT_FAILED` |
| `DEVICE` (устройство отказало во время игры) | 5002 `AUDIO_TRACK_WRITE_FAILED`, 5003 `AUDIO_TRACK_OFFLOAD_WRITE_FAILED`, 4006 `DECODING_RESOURCES_RECLAIMED` |
| `UNDECODABLE` | 3001–3004 `PARSING_*`, 4001–4005 `DECODER_INIT_FAILED`, `DECODER_QUERY_FAILED`, `DECODING_FAILED`, `DECODING_FORMAT_EXCEEDS_CAPABILITIES`, `DECODING_FORMAT_UNSUPPORTED` |
| `null` | всё остальное: сеть и HTTP (2xxx — это `api` и `playback`), DRM, неизвестные коды |

Эта же ошибка идёт и в `queue` как `FailureKind` (обычно `TRACK`), поэтому битый файл даёт два события: `audio/undecodable` и `playback/track`. `Media3Engine` зовёт `onAudioFailure` до `controller.onFailure`; по умолчанию это `{}`, `PlaybackService` передаёт `AppTelemetry.audioFailed`.

`PlaybackFailures.errorKind` говорит, что показать: `SESSION` → `TokenRejected`, `NETWORK` → `NoNetwork`, `TRACK` → `ServerError(status)`, если в цепочке есть `HttpException` или `HttpDataSource.InvalidResponseCodeException` хранилища, иначе `TrackUnplayable` (нет вариантов, декодер, парсинг). Подробности ошибки — только в logcat.

**Traps:**
- ExoPlayer сам повторяет сетевые ошибки загрузчика (около 3 попыток с паузой до 5 с) до `onPlayerError`, поэтому пауза наступает через несколько секунд после пропажи сети, а не сразу. Пока в буфере есть звук, трек доигрывает.
- Ошибки `TrackResolver` приходят с общим кодом 2000 (`IO_UNSPECIFIED`): отличить сеть от битого трека можно только по причине, поэтому `yandex` бросает типизированные исключения.
- `ERROR_CODE_DECODING_RESOURCES_RECLAIMED` стабилен с Media3 1.6.0 (в 1.4.1 был `@UnstableApi`), поэтому `PlaybackFailures` без `@OptIn`. При следующем обновлении Media3 коды надо сверить заново: новый код без строки в таблице даст `null`, то есть ничего в `audio`.
- С Media3 1.9 ExoPlayer сам останавливает зависший плеер (`StuckPlayerDetector`): буферизация без прогресса 10 мин, игра без движения позиции 10 с, позиция за длительностью трека 1 мин, подавление звука 10 мин. Это ошибка `ERROR_CODE_TIMEOUT` (1003) с причиной `StuckPlayerException`: `classify` даёт `TRACK` (трек пропускается, `TrackUnplayable`), `audioFailure` — `null`. Внутренняя проверка «буферизация без загрузки» 4 с даёт `ERROR_CODE_FAILED_RUNTIME_CHECK` (1004), как и в 1.4.1. Переназначать их или нет — вопрос к спеке, не к этому пакету.

## `MediaItems`, `TrackResolver`, кэш ссылок

URI трека виртуальный (`MediaItems.SCHEME = "qiyaa"`):

| URI | У какого элемента | Что из него читается |
|---|---|---|
| `qiyaa://track/{id}` | у каждого (`uriFor(track)` = `uriText(track.id)`) | `trackIdOf` → `{id}` |
| `qiyaa://track/{id}?r=<n>` | у элемента, загруженного заново (`Media3Engine.reload`, QUAL-05); `PARAM_REVISION = "r"`, `n ≥ 1` — счётчик движка | `trackIdOf` → `{id}`; запрос ничего не значит, он только делает URI другим |

`uriText(id, revision = 0)` строит текст (`require(revision >= 0)`), `revised(item, id, revision)` — тот же `MediaItem` (`buildUpon`) с новым URI: `mediaId`, метаданные и `extras` те же. `trackIdOf(uri)` — `uri.lastPathSegment` при схеме `qiyaa`: путь `qiyaa://track/42?r=3` — `/42`, запрос в путь не входит, так что `TrackResolver` и `ExpiredLinkDataSource` ревизии не видят. URI с ревизией живёт только в плейлисте ExoPlayer: `QueueSnapshot` хранит треки, `onPlaybackResumption` строит обычные элементы, а кроме `trackIdOf` URI в приложении никто не читает. `mediaId = track.id`, поэтому `PlaybackService.currentTrackId`, ♥ и `CurrentBitrate` замены не замечают. В `MediaMetadata.extras` (`Bundle`) лежат `id`, `albumId`, `durationMs` (long), `artists` (string array list), `cover` (nullable string), `title`, чтобы `toTrack` восстанавливал `Track` из уведомления и после пересоздания процесса без сети. `artworkUri` = `coverUrl`.

**Одна игра — один источник.** Источник данных собирает `PlaybackDataSources` («`PlaybackDataSources` — цепочка источников» ниже). Каждый вызов фабрики даёт новый `ResolvingDataSource` со своим `TrackResolver`, а у того свой `PlayLink`. Сверено по исходникам Media3 1.11.1 (на устройстве не проверялось, Kickoman/QiYaa-android#91):
- ExoPlayer зовёт фабрику один раз на период: `ProgressiveMediaSource.createPeriod` (`ProgressiveMediaSource.java:416–417`). Все загрузки периода идут через этот источник: `startLoading` отдаёт его каждой `ExtractingLoadable` (`ProgressiveMediaPeriod.java:1059–1062`), а та оборачивает его в `StatsDataSource` (`:1273`). Первое открытие периода — всегда с начала файла: позицию загрузки период ставит, только когда уже подготовлен (`:1063–1078`).
- Период — одна игра одной строки. Каждый круг повтора одной строки — новое окно с новым `windowSequenceNumber` (`MediaPeriodQueue.java:1221–1230`), то есть другой `MediaPeriodId`, и `enqueueNextMediaPeriodHolder` создаёт для него новый держатель (`:239–247`), а держатель — новый период (`MediaPeriodHolder.java:126`). Готовый держатель из пула предзагрузки берётся только при равном `MediaPeriodId` (`MediaPeriodHolder.java:489–492`), а пул пуст, пока `PreloadConfiguration` по умолчанию (`MediaPeriodQueue.java:266–270`, ловушка `Media3Engine`).
- Новый период, то есть новая игра, начинается и на новой очереди (`setMediaItems`), на переходе к строке, после `reload` (выше) и на повторе после ошибки или «играть» после `Player.stop()`: ошибка и `stop()` сбрасывают очередь периодов (`ExoPlayerImplInternal.stopInternal` → `resetInternal(releaseMediaSourceList = true)` → `queue.clear()`, `ExoPlayerImplInternal.java:2041–2046`, `:2124`), а `prepare()` создаёт их заново. `Player.stop()` — это команда «стоп» контроллера сессии (`QueueForwardingPlayer` её не переопределяет, и она доходит до ExoPlayer) и `QueueController.clear` вне джема. «Стоп» экрана плеера — не он: `PlayerViewModel.stop` → `QueueController.stop` — пауза и перемотка в 0 (`seekToPosition(0)`), период остаётся, и «играть» после него продолжает ту же игру в её качестве, из удержанного позади или новым открытием через тот же `PlayLink`. Для `/play-audio` это всё же новый старт (`queue/README.md`, «Отметка `/play-audio`»).

`TrackResolver.resolveDataSpec` вызывается на потоке загрузчика периода при каждом открытии сети (`ResolvingDataSource.open` зовёт резолвер всякий раз, `ResolvingDataSource.java:107–111`), а сеть `CacheDataSource` игры открывает только для того, чего нет на диске («`PlaybackCache`» ниже): старт игры (её первое открытие всегда идёт в сеть), перемотка мимо удержанного в памяти и мимо скачанного на диск («Перемотка и буфер» ниже), дыра после куска на диске, повтор после обрыва, повторное открытие внутри одной загрузки (экстрактор просит другое место файла), переоткрытие после 403/410, предзагрузка следующего трека. Чтение с диска резолвер не зовёт. `runBlocking { play.url(id) }` там допустим. URI с другой схемой проходит без изменений.

```kotlin
class PlayLink(links: TrackUrlCache, bitrate: CurrentBitrate) {
    suspend fun url(trackId: String): String   // первое открытие — в действующем качестве, дальше — в нём же
}
```

**Память игры** (`PlayLink`, QUAL-08). `@Volatile quality: Quality?` — качество, которое вернул первый удачный `get` этой игры, то есть `get(id)` без качества. Попадание в кэш тоже считается: первое открытие часто берёт ещё свежую ссылку без подписи (повтор трека в пределах 15 минут, следующий круг, следующая строка того же трека), и качество этой ссылки — качество файла игры. Все следующие открытия той же игры продолжают тот же файл и просят это качество явно: `get(id, quality)`. Файл другого кодека не продолжит начатый (QUAL-08). Упавшая первая подпись память не ставит: следующее открытие снова первое. Битрейт в `CurrentBitrate.onResolved` сообщает только первое открытие. Загрузки одного периода идут по одной на его собственном потоке: у `ProgressiveMediaPeriod` свой `Loader` (`ProgressiveMediaPeriod.java:240–241`) с однопоточным исполнителем (`Loader.java:236–240`), поэтому гонки внутри игры нет, и `@Volatile` хватает.

```kotlin
class TrackUrlCache(
    clock: () -> Long,
    quality: () -> Quality = { Quality.STANDARD },   // качество, действующее сейчас
    ttlMs: Long = TTL_MS,
    capacity: Int = CAPACITY,
    resolve: suspend (String, Quality) -> ResolvedUrl,
) {
    data class SignedLink(val link: ResolvedUrl, val quality: Quality)   // quality — в котором ссылка подписана
    suspend fun get(trackId: String, quality: Quality? = null): SignedLink   // null — первое открытие игры
    fun peek(trackId: String): String?              // свежая ссылка последнего первого открытия трека, без подписи; для слушателей джема
    fun invalidate(trackId: String, url: String)    // отказ хранилища: удаляет запись с этой ссылкой; нет такой — ничего
    fun askedInOtherQuality(trackId: String): Boolean   // последнее первое открытие трека (подписано или ещё подписывается) просило не quality(); false, если не просили
    companion object { TTL_MS = 15 * 60 * 1_000; CAPACITY = 64 }
}
```

**Качество** (`spec/player/quality.md`). Ключ записи — трек и качество, в котором подписана ссылка: ссылки одного трека в двух качествах живут рядом, и новый старт в новом качестве не перезаписывает ссылку, по которой читает играющий круг того же трека. `get(id)` — первое открытие игры, новый старт: берётся `quality()` и свежая запись этого качества, иначе подпись (QUAL-01, QUAL-02). `get(id, q)` — продолжение игры, начатой в `q`: свежая запись `q` или подпись в `q`, даже если выбор уже другой (QUAL-08). Каждый новый старт берёт действующее качество (QUAL-05 и последнее предложение QUAL-08): следующий круг одной строки с повтором, следующая строка того же трека, новая очередь с играющим треком, «назад» к недавнему, повтор после ожидания сети (ERR-09) и «играть» после `Player.stop()` — новые периоды, то есть новые игры; «играть» после «Стоп» экрана плеера — та же игра («Одна игра — один источник» выше). `get` возвращает качество ссылки, которую отдал, и на попадании в кэш: по нему `PlayLink` запоминает качество игры. `invalidate(id, url)` удаляет только запись с отвергнутой ссылкой. Если её уже вытеснили или другая игра подписала новую, он ничего не делает, и повторное открытие возьмёт ту ссылку, что есть, или подпишет новую; качество повторного открытия держит игра, а не запись. `peek` отдаёт ссылку последнего первого открытия трека: карта `opened: trackId → Quality` той же ёмкости (64) и с тем же порядком доступа, что и записи, пишется после удачного `get` без качества, в том числе на попадании. Это файл, который играет или вот-вот заиграет (ловушка «Хвост круга» ниже). Упавшая подпись `opened` не трогает, и `peek` по-прежнему отдаёт ссылку файла, который играет.

**Какое качество просили** (QUAL-05). Карта `asked: trackId → Quality` той же ёмкости (64) и с тем же порядком доступа, что и записи, помнит, в каком качестве трек спросили последним. `get` пишет её только на первом открытии игры (`quality == null`), в первом `synchronized`-блоке, сразу как решено `wanted`, и **до** подписи: попадание в кэш тоже считается, подпись, которая ещё идёт или упала, — качество, в котором её начали. Продолжение игры её не пишет: иначе чтение играющего круга в старом качестве после нового старта того же трека выглядело бы как загрузка в старом качестве. `askedInOtherQuality(id)` — `true`, если последнее первое открытие этого трека просило качество, отличное от `quality()` сейчас; трек, который не спрашивали (или вытесненный), — `false`. Так видно, что ExoPlayer уже начал грузить файл в старом качестве. `asked` пишется в том же блоке, что читает `quality()`: подпись либо записала старое качество до проверки (проверка скажет «другое»), либо прочла уже новое; середины нет. `AppGraph` передаёт `quality = { qualityInEffect.value }`. `AppGraph.qualityInEffect: StateFlow<Quality>` — `combine(Settings.quality, Settings.qualityMetered, NetworkMonitor.metered)` → `stateIn(applicationScope, Eagerly, …)` с начальным значением из трёх `.value`: `Settings.qualityMetered` на лимитной сети (мобильная или лимитный Wi-Fi), иначе `Settings.quality` (QUAL-07). Это единственный источник действующего качества: подпись и всё, что следит за его сменой, читают одно значение и разойтись не могут.

Кэш один на процесс — `AppGraph.trackLinks`: его берут и сервис, и хозяин джема. `resolve` — `YandexApi.resolveTrackUrl(id, quality)`: в стандартном качестве два запроса, `download-info` к API и `download-info` хранилища; в экономии `get-file-info` (см. `yandex/README.md`). Часы — `SystemClock.elapsedRealtime`. Каждая настоящая подпись пишет в logcat `Signing the link of track <id>` (тег `QiYaa`, уровень debug): по ней видно, что перемотка и повторное открытие обходятся без API. Без кэша эти два запроса шли на каждое открытие; с кэшем перемотка и предзагрузка того же трека обходятся без API. Срок жизни подписанной ссылки Яндекс не документирует; проверено 2026-10-02: ссылка живёт час (параметр `ts` — время истечения в микросекундах), потом хранилище отвечает 401. 15 минут выбраны, чтобы перемотка в любое место почти любого трека шла по той же ссылке. Если ссылка истекла раньше, хранилище отвечает 403 или 410, и `ExpiredLinkDataSource` сбрасывает запись, заново открывает источник, а `TrackResolver` подписывает новую ссылку: цена слишком длинного срока — один лишний запрос. `CAPACITY` ограничивает память в длинной волне: 64 записи, трек в двух качествах — две; вытесняется давно не использованная ссылка. Упавшая подпись не кэшируется. Доступ к кэшу синхронизирован: предзагрузка и текущий трек открываются с разных потоков; два одновременных промаха по одному треку в одном качестве подпишут ссылку дважды, это допустимо.

`ExpiredLinkDataSource` оборачивает `ResolvingDataSource` и повторяет открытие один раз, только для `HttpDataSource.InvalidResponseCodeException` 403/410 у `qiyaa://`-трека; второй отказ уходит в ExoPlayer как обычно (трековая ошибка, `queue/ErrorPolicy`). Отвергнутую ссылку он берёт из исключения: `failed.dataSpec` — тот `DataSpec`, с которым `ResolvingDataSource` открыл `OkHttpDataSource`, то есть подписанная ссылка, как её запросили, до редиректов (`OkHttpDataSource.java:261–262`, `:308–309`), а `Uri.parse(s).toString()` отдаёт `s` как есть. `upstream.uri` не годится: до `close()` это адрес ответа, то есть после редиректа (`:216–218`), а после — `null` (`:362–371`). Повторное открытие идёт через тот же `ResolvingDataSource` с тем же `TrackResolver`, то есть в качестве игры, и тогда, когда отказ пришёл на первое открытие: память игры ставится до HTTP-запроса. Все методы `DataSource` пересылаются явно: `getResponseHeaders` — default-метод Java, и делегирование Kotlin `by` его бы не переслало (см. ловушку `TransportCommandsListener`).

**Битрейт.** В экономии показание — `64K`. `PlayLink` сообщает битрейт первого открытия игры в `CurrentBitrate.onResolved(id, kbps)` («Память игры» выше), а сервис — смену текущего трека (`onMediaItemTransition` → `currentTrackId` → `onCurrentChanged`). В `AudioBus.bitrateKbps` попадает битрейт текущего трека: предзагрузка следующего (до перехода, «Следующий трек и бесшовный переход») его не меняет, показание меняется ровно на переходе, кроме нового старта того же трека в другом качестве (ловушка «Хвост круга» ниже); пока ссылка текущего трека не подписана — 0 (`--K`). Битрейты помнятся для последних 64 треков. Исключения `yandex` — `IOException`, поэтому ExoPlayer превращает их в `PlaybackException`, а не падает (см. `yandex/README.md`).

**Traps (URI):**
- `android.net.Uri` в JVM-тестах — заглушка с пустыми значениями (`unitTests.isReturnDefaultValues`), поэтому `MediaItemsTest` проверяет текст `uriText`, а то, что `lastPathSegment` не включает запрос, держится на документации Android (`Uri.getLastPathSegment` — последний сегмент пути) и проверке на телефоне (#91). Строить URI ревизии иначе, чем запросом (например, сегментом пути), нельзя: `trackIdOf` прочёл бы ревизию как id.

**Traps (качество):**
- Смена действующего качества (выбор для сети, которая сейчас, или переход между лимитной и безлимитной сетью, QUAL-07) доходит и до следующего трека, который ExoPlayer уже начал грузить (QUAL-05): если его ссылку уже спрашивали в другом качестве (подписанную или ещё подписываемую, `askedInOtherQuality`), `Media3Engine.reload` грузит его заново, и ExoPlayer выбрасывает вместе с ним всё подгруженное после (`queue/README.md`, «Смена качества»; `Media3Engine`, «Загрузить элемент заново»). Трек, которого ещё не спрашивали, загрузится в новом качестве сам. Трек, который играет, доигрывает своим файлом. Смена выбора для другой сети ничего не делает. На устройстве не проверялось (Kickoman/QiYaa-android#91).
- Бесшовность: `reload` идёт сразу при смене, обычно задолго до перехода; если до конца трека остаётся хотя бы время подписи и первых байтов (на деле несколько секунд), следующий трек идёт без паузы. В последние 1–2 с — щелчок, мигание `playing` в джеме и, может быть, короткая буферизация следующего трека (`Media3Engine`, «Загрузить элемент заново»). Порога нет: иначе следующий трек остался бы в старом качестве.
- Цена: выбрасывается всё, что скачано из следующего трека, — до 50 с плюс один кусок в 1 МиБ, и первый кусок качается в любом случае, без вопроса к `LoadControl` («Следующий трек и бесшовный переход»). Это до 2,2 МБ при 192 кбит/с и до 3,0 МБ при 320 кбит/с, верхняя граница столбца «Впереди» в «Памяти» ниже. В экономии заново качается до 1 МиБ: первый кусок — 131 с звука, больше окна, а файл меньше 1 МиБ (трек до 2 мин 11 с) приходит им целиком. Переход с Wi-Fi на мобильную сеть качает его заново по мобильной, так и задумано (QUAL-07). Подавления дребезга сети нет: каждое переключение стоит не больше одной такой загрузки. Быстрый возврат (A → B → A) ничего не стоит, только если он пришёл до подписи после `reload`: заново созданный период ещё не спросил ссылку, `asked` по-прежнему A, то есть действующее качество, и период загрузится в A. Если подпись уже началась, `asked` — B (`get` пишет его до подписи), и возврат загружает трек заново ещё раз. Трек, который спросили в экономии, а получили стандарт (QUAL-03), при выборе «Стандарта» загрузится заново один раз без нужды.
- Без сети смена качества выбрасывает и целиком скачанный следующий трек, а новую ссылку не подписать: на переходе будет ERR-01, хотя без смены трек сыграл бы из буфера. Этого требуют QUAL-05 и QUAL-04, и так же делает десктоп. Ожидание сети (ERR-09) от этого не меняется: текущий элемент `reload` не трогает.
- Слушать вместе (LISTEN-03, LISTEN-13): `listenNextUrl` — `peek` следующего трека. Пока первое открытие после `reload` не получило ссылку (около секунды), `peek` отдаёт старую — она свежая и того же трека; потом переход на экономию убирает поле (файл не `/get-mp3/`), а на стандарт — даёт mp3. Новое значение уходит с ближайшим 10-секундным `playing`; отдельного `playing` при `reload` нет, новой ссылки тогда ещё нет. Ссылка текущего трека не меняется, поэтому при экономии слушатели и дальше встают на паузу до следующего трека в стандарте (LISTEN-10).
- Две игры одного трека (Kickoman/QiYaa-android#94). Ключ кэша — трек и качество, а качество продолжения держит игра (`PlayLink`), поэтому новый старт трека в новом качестве — следующий круг одной строки с повтором, следующая строка того же трека, период, который `reload` создал заново за следующим (очередь из двух строк с повтором), — не трогает файл, который играет: его перемотка мимо удержанного читает свою ссылку в своём качестве. Поэтому `queue` перезагружает следующую строку с тем же треком, что играет, как любую (`queue/README.md`, «Смена качества»). Исключение — одна строка с повтором: её следующий круг — та же строка, и `reload` её не трогает (замена удалила бы играющий трек), так что круг, подгруженный до смены, играет в старом качестве (QUAL-05, проверка на телефоне — Kickoman/QiYaa-android#91).
- Память игры живёт в источнике данных: фабрика создаёт `TrackResolver` на каждый вызов. `ResolvingDataSource.Factory(http, resolver)` с одним резолвером на всех (так было до #94) дал бы одну память на все периоды, и качество первой игры осталось бы навсегда. Повторное открытие того же файла с нуля (mp3 без тега ID3) — тоже продолжение игры, а не новый старт: позиция открытия ничего не решает.
- Хвост круга. Когда новый старт того же трека в другом качестве уже открылся (следующий круг одной строки с повтором или следующая строка того же трека; предзагрузка начинается за 50 с до конца или раньше), а перехода ещё не было, показание битрейта и `listenUrl` джема — уже от нового файла: `CurrentBitrate` и `peek` знают трек только по id. Это исключение из «Битрейт» выше. После перемотки в играющем круге так остаётся до самого перехода, даже если до него минуты: перемотка выбрасывает уже открытый круг или строку (`removeAfter`, ловушка про перемотку в «Следующий трек и бесшовный переход»), а `CurrentBitrate` и `opened` остаются на его файле. Играющий файл от этого не меняется, и так было и до #94: тогда новый старт перезаписывал общую запись.
- `NetworkMonitor.metered` — `StateFlow<Boolean>` на втором `registerDefaultNetworkCallback`: на каждый `onCapabilitiesChanged` сети по умолчанию он заново спрашивает `ConnectivityManager.isActiveNetworkMetered`. Колбэк только сообщает, что что-то изменилось, а определение лимитной сети то же, с каким QUAL-07 проверен на телефоне, когда его читали прямо при подписи (`isMetered()`). Это важно на API 26–28 под VPN: там, по AOSP, `isActiveNetworkMetered` смотрит на нижележащую сеть VPN, а возможности сети по умолчанию — это возможности самого VPN (ревью плана QiYaa-android#76, пункт 3). `onLost` значения не меняет: без сети действует прежний выбор, а следующая сеть сообщит своё (на API 26+ `onCapabilitiesChanged` идёт сразу за `onAvailable`). Начальное значение — `isActiveNetworkMetered` при создании, повторы отсекает `distinctUntilChanged`. Если смена сети не даст колбэка у сети по умолчанию (например, VPN не сообщит о смене нижележащей), действующее качество останется прежним до следующего колбэка: раньше подпись спрашивала заново каждый раз. На устройстве не проверялось (Kickoman/QiYaa-android#91).
- Подпись читает `qualityInEffect.value` на loading-потоке ExoPlayer: `StateFlow.value` потокобезопасен. Сразу после смены выбора или сети производное значение обновляется не мгновенно (`combine` на `Dispatchers.Default`), и подпись в эти миллисекунды ещё возьмёт старое качество. Это не страшно: сигнал QUAL-05 приходит уже после обновления, а такая подпись записала старое качество в `asked`, так что следующий трек всё равно будет загружен заново.

## Перемотка и буфер (TR-08, TR-09)

```kotlin
@UnstableApi
object PlayerBuffer {
    const val BACK_BUFFER_MS = 10 * 60 * 1_000
    fun loadControl(): DefaultLoadControl   // setBackBuffer(BACK_BUFFER_MS, false) и setPrioritizeTimeOverSizeThresholds(true); остальное — умолчания Media3
}
```

`PlaybackService.onCreate` отдаёт `PlayerBuffer.loadControl()` в `ExoPlayer.Builder.setLoadControl`. Всё ниже сверено по исходникам Media3 1.11.1 (`media3-exoplayer`, `media3-session`, `media3-datasource`, `media3-datasource-okhttp`; OkHttp 5.5.0 — по байткоду из Gradle и JVM-тестом `StalledReadTest`) и на устройстве не проверялось (Kickoman/QiYaa-android#91). В спеке у Android TR-08 и TR-09 — `not checked: Kickoman/QiYaa-android#91` до проверки на телефоне; Given TR-09 — «…has stalled midway, and no network wait of ERR-01 to ERR-03 has begun» (`spec/player/transport.md`, «Ошибки» ниже). Расхождений в «Known gaps» (`spec/player/README.md`) нет, а строка «Seeking» в `spec/parity.md` — `not checked: Kickoman/QiYaa-android#91`; её примечание говорит, что Android держит последние 10 минут в памяти и скачанное текущим треком на диске, до 512 МиБ (около 3 ч 43 мин при 320 кбит/с), и что на устройстве это не проверено.

**Где лежат скачанные байты.** В памяти — закодированные сэмплы в `SampleQueue` периода (`ProgressiveMediaPeriod`), блоками `DefaultAllocator` по 64 КиБ в куче Java; пределы ниже. На диске — копия всего, что скачала игра, кусками по 5 МиБ в `cacheDir/playback` («`PlaybackCache`» ниже); кусок читается, когда записан целиком или загрузка закрылась.
- Впереди загрузка встаёт на 50 с (`DEFAULT_MIN_BUFFER_MS` = `DEFAULT_MAX_BUFFER_MS` = 50 000, `DefaultLoadControl.java:64`, `:76`) плюс не больше одного куска: период спрашивает `LoadControl` раз в 1 МиБ (`DEFAULT_LOADING_CHECK_INTERVAL_BYTES`, `ProgressiveMediaSource.java:321`), это около 26 с звука при 320 кбит/с и около 131 с при 64 кбит/с.
- Позади `doSomeWork` на каждом проходе зовёт `discardBuffer(позиция − backBufferDurationUs, …)` (`ExoPlayerImplInternal.java:1476–1477`), перемотка — тоже (`:1903–1904`). По умолчанию (`DEFAULT_BACK_BUFFER_DURATION_MS = 0`, `DefaultLoadControl.java:130`) сыгранный сэмпл освобождается сразу, с `PlayerBuffer` — когда он старше 10 минут.

**Настройки.**
- `setBackBuffer(BACK_BUFFER_MS, false)`. Каждый сэмпл звука — ключевой, так что «держать от ключевого кадра» ничего не меняет. Границу `ExoPlayerImplInternal` читает один раз, в конструкторе (`:330`), поэтому она не может следовать за длиной трека или битрейтом.
- `setPrioritizeTimeOverSizeThresholds(true)` — и для сети, и для локальных файлов (`DefaultLoadControl.java:453–461`). Цель по байтам остаётся умолчанием: 200 × 64 КиБ = 13 107 200 Б на плеер (`DEFAULT_MIN_BUFFER_SIZE` с `onPrepared`, `:169`, `:887–895`; для одной звуковой дорожки после выбора дорожек — `DEFAULT_AUDIO_BUFFER_SIZE`, столько же, `:144`), и блоки позади в неё входят. Пока впереди меньше 50 с, `shouldContinueLoading` с флагом грузит и сверх цели, если у кучи есть запас: она ещё может расти (`totalMemory() < maxMemory()`) или свободно не меньше 4 % (`:786–804`, `heapHasEnoughHeadroomForPrioritizeTimeOverSizeThreshold`, `:1010–1018`).
- Без флага при 320 кбит/с цель набирается за 328 с (около 4,6 мин позади и 50 с впереди), и загрузка встаёт. Когда впереди остаётся меньше 0,5 с, `ExoPlayerImplInternal.shouldContinueLoading` выбрасывает весь буфер позади и спрашивает снова (`:3553–3565`): позади пусто, впереди почти ничего, и раз в несколько минут — буферизация.
- Под нехваткой памяти то же бывает и с флагом: без 4 % запаса загрузка встаёт на цели по байтам. Проверка запаса только не даёт Media3 расти дальше. Удержанное позади под нехваткой памяти не отдаётся: его выбрасывает только откат выше, когда впереди меньше 0,5 с, а освобождённые блоки остаются в пуле `DefaultAllocator` для следующей загрузки, куче они не возвращаются («Память» ниже). Так что это защита от роста самого Media3, а не от `OutOfMemoryError` в остальном приложении; на этот случай — ловушка про `BACK_BUFFER_MS` ниже. Своей цели по байтам нет: цель выше пика (таблица ниже) выключила бы и эту остановку.
- Остальное — умолчания 1.11.1: старт с 1 с впереди (`DEFAULT_BUFFER_FOR_PLAYBACK_MS`, `:90`), после буферизации — с 2 с (`DEFAULT_BUFFER_FOR_PLAYBACK_AFTER_REBUFFER_MS`, `:102`); проверка — `shouldStartPlayback` (`:812–829`).

**Память.** Расчёт, не измерение; всё в куче (диск — «`PlaybackCache`» ниже). Позади = `BACK_BUFFER_MS` / 1000 × битрейт / 8, впереди — 50 с и до 1 МиБ сверху. Это пик трека длиннее 10 минут; на коротком позади только сыгранное, например 4 минуты при 320 кбит/с — 9,6 МБ и до 3,0 МБ впереди.

| Файл | Позади | Впереди | Пик |
|---|---|---|---|
| mp3 320 кбит/с (стандарт берёт лучший вариант, `yandex/README.md`) | 24,0 МБ | 2,0–3,0 МБ | 26,0–27,0 МБ |
| mp3 192 кбит/с | 14,4 МБ | 1,2–2,2 МБ | 15,6–16,6 МБ |
| HE-AAC 64 кбит/с (экономия) | 4,8 МБ | 0,4–1,4 МБ | 5,2–6,2 МБ |

До `PlayerBuffer` пик был только впереди: до 3,0 МБ при 320 кбит/с.

`DefaultAllocator.release` оставляет освобождённые блоки себе в пуле для повторного использования и не обрезает их. Обрезает `DefaultAllocator.trim` (`DefaultAllocator.java:134–173`): в пуле остаётся не больше ⌈цель / 64 КиБ⌉ минус занятые блоки, то есть, пока занятых меньше цели, занятые и свободные вместе — не больше 13 107 200 Б. `trim` зовёт сброс очереди сэмплов (`SampleDataQueue.reset`, `SampleDataQueue.java:70–77`), а он бывает:
- на каждой смене трека: сыгранный период освобождается (`MediaPeriodQueue.advancePlayingPeriod`, `MediaPeriodQueue.java:499–506`), и поток загрузки зовёт `onLoaderReleased` → `SampleQueue.release` → `reset` (`ProgressiveMediaPeriod.java:276–281`, `SampleQueue.java:207–210`, `:226–227`);
- после перемотки мимо удержанного: `onLoadCanceled` → `SampleQueue.reset` (`ProgressiveMediaPeriod.java:831–834`), а если загрузка не шла — сразу (`:620–624`).

Выбор дорожек нового трека пул не обрезает: `onTracksSelected` → `updateAllocator` ставит ту же цель 13 107 200 Б (`DefaultLoadControl.java:725–735`, `:917–923`), а `setTargetBufferSize` обрезает только при уменьшении цели (`DefaultAllocator.java:91–97`). Остановка или освобождение плеера (`onStopped`/`onReleased` → `updateAllocator` → `DefaultAllocator.reset`: «стоп», ошибка, `onDestroy` сервиса) ставит цель 0 и отдаёт весь пул.

Так что пик держится в пределах одного трека, на паузе тоже. На смене трека или после перемотки мимо удержанного Media3 возвращается к 13,1 МБ (занятые блоки и пул вместе; занято тогда не больше того, что впереди) и растёт снова; обрезанные блоки куча получит после сборки мусора. Замера на телефоне ещё нет (#91).

**Позиция при перемотке (TR-08).** Своего кода у приложения тут нет, кроме записи цели в `ui/PlayerViewModel` (`ui/README.md`); остальное — маскировка Media3.
- `ExoPlayerImpl.seekTo` (`ExoPlayerImpl.java:954–1000`) увеличивает `pendingOperationAcks`, переводит `READY` или `ENDED` в `BUFFERING` (`isPlaying` — `false`), пишет цель в `playbackInfo` (`maskTimelineAndPosition`) и сообщает её внутри вызова (`updatePlaybackInfo(…, DISCONTINUITY_REASON_SEEK)`, см. ловушку про `onSeeked` в `Media3Engine`). Обновление с потока воспроизведения применяется, только когда `pendingOperationAcks` дошёл до 0 (`handlePlaybackInfo`, `:2228–2234`): позиция, посчитанная до последней перемотки, не показывается и при серии перемоток.
- `MediaController` экрана маскирует сам. `seekTo(ms)` (`MediaControllerImplBase.java:510–518`) кладёт номер команды в `pendingMaskingSequencedFutureNumbers` (`:405–412`), а `seekToInternal` (`:2392–2456`) ставит `BUFFERING` (кроме `IDLE`) через `copyWithPlaybackState`, который пересчитывает `isPlaying`, и цель с `eventTimeMs` = сейчас. Пока набор не пуст, состояние от сессии откладывается (`onPlayerInfoChanged`, `:2940–2958`), а периодические позиции отбрасываются (`updateSessionPositionInfoIfNeeded`, `:3326–3328`). При `!isPlaying` `MediaUtils.getUpdatedCurrentPositionMs` отдаёт сохранённую позицию как есть (`MediaUtils.java:274–288`).
- Пауза остаётся паузой: перемотка не меняет `playWhenReady` ни в ExoPlayer, ни в контроллере. `QueueController.onSeeked` его тоже не трогает: он сообщает джему, сохраняет позицию и снимает ожидание продолжения (`stopWaiting` → `continueAtEnd = false`; `queue/README.md`, «Ждёт продолжения»), так что и ответ догрузки, пришедший после перемотки, только дописывается и игру не включает.
- Перемотка из уведомления, с экрана блокировки и гарнитуры доходит до ExoPlayer через сессию; экран показывает состояние сессии, которое ExoPlayer уже замаскировал.
- JVM-теста нет: ExoPlayer и `MediaController` работают только на `Looper`, `TestExoPlayerBuilder` — на лупере Robolectric, а Robolectric в проекте нет (`CLAUDE.md`, §6).

**Перемотка, пока загрузка стоит (TR-09).** `ProgressiveMediaPeriod.seekToUs` (`ProgressiveMediaPeriod.java:583–627`) сначала пробует перемотку внутри буфера, если загрузка кончилась или идёт (`loadingFinished || loader.isLoading()`, `:603–607`); `isLoading()` истинно и тогда, когда загрузка висит в чтении или ждёт повтора. `SampleQueue.seekTo(цель, false)` (`SampleQueue.java:533–557`) отматывает к первому удержанному сэмплу и удаётся, если первый удержанный ≤ цель ≤ последний в очереди. Тогда зависшую загрузку никто не трогает, `seekToPeriodPosition` сбрасывает `isRebuffering` (`ExoPlayerImplInternal.java:1839`), и для `READY` хватает 1 с впереди (`shouldTransitionToReadyState`, `:2536–2578`).

Иначе все очереди делают `discardToEnd()`, затем `loader.cancelLoading()` (`ProgressiveMediaPeriod.java:614–619`), а новая загрузка с байта по карте перемотки стартует только после `onLoadCanceled` (`:811–839`), то есть когда поток загрузки выйдет из старого `read`. Новое `open` идёт в `CacheDataSource` игры: байты цели, которые игра уже скачала, читаются с диска без сети и без подписи; иначе — `TrackResolver` (продолжение игры в её качестве, `PlayLink`, QUAL-08) → запрос диапазона. `Loader.LoadTask.cancel` прерывает поток загрузки (`Loader.java:420–428`), но `OkHttpDataSource.readInternal` — обычный `InputStream.read`; сам по себе прерывается только `open` (`executeCall`: `enqueue` и `SettableFuture.get`).
- HTTP/1.1: чтение из сокета прерывания не замечает. Его заканчивает `ReadInterrupts` (ниже): не позже чем через 100 мс проверка видит прерванный поток загрузки и отменяет HTTP-вызов этого чтения. Без неё чтение на молчащем соединении вернулось бы только по тайм-ауту чтения 20 с (`AppGraph.HTTP_TIMEOUT_SECONDS`).
- HTTP/2: OkHttp ждёт данные потока в `Http2Stream.waitForIo`, который превращает прерывание в `InterruptedIOException` сразу.
- Новый запрос (цель не на диске) ждёт сети: заголовков ответа — до тех же 20 с.
- Хост экономии (`strm-*.strm.yandex.net`) отвечает по HTTP/2 (`curl --http2`, 2026-10-17). Отвечают ли по HTTP/2 хосты хранилища стандарта (`*.storage.yandex.net`), ещё не проверено (#91).

|---|---|---|---|
| Вперёд, в скачанное, не ближе 3 с к его концу | играет сразу | играет сразу | играет сразу (память) |

| Назад за прежнюю перемотку за скачанное | новый запрос, ждёт сети | новый запрос, ждёт сети | играет с диска, так же |
| Вперёд за скачанное | новый запрос, ждёт сети | новый запрос, ждёт сети | новый запрос, ждёт сети |
| Любая, когда уже показан сетевой статус (ERR-03, «Ошибки» ниже) | новый запрос, ждёт сети | новый запрос, ждёт сети: плеер ничего не держит | так же, как десктоп |

До #89 на HTTP/1.1 каждый «новый запрос» ждал сначала ещё до 20 с, пока вернётся старое чтение; теперь его отменяет `ReadInterrupts`, а на HTTP/2 (экономия) оно и раньше кончалось сразу.

**Ошибки (ERR-01…03, ERR-09).** Упавшая загрузка повторяется сама (через `min((n − 1) × 1000, 5000)` мс, `DefaultLoadErrorHandlingPolicy.java:128–132`), а её ошибку бросает рендерер и только после больше чем 3 неудач подряд (`DEFAULT_MIN_LOADABLE_RETRY_COUNT`, `:37`; `Loader.java:393–397`): когда рендереру нечего играть (`ExoPlayerImplInternal.java:1501–1503`) или, пока плеер в `BUFFERING`, у рендерера, который читает играющий период (`:1554–1559`). После перемотки в удержанное плеер переходит в `READY` в том же проходе `doSomeWork`, раньше этой проверки (`:1531–1533`): сэмплы есть, 1 с впереди есть. Поэтому TR-09 держится и после долгой остановки, когда загрузка уже упала больше 3 раз. После ошибки ExoPlayer останавливается и освобождает период вместе с удержанным (`handleIoException` → `stopInternal`, `ExoPlayerImplInternal.java:1016–1024`, `:2041–2048`), а повтор (`prepare()`, `queue/ErrorPolicy`) грузит с позиции, как раньше. Поэтому, когда сетевой статус (ERR-03) уже показан, плеер ничего не держит, и любая перемотка ждёт сети. Диск тут не помогает: повтор — новый период, то есть новая игра со своим ключом, и её первое открытие идёт в сеть («`PlaybackCache`»). Так же ведёт себя десктоп: `Player::waitForNetwork` бросает скачанное (`current->feed = Feed{}`) и начинает пустой поток с позиции (Kickoman/QiYaa 8cfe9f3, `src/core/player.cpp:802–830`; `src/core/README.md`, «Network»: «the download and the preload are dropped»). Поэтому это не расхождение: в спеке Given TR-09 оговаривает, что ожидание сети ERR-01…03 ещё не началось (`spec/player/transport.md`).

**Что не меняется.**
- Ссылки и качество (`ExpiredLinkDataSource`, `TrackResolver`, `TrackUrlCache`): перемотка в удержанное ничего не открывает, в скачанное на диск — открывает файл без подписи, за их пределы — сеть, как раньше (в качестве игры, `PlayLink`, при 403/410 одна переподпись). Перемотка назад больше не подписывает заново ссылку старше 15 минут, как и игра без перемотки.
- Джем: ссылки слушателей по-прежнему из `peek`, ничего нового не подписывается и не отдаётся.
- Предзагрузка следующего трека: `bufferedDurationUs` считает только впереди (`getTotalBufferedDurationUs`, `ExoPlayerImplInternal.java:3791–3799`), так что удержанное позади её не сдвигает. Ни то, когда она начинается, ни то, что её выбрасывает любая перемотка, `PlayerBuffer` не меняет («Следующий трек и бесшовный переход»), кроме нехватки памяти: блоки позади входят в цель по байтам, на которой тогда встаёт загрузка («Настройки», пункт о нехватке памяти).
- Заодно «назад» после 3 с (перемотка в 0, TR-02, HOST-07) на треке, сыгранном не дольше 10 минут, играет из памяти без запроса. Если первый сэмпл файла позже 0, так бывает, только пока трек играет с 0 без перемоток в другое место (ловушки ниже).

**Traps:**
- `prioritizeTimeOverSizeThresholds` должен остаться `true`, и своей цели по байтам быть не должно («Настройки» выше). Флаг ловит `PlayerBufferTest`.
- Границу позади ExoPlayer читает один раз, когда собирается.
- Перемотка мимо удержанного выбрасывает из памяти всё удержанное (`discardToEnd`) и грузит от своей цели. Назад за эту цель — уже не память, а диск: первые байты ждут отмены старого чтения (до 0,1 с) и открытия файла.
- `SampleQueue.seekTo` отказывает, если цель раньше первого удержанного сэмпла. Исключение для цели до первого сэмпла (задержка кодера, `ProgressiveMediaPeriod.java:1152–1165`) работает, только если с начала файла ничего не выброшено и прошлая перемотка этого периода была в то же место. `lastSeekPositionUs` (`:171`) начинается с 0 и меняется только в `seekToUs` (`:593–594`; туда же идёт `selectTracks` при старте не с 0, `:378–379`, `:466–467`) и при перезапуске загрузки с 0 (`:737`, `:1117`), так что период, начатый с 0 без перемоток, считается перемотанным в 0. Поэтому у файла, первый сэмпл которого позже 0, перемотка в 0 идёт в сеть только после перемотки этого трека в другое место или если трек начат не с 0 (восстановленная позиция).
- Lossless (в 5–10 раз больше mp3) — пересчитать таблицу памяти. Если на телефонах с кучей 128 МБ появятся `OutOfMemoryError`, уменьшить `BACK_BUFFER_MS` вдвое (формула выше).

## `PlaybackDataSources` — цепочка источников

```kotlin
@UnstableApi
class PlaybackDataSources(client: Call.Factory, links: TrackUrlCache, bitrate: CurrentBitrate, cache: PlaybackCache, interrupts: ReadInterrupts) : DataSource.Factory {
    override fun createDataSource(): DataSource   // своя цепочка на каждый вызов, то есть на каждую игру
    companion object { const val USER_AGENT = "QiYaa/Android" }
}
```

Фабрика, которую `PlaybackService` отдаёт в `DefaultMediaSourceFactory.setDataSourceFactory`. ExoPlayer зовёт её один раз на период (`ProgressiveMediaSource.java:416–417`), на потоке воспроизведения. Каждый вызов собирает цепочку заново, снаружи внутрь:

| Слой | Что делает |
|---|---|
| `DiskErrorDataSource` (`PlaybackCache.dataSource`) | ошибку диска превращает в ошибку, которую загрузчик повторяет («Ошибки диска трек не роняют» ниже). Без диска этого слоя нет |
| `CacheDataSource` (`PlaybackCache.dataSource`) | ключ игры; то, что игра уже скачала, — с диска, остальное — из сети с записью на диск («`PlaybackCache`» ниже). Без диска (`SimpleCache` не открылся) этого слоя нет |
| `ExpiredLinkDataSource` | при 403/410 сбрасывает отвергнутую ссылку и открывает заново («`MediaItems`, `TrackResolver`, кэш ссылок» выше) |
| `ResolvingDataSource(TrackResolver)` | `qiyaa://track/{id}` → подписанная ссылка в качестве игры (`PlayLink`, QUAL-08) |
| `InterruptibleDataSource` | `open` и `read` под присмотром `ReadInterrupts.Watch` этой игры (ниже) |
| `OkHttpDataSource` | HTTP через `CallTracker(client, watch)`; `client` — `AppGraph.httpClient` (тайм-ауты 20 с), User-Agent `QiYaa/Android` |

`OkHttpDataSource.Factory(calls).setUserAgent(USER_AGENT).createDataSource()` — тоже на каждый вызов: конструктор `OkHttpDataSource` закрыт (1.11.1), а `CallTracker` у каждой игры свой.

Порядок важен. Диск снаружи: чтение с диска не подписывает и сети не касается, а переподпись при 403/410 остаётся внутри одного открытия сети, и `CacheDataSource` видит одно открытие; 403/410 для него — не ошибка кэша (`CacheDataSource.java:866–870`). Кэш под резолвером взял бы ключом подписанную ссылку, а ссылку старше 15 минут подписывал бы по сети раньше, чем прочесть диск.

## `ReadInterrupts` — прерываемое чтение (TR-09)

```kotlin
class ReadInterrupts(schedule: (delayMs: Long, check: () -> Unit) -> Unit, log: (String) -> Unit = {}) {
    fun watch(): Watch                                  // одна на источник данных, то есть на игру
    inner class Watch {
        fun <T> during(call: Call?, block: () -> T): T  // на прерванном потоке — InterruptedIOException сразу, без block
        fun bind(call: Call)                             // вызов, сделанный внутри during на том же потоке; иначе ничего
    }
    companion object { const val CHECK_PERIOD_MS = 100L }
}
class CallTracker(client: Call.Factory, watch: ReadInterrupts.Watch) : Call.Factory {
    override fun newCall(request: Request): Call       // запоминает вызов и зовёт watch.bind
    fun takeLast(): Call?                              // последний вызов; забывает его
}
@UnstableApi
class InterruptibleDataSource(upstream: DataSource, calls: CallTracker, watch: ReadInterrupts.Watch) : DataSource
```

**Зачем.** Перемотка мимо удержанного отменяет загрузку периода, и новая загрузка стартует только после того, как старая вернулась («Перемотка, пока загрузка стоит» выше). Отмена ставит флаг (`ExtractingLoadable.cancelLoad`, `ProgressiveMediaPeriod.java:1286–1288`) и прерывает поток загрузки (`Loader.java:424–427`); источник закрывается только в `finally` самой загрузки, на её потоке (`ProgressiveMediaPeriod.java:1351`). `OkHttpDataSource` 1.11.1 (сверено по исходникам) свой `Call` наружу не отдаёт: конструктор закрыт, `open` создаёт вызов (`OkHttpDataSource.java:270`) и ждёт ответа в `executeCall` — `enqueue` и `future.get()`, который прерывается и сам отменяет вызов (`:429–452`); `read` — обычное чтение потока тела (`:351–358`, `readInternal`, `:511`). На HTTP/1.1 такое чтение прерывания не замечает и на молчащем соединении возвращается только по тайм-ауту 20 с. `Call.cancel()` потокобезопасен и заканчивает его с другого потока: в OkHttp 5.5.0 он закрывает сокет соединения (на HTTP/2 — сбрасывает поток). Это и проверяет `StalledReadTest` на JVM.

**Как.** `InterruptibleDataSource` стоит прямо над `OkHttpDataSource` и выполняет каждое `open` и `read` внутри `watch.during`. Запись на время чтения — одна на источник и переиспользуется: на каждое чтение — два захвата замка и одна лямбда.
- `open` регистрируется с пустым вызовом. `OkHttpDataSource.open` создаёт ровно один вызов на том же потоке, и `CallTracker.newCall` кладёт его в запись под замком `ReadInterrupts` (`bind`). С этого момента открытие под присмотром: `skipFully` после ответа 200 на запрос диапазона (`:463–495`) и чтение тела ошибки (`:295–300`) отменяются так же, как `read`. До вызова прерывание отменяет открытие само (`future.get()`).
- После удачного `open` — `calls.takeLast()`, то есть вызов этого открытия, и каждое `read` регистрируется с ним. Упавшее `open` вызов не берёт: мёртвый вызов остаётся в `CallTracker` до следующего `newCall`, а чтений без открытия не бывает. `close` вызов забывает.
- Поток, прерванный ещё до `during`, получает `InterruptedIOException` сразу, без чтения.
- Пока идёт хоть одно чтение, раз в `CHECK_PERIOD_MS` = 100 мс `check` под замком копирует поток и вызов каждой записи, потом смотрит `isInterrupted()` скопированного потока и отменяет скопированный вызов, если тот ещё не отменён. В logcat — `Canceled the HTTP call of a canceled load stuck in a read` (тег `QiYaa`, debug). Без чтений проверка не планируется (`ReadInterruptsTest`).
- `AppGraph.readInterrupts` — одна на процесс; `schedule` — однопоточный демон `QiYaa:ReadInterrupts` (`ScheduledExecutorService`, поток появляется с первой задачей).

Отменённое чтение кончается `IOException`: на HTTP/1.1 — `SocketException: Socket closed`, на HTTP/2 — `InterruptedIOException`. Задача загрузчика отменена, поэтому `Loader` зовёт `onLoadCanceled` (`Loader.java:466–469`, `:512–514`), и стартует новая загрузка. Итог: зависшее чтение отменённой загрузки кончается не позже чем через 0,1 с, а не через 20 с. Так же быстрее отпускает поток загрузки освобождённый период (смена трека, `player.release()`). Сверено по исходникам Media3 1.11.1 и на JVM с OkHttp 5.5.0; на устройстве не проверялось (Kickoman/QiYaa-android#91).

**Traps:**
- Всё держится на том, что Media3 прерывает поток загрузки при отмене (`Loader.java:420–428`). Если обновление Media3 перестанет его прерывать, тесты этого не заметят (`ReadInterruptsTest` и `StalledReadTest` прерывают поток сами), заметит только проверка на телефоне.
- Флаг прерывания переживает отменённое чтение: ветка `catch (IOException)` (`Loader.java:466–469`) пропускает сброс флага (`:458–462`, `Thread.interrupted()` на `:461`). Следующая загрузка периода стартует чистой только потому, что исполнитель загрузчика — однопоточный пул (`Loader.java:236–240`, `Util.java:1007–1008`), а `ThreadPoolExecutor.runWorker` сбрасывает флаг перед каждой задачей. `InterruptibleDataSource` на прерванном потоке бросает сразу, так что исполнитель загрузки не из пула (`DefaultMediaSourceFactory.setDownloadExecutor`) ронял бы каждую загрузку после отмены.
- Порядок в `check` — копия под замком, потом флаг, потом отмена копии. Запись одна на источник: если прочесть флаг, а запись потом, проверка могла бы отменить вызов следующей загрузки той же игры (старая вернулась сама, `onLoadCanceled` начал новую). В этом порядке устаревшая копия отменяет только вызов загрузки, которую уже отменили.
- Вызов чтения — только из `takeLast()` после удачного `open`, вызов открытия — только из `newCall` на том же потоке. «Последний вызов игры», взятый в момент отмены, мог бы оказаться вызовом следующей загрузки. `takeLast` после `open` — вызов этого открытия, пока `OkHttpDataSource.open` делает ровно один `newCall` (1.11.1).
- Опрос, а не событие. Без опроса можно так: свой исполнитель загрузки (`DefaultMediaSourceFactory.setDownloadExecutor(Supplier<ReleasableExecutor>)`, `DefaultMediaSourceFactory.java:520`; один на период, `ProgressiveMediaSource.java:438`, `ProgressiveMediaPeriod.java:238–241`), чей поток в `interrupt()` сразу отменяет вызов. Не сделано: опрос проще и стоит не больше 0,1 с.

Всё ниже сверено по исходникам Media3 1.11.1; на устройстве не проверялось (Kickoman/QiYaa-android#91).

**Что на диске.** Копия того, что скачала каждая игра. `CacheDataSource` пишет байты из сети в файлы по 5 МиБ (`CacheDataSink(cache, DEFAULT_FRAGMENT_SIZE)`; дробить на куски разрешает сам период флагом `FLAG_ALLOW_CACHE_FRAGMENTATION`, `ProgressiveMediaPeriod.java:1391–1392`) и читает с диска то, что там уже есть. Папка — `cacheDir/playback`, своя: `SimpleCache` удаляет из папки незнакомые файлы, а дисковый кэш обложек Coil живёт в `cacheDir/coil3_disk_cache`. Базы данных нет: `SimpleCache(dir, LeastRecentlyUsedCacheEvictor(MAX_BYTES), null, null, false, false)` — конструктор с шестью аргументами не устарел (`SimpleCache.java:191–210`), в отличие от двухаргументного (`:141`), и индекс — файл в той же папке. `StandaloneDatabaseProvider` положил бы индекс в `databases/exoplayer_internal.db`: она переносится между устройствами (`data_extraction_rules.xml` исключает только `sharedpref` и файлы `jam-guest`), пережила бы стирание папки и хранила бы подписанную ссылку редиректа.

**Сколько.** `MAX_BYTES` = 512 МиБ — около 3 ч 43 мин при 320 кбит/с (40 000 Б/с), 6 ч при 192 кбит/с и 18 ч при 64 кбит/с. На деле на диске лежат текущий и следующий трек (ниже), обычно 10–30 МБ; предел только ограничивает один очень длинный трек: LRU выбрасывает сначала его самые старые куски. 256 МиБ (1 ч 51 мин при 320 кбит/с) — запасной вариант, если 512 окажется много. Запись — около 144 МБ в час при 320 кбит/с.

**Ключ — игра, а не трек с качеством.** Один источник данных — одна игра, то есть период ExoPlayer («Одна игра — один источник» выше; `ProgressiveMediaSource.java:416–417`). Ключ живёт в той же цепочке, что и `PlayLink` игры, поэтому он точен для QUAL-08 по построению и не смешивает файлы разного качества или кодека: экономия может дать AAC при одной подписи и mp3 при другой (QUAL-03). Новый старт — новый период — новый ключ: следующий круг повтора, следующая строка того же трека, `reload` (`?r=n`, QUAL-05), повтор после ERR-09. Ключ из трека и качества пришлось бы знать до подписи, а действующее качество может смениться между ключом и подписью; трек, сыгранный целиком с диска, вовсе не подписывался бы, и слушатели джема остались бы без `listenUrl`. Цена ключа игры: игры одного трека диск не делят; TR-09 этого не нужно. `MediaItem.customCacheKey` не ставится: `canUpdateMediaItem` сравнивает его (`ProgressiveMediaSource.java:387–394`), а на этом держатся голый `prepare()` ERR-09 и `replaceMediaItem` у `reload`.

**Инвариант: первое открытие игры всегда идёт в сеть.** Ключ новой игры на диске ничего не находит: `n` в процессе не повторяется, а часть `<процесс>` своя у каждого процесса (8 шестнадцатеричных знаков `SecureRandom`, раз на процесс), так что остаток прошлого процесса с тем же `n` с ключом не совпадёт, даже если стереть папку не удалось. На этом держится логика #94: первое открытие подписывает ссылку в действующем качестве и ставит память игры (`PlayLink`: качество, битрейт, `asked`, `opened` для `peek`).

**Что открывает `CacheDataSource`.** На каждое открытие — ключ игры (`CacheKeyFactory`, `CacheDataSource.java:584`; первое открытие записывает URI игры в `CachedPlays.opened`). Дальше с позиции чтения (`startReadWriteNonBlocking`, `:723`):
- кусок на диске — чтение файла через `CacheFileDataSource` (`:734–751`);
- дыра — сеть с записью на диск (`TeeDataSource` + `CacheDataSink`, `:752–772`), запрос — к URI `qiyaa://track/…`, так что резолвер работает как раньше (`:763–764`);
- кусок, который пишет другая загрузка той же игры, — сеть без записи (`:728–733`). Блокировать (`FLAG_BLOCK_ON_CACHE`, `:715–721`) не нужно: загрузки одной игры идут по одной.

Когда кусок на диске кончился, `read` открывает следующий источник (`:655–658`): дальше снова сеть через `TrackResolver` в качестве игры (#94), а прочитанное с диска тем временем играет. Без `Content-Length` у ответа на диск ничего не пишется (`FLAG_DONT_CACHE_IF_LENGTH_UNKNOWN` ставит период, `ProgressiveMediaPeriod.java:1391–1392`; `CacheDataSink.java:185–190`, `TeeDataSource.java:59–61`): такая игра живёт только в памяти, как до #89.

**Когда кусок читается.** Кусок записан на диск, когда набралось 5 МиБ или загрузка закрылась (`CacheDataSink.closeCurrentOutputStream` → `commitFile`). Загрузка, отменённая перемоткой, закрывает источник в `finally` (`ProgressiveMediaPeriod.java:1351`) до `onLoadCanceled`, так что следующая загрузка той же игры видит всё, что скачала прошлая.

**Что остаётся на диске.** `keepFor(player)` на каждом `onMediaItemTransition` (главный поток) берёт URI `currentMediaItem` и элемента на `nextMediaItemIndex` (того, что ExoPlayer грузит следующим, с учётом shuffle и повтора) и отдаёт удаление однопоточному планировщику `removals` (`AppGraph.daemonScheduler`: `ScheduledExecutorService` на демоне `QiYaa:PlaybackCache`). Там `toDrop(cache.keys, keep)` и `removeResource` на каждый выброшенный ключ; в logcat — `Dropped <n> plays from the disk`. Через `LATE_FRAGMENT_DELAY_MS` = 1 с те же ключи удаляются ещё раз (`dropLate`; в logcat — `Dropped the late fragments of <n> plays from the disk`, если у них нашлись куски): кусок, который ещё пишет загрузка выброшенной игры, попадает в индекс только в `commitFile` (`SimpleCache.java:398–434`), и первый проход его не видит (`getCachedSpans`, `:307–313`). Второй проход берёт только ключи первого, а ключи в процессе не повторяются, так что игру, начатую после удаления, он не трогает. Остаются две новейшие игры каждого из этих URI (новее — больше `n`): играющая, подгруженная следующая, а в повторе одного трека — и предыдущий круг. Всё прочее уходит, в том числе ключи, которых `CachedPlays` не знает: остатки прошлого процесса и игра, выброшенная по ошибке, но успевшая записать ещё кусок. Пустой плейлист (`onMediaItemTransition(null)`, `ExoPlayerImpl.java:2324–2330`, `:2565–2566`; туда же ведёт выход из аккаунта через `queue.clear()`) и `onDestroy` (`clear()` после `player.release()`) удаляют всё. Ошибочно выброшенная живая игра теряет только копию на диске: `removeResource` у ключа, в который идёт запись, оставляет его запись занятой (`CachedContentIndex.maybeRemove`, `:284–287`), следующий кусок ложится как обычно, и его уберёт следующая смена трека. С тремя играми одного URI (повтор, строки A, A) правило может выбросить играющую, только когда та скачана целиком и коротка, то есть вся в памяти.

**Жизнь кэша.** `SimpleCache` один на процесс (`AppGraph.playbackCache`): на одну папку в процессе можно открыть только один (`SimpleCache.java:217–219`). Он никогда не освобождается. Создаёт его один ленивый держатель при первом `dataSource()`, на потоке воспроизведения: сначала `SimpleCache.delete(dir, null)` (`@WorkerThread`, `SimpleCache.java:99–130`), потом конструктор и `checkInitialization()`. `keepFor` и `clear` до этого ничего не делают и кэш на главном потоке не создают; `isInitialized()` у `Lazy` не блокирует. Если инициализация не удалась (`Cache.CacheException`, например папку не создать), кэш освобождается, в logcat — `The disk cache is off for this run: …`, и до конца процесса цепочки собираются без диска.

**Ошибки диска трек не роняют.** С `FLAG_IGNORE_CACHE_ON_ERROR` (`CacheDataSource.java:373`) ошибка, пока читается диск, и любая `Cache.CacheException` ставят `seenCacheError` (`handleBeforeThrow`, `:866–870`), и все следующие открытия этой игры идут мимо диска (`:872–880`); в logcat — `The disk cache is off for play-… after an error` (`onCacheIgnored`). Но саму ошибку `CacheDataSource` бросает дальше как есть, а повторит ли её загрузчик, решает `DefaultLoadErrorHandlingPolicy`. Она проходит всю цепочку причин и не повторяет, если в ней есть `FileNotFoundException` или `DataSourceException` с `ERROR_CODE_IO_READ_POSITION_OUT_OF_RANGE` (`DefaultLoadErrorHandlingPolicy.java:164–182`). Без обёртки ниже период с такой ошибкой падал бы (`DONT_RETRY_FATAL`, `ProgressiveMediaPeriod.java:866–870`), `PlaybackFailures.classify` не нашёл бы в цепочке сети, и трек пропускался бы как `TRACK` (ERR-04). Следующая игра — новый источник с новым `CacheDataSource`, на полном диске она упала бы так же, и на третьей плеер остановился бы (ERR-05). А `FileOutputStream` бросает `FileNotFoundException` на любой неудаче открытия файла (так в его документации), в том числе на ENOSPC. Ошибки диска с такой причиной:
- файл куска не создать (ENOSPC на полном диске; ENOENT или ENOTDIR, если папку `0`…`9` стёрли или на её месте файл): `new FileOutputStream` в `CacheDataSink` (`CacheDataSink.java:248`) на открытии дыры (`:197`) и на каждом следующем куске (`:214`) → `CacheDataSinkException(FileNotFoundException)` (`:199`, `:224`). `CacheDataSinkException` — наследник `Cache.CacheException` (`:116`);
- индекс не записать: `AtomicFile.startWrite` → `IOException("Couldn't create …", FileNotFoundException)` (`AtomicFile.java:107–117`) → `Cache.CacheException` (`SimpleCache.java:509` на открытии сети, `:431` на записанном куске);
- файл куска пропал между проверкой длины (`SimpleCache.java:672–687`) и открытием: `FileDataSourceException(FileNotFoundException)` (`FileDataSource.java:181–203`); позиция за концом файла куска — `FileDataSourceException` с `ERROR_CODE_IO_READ_POSITION_OUT_OF_RANGE` (`:121–125`).

Поэтому `PlaybackCache.dataSource` отдаёт `CacheDataSource` в обёртке `DiskErrorDataSource`. Её `open`, `read` и `close` ловят `Cache.CacheException` и `FileDataSource.FileDataSourceException` и бросают вместо них `Cache.CacheException("The disk failed for play-…: <ошибка>")` без причины; в logcat — та же строка. Такую ошибку политика повторяет сразу (первый раз через 0 мс, `DefaultLoadErrorHandlingPolicy.java:128–132`). Повтор идёт мимо диска: `seenCacheError` уже стоит, а загрузчик повторяет ту же загрузку (`Loader.java:526–541`) с тем же источником — `ExtractingLoadable` держит `StatsDataSource` над источником периода (`ProgressiveMediaPeriod.java:1273`), и новые загрузки периода берут тот же (`:1060–1062`). Трек играет из сети, как до #89. Ошибки сети проходят как есть: `TeeDataSource` бросает ошибку сети без обёртки (`TeeDataSource.java:54–82`), а ни сеть, ни резолвер не бросают ни `CacheException`, ни `FileDataSourceException`. `close`, который упал после упавшего `open` или `read`, исходную ошибку не прячет: загрузка закрывает источник через `DataSourceUtil.closeQuietly` (`ProgressiveMediaPeriod.java:1351`, `DataSourceUtil.java:84–92`), а сама обёртка `close` из `catch` не зовёт. ENOSPC на `write` (ext4 с отложенным выделением) — `CacheDataSinkException(IOException)` без `FileNotFoundException`, такую политика повторяет и без обёртки. На JVM с настоящей `DefaultLoadErrorHandlingPolicy` это проверяет `DiskErrorDataSourceTest`; на устройстве не проверялось (#91, проверка 16 корневого `README.md`).

«Очистить кэш» в настройках Android посреди трека: уже открытый файл дочитывается, удалённая папка создаётся заново (`SimpleCache.java:380–385`), пропавшие куски выбрасываются из индекса (`:672–687`). Если папку стёрли между `cacheSubDir.exists()` (`:388–391`) и созданием файла, это ошибка создания файла из списка выше, и её ловит та же обёртка.

**Логи для #91** (тег `QiYaa`, debug):
- `Reading play-<процесс>-<n> from the disk at byte <b>` — каждое открытие куска на диске (`CacheFileDataSource.open`). Открытие получает позицию внутри куска, поэтому `b` = `uriPositionOffset + position`, байт файла трека. Чтение через границу куска даёт строку на каждый кусок, то есть на каждые 5 МиБ;
- `The disk failed for play-…: <ошибка>` — ошибка диска, которую `DiskErrorDataSource` сделала повторяемой; следом, на повторе, — `The disk cache is off for play-… after an error`. И `The disk cache is off for this run: …`;
- `Dropped <n> plays from the disk`, через 1 с — `Dropped the late fragments of <n> plays from the disk`, если у выброшенных игр появились куски;
- `Canceled the HTTP call of a canceled load stuck in a read` («`ReadInterrupts`» выше).

`onCachedBytesRead` не логируется: его зовёт только `close()` (`CacheDataSource.java:686`, `:888–893`), то есть в конце загрузки, а не когда началось чтение с диска.

**Что не меняется.** Предзагрузка и бесшовный переход: следующий трек — своя игра, и его первое открытие идёт в сеть. Битрейт: `CurrentBitrate.onResolved` зовёт только резолвер на первом открытии. Телеметрия: новых событий нет, ошибки диска трековыми не становятся. Куча. Джем (LISTEN-02, LISTEN-13): ссылки слушателей — по-прежнему `peek`, первое открытие каждой игры подписывает, чтение с диска не подписывает ничего; как и с буфером в памяти, перемотка назад больше не переподписывает ссылку старше 15 минут.

**Приватность.** Звук открытым текстом — текущий и следующий трек и, ненадолго, последний кусок (до 5 МиБ) выброшенной игры, в личной папке приложения (`cacheDir`: разрешений не нужно, в резервную копию и перенос между устройствами Android её не берёт). Удаляется на смене трека, на пустом плейлисте и при выходе из аккаунта (`keepFor`), в `onDestroy` (`clear`), а если процесс убит — при первой игре следующего процесса. Кусок, который загрузка выброшенной игры ещё пишет, первый проход удаления не видит («Что остаётся на диске» выше), его убирает второй, через 1 с. Успевает он, если загрузка закрылась раньше; обычно это доли секунды: чтение отменённой загрузки обрывается не позже чем через 0,1 с («`ReadInterrupts`» выше), но на устройстве это не измерялось. Если загрузка закрылась позже или процесс умер раньше, кусок живёт до следующей смены трека или до первой игры следующего процесса. Подписанные ссылки в индексе (редирект, `CacheDataSource.java:810–814`) живут час. Шифрования нет: можно было бы `AesCipherDataSink`/`AesCipherDataSource` со случайным ключом процесса в памяти.

**Traps:**
- Ошибка диска залипает: `seenCacheError` — поле источника, и его никто не сбрасывает (`CacheDataSource.java:866–875`). Один пропавший или вытесненный кусок выключает диск до конца этой игры, и чтение, и запись; следующая игра снова с диском.
- Индекс пишется на потоке загрузчика с `fsync` (`AtomicFile.java:175`), под замком кэша, но только когда он изменился: `store()` без изменений сразу возвращается (`storeIncremental`, `CachedContentIndex.java:563–567`). Меняют его новый ключ (`addNew` → `onUpdate`, `:339–346`), другие метаданные (`:326–331`) и удалённый ключ (`maybeRemove` → `onRemove`, `:284–290`); записанный кусок — нет (`addSpan`, `SimpleCache.java:694–698`). Сохраняют индекс открытие сети с записью на диск (`CacheDataSource.java:804–817` → `SimpleCache.applyContentMetadataMutations`, `SimpleCache.java:500–511`) и записанный кусок (`commitFile`, `:398–434`). На деле это одна запись с `fsync` на новую игру — на её первом открытии, до первого чтения (новый ключ и длина), — и одна после удалений `drop`, на ближайшем сохранении любой игры. Кроме этого, куски и закрытие отменённой загрузки индекс не пишут; повторное открытие сети той же игры пишет его, только если сменился конечный адрес ответа (редирект, `CacheDataSource.java:810–813`). Обычно это миллисекунды; в проверке #91 — «время до первого звука не изменилось».
- Без файлового индекса каждое открытие куска на диске переименовывает его файл: так LRU получает метку касания (`touchSpan`, `SimpleCache.java:637–661`).
- `SimpleCache.delete` и первая инициализация идут на потоке воспроизведения при первой игре процесса. На главный поток их не переносить.
- На JVM этот путь не проверить. `CachedContentIndex` держит id в `SparseArray`/`SparseBooleanArray` (`CachedContentIndex.java:94`, `:100`, `:103`), а на JVM это заглушки: каждый ключ получает id 0 (`getNewId`, `:355`), и `commitFile` падает на `SimpleCache.java:408–409`. `Uri.fromFile` (`CacheDataSource.java:736`) на JVM — `null`, и `DataSpec.Builder.build` падает. Поэтому JVM-тесты — только у `CachedPlays` и `DiskErrorDataSource` (над поддельным источником, `DiskErrorDataSourceTest`), остальное — проверка на телефоне (#91).
- `PlaybackCache` помечен `@OptIn(UnstableApi::class)` (`androidx.annotation.OptIn`), а не `@UnstableApi`, как `Media3Engine`: его держит `AppGraph`, а lint не принимает `@OptIn` на свойстве Kotlin и требует пометки и у свойства, и у вызова конструктора (`UnsafeOptInUsageError`). Наружу он отдаёт только стабильные `DataSource` и `Player`.
- `CachedPlays` зовут три потока: `newKey` — поток воспроизведения, `opened` — потоки загрузчиков (через `CacheKeyFactory`), `toDrop` — `removals`. Поэтому всё под одним замком: `HashMap` без него мог бы бросить `ConcurrentModificationException` на потоке `removals` и уронить приложение.

## `TimedAudioSink`

`buildAudioSink` оборачивает `DefaultAudioSink` в `TimedAudioSink(sink, audioBus.visualizerTap)`. `handleBuffer(buffer, presentationTimeUs, …)` сначала сообщает кольцу `announceInput(presentationTimeUs)`: процессоры вызываются внутри этого же `handleBuffer`, и отвод пишет кадры буфера с его временем. `getCurrentPositionUs`, который рендерер ExoPlayer спрашивает, пока играет, отдаёт звучащую позицию в тех же единицах и уже с учётом задержки `AudioTrack` и Bluetooth; `TimedAudioSink` передаёт её в `reportPlaying` с `System.nanoTime()`. Раз в 5 с пишет в logcat `Visualizer: the newest written audio sounds in N ms`.

**Traps:**
- С Media3 1.11 ExoPlayer по умолчанию планирует работу рендереров динамически (`dynamicSchedulingEnabled`), а PCM-буфер `AudioTrack` по умолчанию 500 мс (в 1.4.1 — четыре минимальных буфера в пределах 250–750 мс). `getCurrentPositionUs` поэтому может спрашиваться реже, и `VisualizerTap` чаще досчитывает позицию по часам (не больше 0,5 с, `audio/README.md`). Если на телефоне спектр начнёт отставать или дёргаться, выключатель — `ExoPlayer.Builder.experimentalSetDynamicSchedulingEnabled(false)` (`@ExperimentalApi`). На устройстве не проверялось.

## Процессоры

Оба — `BaseAudioProcessor` и работают только с `ENCODING_PCM_16BIT`. На другой формат (float, 24 бит) `onConfigure` возвращает `AudioFormat.NOT_SET`: процессор выключается, и `DefaultAudioSink` его пропускает, а звук идёт без EQ и визуализации, но играет. Раньше они бросали `UnhandledAudioFormatException`, и падало всё воспроизведение. `enableFloatOutput = false` держит декодеры в PCM16, так что это страховка. `EqualizerProcessor.onConfigure` сообщает формат в `AudioBus.setFormat`. `queueInput`: пустой буфер возвращается сразу — `replaceOutputBuffer(0)` в Media3 1.4–1.11 отдаёт общий `EMPTY_BUFFER`, и `put(inputBuffer)` на нём бросает «The source buffer is this buffer». `onFlush(streamMetadata)`/`onReset` сбрасывают состояние EQ и очищают кольцо (flush бывает и на каждой границе трека, «Следующий трек и бесшовный переход»); `onFlush()` без аргумента и `flush()` в Media3 1.11 устарели.

**Traps:**
- С Media3 1.8.0 `BaseAudioProcessor.reset()` больше не зовёт `onFlush`. В плеере это ничего не меняет: `AudioProcessingPipeline.reset()` сначала зовёт `flush(StreamMetadata.DEFAULT)`, потом `reset()`. Но прямой `reset()` (в тесте) кольцо `VisualizerTapProcessor` не очищает: у него нет `onReset`.

## Следующий трек и бесшовный переход

Своего кода здесь нет: следующий трек грузит и играет плейлист ExoPlayer, а приложение только подписывает ссылку, когда период открывает поток (`TrackResolver`). Всё ниже сверено по исходникам Media3 1.11.1; на устройстве не проверялось (Kickoman/QiYaa-android#91).

- **Когда начинает грузиться следующий трек.** `ExoPlayerImplInternal.maybeUpdateLoadingPeriod` (`ExoPlayerImplInternal.java:2769–2788`) создаёт период следующего элемента, как только `MediaPeriodQueue.shouldLoadNextMediaPeriod()` (`MediaPeriodQueue.java:209–215`): грузящийся период не последний (`isFinal`), загружен целиком (`isFullyBuffered`, весь файл извлечён), его длительность известна, и в очереди меньше 100 периодов. `prepare` нового периода сразу запускает загрузку на его собственном загрузчике (`ProgressiveMediaPeriod.prepare` → `loadCondition.open()` и `startLoading()`, `ProgressiveMediaPeriod.java:284–303`), так что первый кусок файла в 1 МиБ качается без вопроса к `LoadControl`: его спрашивают только после каждого куска (цикл — `ProgressiveMediaPeriod.java:1331–1344`). В этот момент `TrackResolver` подписывает ссылку следующего трека (logcat: `Signing the link of track <id> (<качество>)`, если свежей ссылки нет в `TrackUrlCache`), и уходит первый запрос за байтами. Раньше ничего не грузится: предзагрузка плейлиста выключена (`Media3Engine`, ловушка про `PreloadConfiguration`).
- **Когда это бывает.** Впереди загрузка встаёт на окне в 50 с плюс не больше одного куска в 1 МиБ («Перемотка и буфер», «Где лежат скачанные байты»). Схемы `qiyaa` нет в `LOCAL_PLAYBACK_SCHEMES` (`DefaultLoadControl.java:192–199`, `:952–960`), поэтому значения для локальных файлов (1 с) не действуют. Файл докачан, когда его остаток уместился в окно плюс один кусок: за 50–76 с до конца при 320 кбит/с, за 50–94 с при 192 кбит/с и за 50 с — 3 мин (50 + 131 с) при 64 кбит/с экономии. Файл экономии меньше 1 МиБ (трек до 2 мин 11 с) скачивается первым же куском, и следующий трек начинает грузиться почти сразу после старта текущего. Следующий трек грузится в то же окно: буфер считается через границу треков. Коротко: примерно за минуту или больше до конца (до ~3 мин в экономии), как только скачан текущий файл. Под нехваткой памяти (у кучи нет 4 % запаса) загрузка может встать на цели по байтам раньше окна, файл докачивается позже, и предзагрузка сдвигается ближе к концу трека («Перемотка и буфер», «Настройки», пункт о нехватке памяти). Десктоп начинает предзагрузку, когда скачан текущий файл, но качает файлы целиком, поэтому раньше. Заранее следующий трек грузят оба.
- **Стык.** Аудиорендерер читает сэмплы следующего трека сразу за текущими. На каждом новом периоде он заново настраивает выход (`MediaCodecRenderer.updateOutputFormatForTime` → `MediaCodecAudioRenderer.onOutputFormatChanged` → `AudioSink.configure`; у работающего выхода это `pendingConfiguration`, `DefaultAudioSink.java:835–836`). `DefaultAudioSink.handleBuffer` доигрывает процессоры (`drainToEndOfStream`) и, если `canReuseAudioOutput` (тот же PCM16, частота и каналы), оставляет `AudioTrack` («The current audio output can be reused», `DefaultAudioSink.java:941–968`): тишины плеер не добавляет. Файлы Яндекса в обоих качествах — 44,1 кГц стерео, так что и стык mp3 → HE-AAC оставляет `AudioTrack`, пересоздаётся только декодер. Файл другого формата (например, 48 кГц) сначала доигрывает старый `AudioTrack` до конца, потом создаёт новый.
- **Задержка и хвост кодера** обрезаются, если файл их объявляет. `Mp3Extractor` берёт их из ID3 `iTunSMPB` или из заголовка Xing/Info (LAME) (`Mp3Extractor.java:430`, `:605–609`), `Mp4Extractor` — из `udta` (`Mp4Extractor.java:649`) или из единственной правки `elst` (`BoxParser.java:795–817`). У MP4 экономии Яндекса `media_time` правки — 0 (десктопный `src/audio/README.md`), и вступление кодера HE-AAC звучит в обоих приложениях. Есть ли заголовок LAME у mp3 стандарта, неизвестно: это проверка на слух.
- **Только Android, на каждом стыке.** Взяв новую настройку, `DefaultAudioSink` заново ставит процессоры: `applyAudioProcessorPlaybackParametersAndSkipSilence` → `setupAudioProcessors` → `AudioProcessingPipeline.flush(StreamMetadata)` (`DefaultAudioSink.java:1704–1724`, `:842–860`). `EqualizerProcessor.onFlush` сбрасывает состояние фильтров, `VisualizerTapProcessor.onFlush` очищает кольцо. С включённым EQ фильтры стартуют с нуля посреди непрерывного звука, и на бесшовном стыке это может щёлкнуть. Это проверка на телефоне; если щёлкает, исправление — не сбрасывать EQ на flush границы трека (`StreamMetadata` несёт период), отдельной задачей.
- **Не бесшовно по замыслу.** Очередь ждёт догрузки волны (WAVE-08; десктоп тоже ждёт). Контроллер заворачивает голову при ждущих треках продолжения (CONT-10, только Android): ExoPlayer встаёт на паузу в конце трека (`pauseAtEndOfCurrent`), и `onPausedAtEnd` перематывает к первому треку головы (`queue/README.md`, «Повтор действует только в голове»). Так же — любая пауза в конце трека, когда цель обхода не естественный следующий трек (`QueueController.applyModes`). Если следующий трек сменился после начала загрузки (элемент джема встал за текущим) или загружается заново (`reload` при смене качества, QUAL-05), новый следующий грузится с нуля, и если до конца осталось меньше времени подписи и первых байтов, на стыке будет пауза.
- **Сеть пропала после предзагрузки.** Следующий трек начинается и играет то, что успел скачать (не больше окна и одного куска), потом действует ERR-03.

**Traps:**
- Состояние EQ и кольцо визуализатора сбрасываются на каждой границе трека, даже бесшовной (выше).
- Заворот головы CONT-10 не бесшовный: пауза в конце трека и перемотка.
- Любая перемотка в текущем треке выбрасывает подгруженный следующий: `seekToPeriodPosition` → `MediaPeriodQueue.removeAfter` (`ExoPlayerImplInternal.java:1866`, `:1890`). С сетью он грузится снова, как только текущий файл опять скачан до конца (после перемотки в скачанное — сразу), обычно по ссылке из кэша, и стык остаётся бесшовным; без сети после перемотки следующему треку играть нечего. Так было и до `PlayerBuffer`. Диск тут не помогает: заново созданный период следующего трека — новая игра с новым ключом («`PlaybackCache`»).
- Время предзагрузки зависит от битрейта, а не только от окна в 50 с: верхняя граница — 181 с до конца при 64 кбит/с экономии и 76 с при 320 кбит/с стандарта («Когда это бывает» выше), так что в экономии следующий трек может начать грузиться до 105 с (около 1¾ мин) раньше. Битрейт в бегущей строке от этого не меняется (кроме того же трека — ловушка «Хвост круга» выше): `CurrentBitrate` показывает трек, который играет.

## `JamHost`

```kotlin
class JamHost(transport: JamTransport, connectivity: Flow<Boolean>, queue: QueueController, catalog: JamCatalog, store: JamSessionStore,
              config: () -> JamHostConfig, scope: CoroutineScope, io: CoroutineContext, appVersion: String,
              signedLink: (trackId: String) -> String? = { null }, newId: () -> String = UUID, clock: () -> Long = System::currentTimeMillis, log: (String, Throwable?) -> Unit = …) : JamHandler, JamPlaybackListener {
    val state: StateFlow<JamHostState>      // phase NONE/CREATING/ACTIVE, connection, connected, room, joinUrl, storedSession
    val events: SharedFlow<JamHostEvent>    // Refused(reason), Ended(BY_HOST | BY_SERVER | EXPIRED | GONE), NotConnected
    fun create(hostName: String, settings: JamSettingsPatch? = null): Boolean;  fun cancelCreate()
    fun continueStored();  fun discardStored()          // «Продолжить джем?» (HOST-23)
    fun end()
    fun add(track: Track): Boolean;  fun playNext(track: Track): Boolean
    fun pin(itemId);  fun remove(itemId);  fun kick(publicId);  fun changeSettings(patch);  fun rotateLink()   // Boolean: false без связи
    fun onServiceStarted();  fun onServiceStopped()
    override fun onItemStarted(itemId);  override fun onPlayback(playback);  override fun onRemoveItems(itemIds)   // JamPlaybackListener очереди
}
interface JamCatalog { suspend fun searchTracks(text: String): List<Track>; suspend fun tracks(ids: List<String>): List<Track> }
data class JamHostConfig(serverUrl: String, waveFeedback: Boolean, shareAudio: Boolean = false)
```

Сценарии — `spec/jam/host.md`. `AppGraph` создаёт один `JamHost` на процесс (`scope` — `Dispatchers.Main.immediate`, `io` — `Dispatchers.IO`, `catalog` — `Library.searchTracks` и `tracksByIds`, хранилище — `data/JamFile`, настройки — `jam/server`, `jam/waveFeedback`). Ключа хозяина нет: комнату может создать любое приложение, сервер ограничивает их число на IP (ROOM-02).

- **Сессия.** `create` чистит имя `jam/JamNames.prefill` (края, серии пробелов ECMAScript, 24 кодовые точки) и проверяет его и настройки тем же `JamCodec`, что и входящие сообщения: сообщение, которое сервер отвергнет и закроет соединение, не уходит вовсе (иначе переподключение слало бы его снова). После `welcome` — `create`, а если сессия уже есть — `resume` со снимком и `outbox`. `created` сохраняет `roomId`, `hostSecret`, `joinUrl` и включает режим джема очереди (`startJam(this, waveFeedback)`; очередь хозяина становится базой и названия не меняет, `jam_queue_title` больше нет); `resumed` очищает `outbox` и отправляет `playing` (HOST-26). **Связь** (`connected`) — это принятый `create` или `resume` на текущем соединении, а не просто `welcome`: до неё `started` идёт в `outbox`, а `playing` и действия хозяина не отправляются (HOST-25).
- **Хранение** (HOST-22). Сессия, последний `snapshot`, новая ссылка из `linkRotated` и каждое изменение `outbox` пишутся в `JamSessionStore` на `io` через `Channel.CONFLATED`.
- **«Продолжить джем?»** (HOST-23). Сохранённая сессия видна как `state.storedSession`; вопрос задаёт UI. «Да» — режим джема очереди сразу (`QueueController.startJam(…, afterRestart = true)`: база пустеет, восстановленный текущий трек на паузе и ждущие элементы остаются, D7, D17), потом `resume`. «Нет» — хранилище очищается сразу, очередь заканчивает джем (`QueueController.endJam`: элементы теряют `itemId`, хвост волны на сидах джема уходит), потом `resume` и `end` только чтобы гости увидели конец.
- **Отказы.** `resume` с `room-not-found` или `bad-secret` заканчивает джем здесь (HOST-24, `Ended(GONE)`); с другой причиной — `Refused` и новая попытка через 30 с (`RESUME_RETRY_MS`). Отказ `create` (например, `rate-limited`: с этого IP уже 2 живые комнаты) — `Refused` и никакой сессии. Отказ действия — `Refused(reason)`.
- **`state`**: версия не больше последней на этом соединении пропускается, первая после переподключения берётся как есть. Очередь уходит в `QueueController.onJamQueue` с сидами и `seedsVersion`.
- **Гости** (HOST-28…31). `searchRequest` — `Library.searchTracks` (`type=track`), доступные, до 20, `JamTracks.toJam`; ошибка — `failed`, 401/403 — `unauthorized` (сам вход покажет `yandex/Session`). `validateRequest` — `POST /tracks`: по ответу на каждый id по порядку, недоступный или пропавший — `track-unavailable`, упавший запрос — `failed` для всех. Оба запроса идут отдельными корутинами на `io` и не ждут плеер.
- **`command{skip}`** — `QueueController.jamSkip` (HOST-18, HOST-19).
- **Убрать элементы** (HOST-36, HOST-25). `onRemoveItems(itemIds)` зовёт очередь, когда REM плейлиста выбрал ждущие элементы джема: при связи — `remove{itemId}` на каждый, элементы уйдут со следующим `state`; без связи — ничего не уходит, и событие `JamHostEvent.NotConnected` (тост `jam_no_connection`). Остальные выбранные строки очередь удаляет сама и без связи.
- **`playing`** — из `onPlayback` очереди, только при связи (HOST-25: `playing` не копится). `ITEM` — `playing{source: item, itemId}`; `BASE` — любой трек базы, в том числе трек волны джема и элемент прошлого джема, — `playing{source: wave, track}` (HOST-10, HOST-14: протокол 1 сохраняет имя `wave`, `spec/jam/protocol/README.md` говорит, что оно покрывает любой трек базы); трек, который протокол не несёт (`JamTracks.toJam` — null), не сообщается вовсе; `IDLE` — `playing{source: idle}`.
- **Добавить** (HOST-20). `add` шлёт `add{track}`; трек попадает в хвост только со следующим `state`. `playNext` — `pin` для уже ждущего трека, иначе `add` и `pin`, когда элемент с этим треком от хозяина появится в `state`.
- **Конец** (HOST-32). `end()` отправляет `end`, если есть связь, и в любом случае заканчивает локально: `QueueController.endJam`, хранилище очищается, соединение закрывается. `ended` от сервера — то же без `end`.
- **Слушать вместе** (`spec/jam/listen.md`, LISTEN-01–05, LISTEN-13). С `JamHostConfig.shareAudio` (`Settings.jamShareAudio`, по умолчанию выключено) `playing` трека джема и трека базы несёт `listenUrl` — ссылку на файл, который играет, и `listenNextUrl` — на следующий (`JamPlayback.nextTrack`). Ссылки берутся из `TrackUrlCache.peek` — уже подписанные, без новых запросов к Яндексу; кэш теперь общий (`AppGraph.trackLinks`) для плеера и хозяина джема. Ссылка не из хранилища Яндекса (`JamCodec.isListenUrl`) не уходит: сервер отказал бы во всём `playing`. Поэтому файл экономии (`strm*.strm.yandex.net`, не `/get-mp3/`) слушателям не передаётся (LISTEN-13).
- **Соединение живёт с `PlaybackService`**: `onCreate` сервиса зовёт `onServiceStarted` (идёт джем — `resume`), `onDestroy` — `onServiceStopped` (соединение закрывается, джем остаётся в памяти и на диске, комната ждёт хозяина час, REC-05). На переднем плане ради джема сервис не держим.

## `JamTracks`

`toJam(track)` — `null`, если трек не проходит протокол (id не `^[0-9A-Za-z_-]{1,64}$`, пустое название); управляющие символы → пробелы, название ≤ 150, исполнители ≤ 10 по ≤ 64 символа, длительность 0…24 ч. `coverUri` восстанавливается из `coverUrl`: без схемы, `400x400` в конце → `%%`; адрес без размера, длиннее 300 знаков UTF-16 или такой, что не проходит `JamCodec.isCoverUri` (пробел ECMAScript внутри), — без обложки. `fromJam` — обратно через `TrackParsing.coverUrl`.

Тем же `toJam` строит трек для своего `add{track}` гость в приложении (GUEST-07, `jam/JamGuest`), как хозяин строит треки для гостей (`spec/jam/host.md`, «Search and check for guests»). Отправитель считает пределы в знаках UTF-16 (строже кодека, который считает кодовые точки, как Ajv), поэтому худший случай для кадра — трёхбайтовые знаки (CJK) во всех полях: такой `add` весит около 3,6 КБ и влезает в 4 КиБ кадра гостя (`limits.md`, `JamTracksTest`).
